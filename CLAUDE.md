# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Unity 6 (6000.3.9f1) C# mobile application for WhatsApp and Telegram bot automation. Manages chat interfaces, bot creation, and workflow automation with products, services, and messaging features. Targets iOS and Android via URP (Universal Render Pipeline).

## Build & Development

- **Unity version**: 6000.3.9f1 — open through Unity Hub
- **Rendering**: Universal Render Pipeline (URP 17.3.0)
- **Solution**: `Automation.sln` (auto-generated by Unity, gitignored)
- **NuGet packages**: managed via NuGetForUnity in "In Packages folder" placement — everything lives under `Packages/nuget-packages/` (`NuGet.config`, `packages.config`, `InstalledPackages/`). Keep NuGet files out of `Assets/`; the plugin reads `Packages/nuget-packages/NuGet.config` first and only falls back to `Assets/NuGet.config`
- **Git LFS**: enabled for binary assets (textures, audio, fonts, plugins) — see `.gitattributes`
- **Icon lab** (`Tools/icon-lab/`): the app's own icon set — 6 business-tile glyphs + 4 nav tabs × outline/filled — is authored as hand-written SVG in `glyphs/*.svg`, the single source of truth. `node publish.js` renders them into the project; `python3 lint.py` checks the style contract in `STYLE.md` and *measures* each glyph (ink bounds, coverage, centroid) so the set stays a family by number rather than by eye; `preview.py`/`sheet.py` composite onto dark at true device size. Two rules worth knowing before touching it: the glyphs are white on transparency, so opening a rendered PNG directly shows white-on-white and reads as blank — always review through `preview.py`; and business glyphs are published *over* the existing `BT_*.png` filenames on purpose, because the `.meta` guid beside each one is what `BusinessTypes.asset` references. `Tools/render_business_icons.js` is now a thin delegate to `publish.js` (it used to hold its own copy of the geometry, which would silently overwrite the published icons).

Command-line build example:
```
Unity -batchmode -nographics -projectPath . -buildTarget Android -quit
```

### Running EditMode tests

EditMode tests live in `Assets/Tests/Editor/Chat/` (no asmdef — they compile into the predefined `Assembly-CSharp-Editor`). Two ways to run them:

- **Editor closed (headless, hands-off)** — `Tools/run-tests-headless.sh`. Launches Unity in batch mode (`-runTests -batchmode -nographics -testPlatform EditMode`, never `-quit`), parses the NUnit3 result, and writes outputs to `Tools/test-output/` (gitignored — must NOT be under `Temp/`, which Unity wipes on launch). Refuses if the Editor has the project open (the project lock is single-instance). Pass a `-testFilter` regex as `$1` to scope the run.
- **Editor open** — `Assets/Editor/ClaudeTestBridge.cs`: drop `Temp/claude/run-tests.trigger`, read `Temp/claude/test-summary.json`. Runs the suite inside the already-open Editor (which must be focused).

## Architecture

**Single scene**: `Assets/Scenes/Main.unity` — all UI is canvas-based, toggled via `GameObject.SetActive()`. No scene transitions.

The keyboard exists ONLY while the field is focused, the panel is the slot's DEFAULT tenant, and Collapsed is reachable ONLY by dragging the 42u `SuggestionSlotDragHandle`. **Six traps, each already paid for — do not undo:** (1) never decide tenancy from `_slotState` — `MessagesBottomPanel.KeepKeyboardOpenRoutine` holds the keyboard after every Send, so the answered-run collapse leaves Collapsed sitting over a LIVE keyboard and the next incoming message would tear it away mid-word; `ApplySlotInput` resolves against `NativeKeyboardVisible` and `ShowPanel` keeps its `(kbVisible || AttachOpen) && !claim` park guard. (2) A key/field tap must NOT set state=Keyboard — the swap watcher recognises the claim as `kbVisible && PanelOwnsSlot`, so flipping early kills the no-dip hold forever and parks the panel active behind the keyboard all session; the watcher owns that transition. (3) The keyboard→panel RETURN must HOLD the inset too (`_lastKeyboardCanvasPx`), and be LEVEL-triggered: it fires the frame the keyboard is already gone, an edge eaten by a guard (the «+» sheet) strands the slot with no tenant. (4) Yielding from Expanded retargets the hold DOWN to standard first — `SuggestionSlotSwap.ShouldReleaseHold`'s 95% fraction can never be met by a slot taller than the keyboard, so it would freeze for the full 0.7s timeout and then snap. (5) Thread-tap: read `ScrollClickBlocker.IsBlocking` at RELEASE (it latches in its own Update on the press frame, unordered), and a tap ON a bubble IS a thread tap — rejecting on gesture-component presence leaves the rule alive only in the gaps between messages; modals need explicit checks because `RaycastAll` does no occlusion culling. (6) The chat-open auto-show must WAIT for the chat to finish opening (`SuggestionSlotOpenTiming`, 2026-08-18). `ChatManager.SelectChat` fires `OnChatSelected` synchronously on the row tap, so `RestoreForActiveChat`→`ShowPanel` claims the slot ~600ms before the chat screen exists (300ms Prep + the ~290ms slide); the claim is invisible while it is made — `MessagesPanel` is deactivated, so `KeyboardAwarePanel.Update` never runs and its `OnDisable` already reset the applied rise to rest — and then lands ALL AT ONCE on the slide's FIRST frame, so the panel rises over exactly the frames the chat travels right-to-left and the chat appears to open diagonally. The rise is not started too early, it is APPLIED at the wrong moment: `ShowPanel` therefore parks (`_pendingShow`) until `!SwipeToBack.IsSliding && Phase ∈ {Populate, Idle}` plus a 0.12s settle beat, and `Update`'s lander carries the same gate. The beat is load-bearing, not cosmetic: `PopulateBubbles` runs INSIDE the slide's own onComplete, so the thread's first batch lays out on the very frames after the slide and a tween started into it stutters. The settle clock is reset in BOTH `OnDisable` and `RestoreForActiveChat` — a re-open that never closed the screen would otherwise still carry the previous chat's settled stamp. Scene surface is built by `SuggestionsSlotHeadlessBuild.Run` (builder + wirer + save); the tint circle is 64u not the sketch's 81u (the 74u composer pill carries a `RectMask2D` inset 8u — 81 overflowed AND sheared to a chord), and the handle costs the standard detent 42u of visible card area. **Second collapse entry — the thread pull-down (2026-08-19).** Dragging the thread down past the composer's top edge takes the slot with the finger (`SlotPullDownRecognizer` + the pure `SuggestionSlotPullDown`), and over a live keyboard it is a one-shot dismissal landing on Collapsed via `SuggestionSlotInput.PullDownDismiss` — the ONE deliberate override of «keyboard leaves ⇒ panel takes the slot». Five things are load-bearing. (1) It hangs off `SnappyFlickScrollRect`'s own drag events, NOT off a sibling `IDragHandler`: bubbles carry `SwipeToReply`, which forwards vertical drags with a TYPED `_scroll.OnDrag(e)` call rather than through `ExecuteEvents` (so does `DragShield`, and `SwipeToBack`'s left-band routing resolves to that same `SwipeToReply`), so a sibling component would only see drags starting in the gaps BETWEEN bubbles. `ScrollRect`'s callbacks are the one point every path converges on, and the component is already in the scene — the gesture ships with zero scene edits. (2) The engage test is a POSITION test against the composer's LIVE top edge, never a delta: that is what makes the handoff continuous (at the crossing instant the finger IS that edge, so the tracked height equals the height on screen and the panel cannot jump), and the line must be re-read every frame because it rides the inset. (3) The flick rule (`SuggestionSlotDetents.SnapWithFlick`, shared with the handle) needs BOTH a velocity threshold and `MinFlickTravelCanvasPx` — the engage line sits at roughly the lower 40% of the screen, so ordinary «scroll back through history» gestures cross it at speed and would otherwise collapse the panel every time; and the flick's upward outcome is scoped by the GESTURE's ceiling (the handle's is the Expanded detent, the pull-down's is its engage height), or pulling down a little and flicking back up would expand a panel the owner never dragged. (4) `PointerDown` carries a pointer-ownership guard (`if (_tracking && pointerId != _pointerId) return;` in `SlotPullDownRecognizer`, mirroring `SuggestionSlotDragHandle`'s own `IsDragging` guard) — the first finger owns the gesture until it releases; without the guard a second finger's press clears the engaged state and `Released` never fires, stranding the slot between detents with the 1:1 tracking latch still held. (5) `HandleKeyboardPullDown` clears `_yieldingToKeyboard` BEFORE routing the input — during a panel→keyboard handoff the controller holds the inset and parks in that latch (the no-dip rule), and `HidePanel` early-returns while it is set, so routing with the flag still true would leave the yield live and `Update`'s «the keyboard bounced away before taking the slot» branch would put the panel back up on the next frame, the exact opposite of what the keyboard branch exists for.
  - **Slot settle + the empty state's chassis (2026-08-20, device-forced).** Two rules the collapse depends on. (1) **The settle must CONTINUE the release, not restart it.** Every inset animation goes through `SuggestionsController.TweenInsetTo`, which HOLDS `TrackInsetImmediately` for the tween's length and releases it in `OnKill` (never `OnComplete` — an interrupted tween would strand it). Dropping the flag at release instead let `KeyboardAwarePanel` resume SmoothDamp *on top of* the tween, two smoothers in series, and because the flag pins the smoothing velocity at ZERO for its whole life the second one restarted from a dead stop — which read on device as the panel pausing partway down to decide whether to keep going. The collapse tween is `Ease.OutCubic` for the same reason (`InCubic` opens at zero speed, a pause on a motion already moving), and its duration comes from `SlotSettleMotion.Duration`: a cubic-out covers distance D in time d with INITIAL speed 3D/d, so matching the finger's speed v means `d = 3D/v`, clamped. A hide the owner did not initiate (answered run, «Авто») deliberately keeps the neutral `InCubic` + `DefaultSeconds` — there is no speed to match there. (2) **The empty/error block is positioned, never resized.** `SuggestionsPanelBuilder` stretches those overlays over the card area, which handed the area's shrink to their `VerticalLayoutGroup`; with `childControlHeight` it lerps children from preferred toward MIN, and the two labels are plain TMP with a min of 0, so their rects collapsed while the glyphs kept drawing and the lines printed on top of each other. The runtime owns the chassis instead (`EnsureStateChassis` + `SuggestionStateLayout.TopOffset`): top-anchored with a `ContentSizeFitter`, centred while the area holds it, pinned to the area's TOP once it does not. **Row height chain (2026-08-18 fix).** The thread nests `Content` (VerticalLayoutGroup, `childControlHeight=false`, spacing 10) → row = `MessageText{Incoming,Outgoing}` root (HorizontalLayoutGroup + ContentSizeFitter) → `Bubble` (VerticalLayoutGroup + ContentSizeFitter). A layout group with `childControlHeight=false` sizes itself from `child.sizeDelta` — the child's size from the PREVIOUS pass — and `LayoutRebuilder.PerformLayoutControl` runs the row's fitter (an `ILayoutSelfController`) BEFORE descending to the bubble's, so the row shipped permanently one pass behind the bubble. It never self-healed: the dirty the bubble's resize raises lands mid-pass and `CanvasUpdateRegistry` drops it (that layout root is already queued, and the queue is cleared when the pass ends), so the mis-size survived until something unrelated dirtied the tree — which is why it read as "only some bubbles, only sometimes". Row too SHORT → the bubble overflows into the 10px inter-row spacing (**bubbles look glued to the next message**); row too TALL → `Tail`/`TailOutline` (ignoreLayout, anchored to the ROW's bottom edge at y≈16) hang below the corner (**detached tail**). Replies were the visible victims because they are the only bubbles whose height changes AFTER bind, via the async quote resolve. Two halves of the fix, both load-bearing — do NOT undo: (1) the row root's HLG carries `childControlHeight = true` so it reads the bubble's freshly computed preferred height in the same pass (`childControlWidth` stays FALSE — the bubble's own fitter owns width, and `AdjustTextBubbleSize`'s max-width clamps measure against that); pinned by `BubbleRowHeightLagTests`. (2) `HandleMediaRefreshed` must NOT skip the layout rebuild — it carries the quote resolution, and `ForceRebuildRoutine`'s deferred parent mark (a frame later, outside any layout pass) is the only rebuild request uGUI will not swallow. Same pattern (a `childControlHeight=false` group over a ContentSizeFitter child) still exists on 11 static scene nodes (auth QR/code panels, the add-bot form) — harmless there because nothing changes their height asynchronously and no ignoreLayout element rides their bottom edge.
  - **Bubble tail rendering — the device-only grey box (2026-08-19 fix).** The tail is two `Image`s over ONE sprite (`Assets/Images/Chat/Tail.png`): `Tail` (fill, STOCK UI material, runtime-tinted to the bubble colour, so only the sprite's ALPHA is ever visible) and `TailOutline`, which carries the project's only hand-authored UI material — `Assets/Shaders/TailOutlineDilated.mat` → `UI/TailDilatedOutline`, a uniform rim built by 8-direction alpha dilation. That shader's `SampleArtAlpha` used to issue an implicit-derivative `tex2D` from INSIDE its out-of-bounds early return. **A texture sample in divergent control flow has an UNDEFINED mip level**: the desktop compiler the Editor runs flattens the branch and keeps the derivatives valid, the GLES/Metal compilers keep it — the LOD collapsed toward the smallest mip (mean alpha 0.239) and the whole outline quad rendered as a uniform ~24 %-opacity `BubbleBorder` rectangle, rgb(19,22,27) over the rgb(9,11,14) wallpaper: a faint square around every tail on device, perfectly clean in the Editor. Fixed by sampling `tex2Dlod(..., mip 0)` branchlessly (a `step()` bounds mask) under `#pragma target 3.0`, and pinned by `TailOutlineShaderTests` — a source-invariant guard because EditMode cannot render a shader at all. **Do NOT "harden" this further by unticking mipmaps on Tail.png.** The FILL still selects its mip implicitly and the sprite is genuinely minified 3.4×–6.5× on every shipping device (CanvasScaler is match-width, so scaleFactor = screenWidth/1080), so mip 0 would undersample the antialiased edge that IS the tail and make it crawl as the thread scrolls. Two facts to carry into any future work on this texture: the live sprite is `spriteMode: 1` (Single) covering the FULL 200×103 texture — the `spriteSheet` slice the .meta still lists (`tail 8_0`, rect 4,0,120,102) is dead residue that the importer ignores, and `_OuterUV × 200×103` reproduces the sprite's `textureRect` byte-for-byte, which is the proof; and cropping the ~40 % transparent padding (the genuinely right lever, it would drop the density AND remove the mip bleed against the art's right edge) is NOT free, because the material bakes `_OuterUV`/`_UVInset`/`_DilateUV` as texture-geometry constants that no code recomputes and no test covers. The same construct — a sample after a data-dependent `return` — also sits in the Nobi package's `RoundedCorners.shader:88`, used by 241 scene Images; it has never manifested because the coordinate there is the identical `i.uv` already sampled unconditionally ten lines above, so the compiler reuses that derivative. ### Caching strategy

- Chat list: `persistentDataPath/BotCache/{botId}/chats.json` (per-bot; the root-level `all_chats_cache.json` is legacy with no code references)
- Message history: `ChatHistoryCache` (per `chatId`, max 100 messages)
- Media/thumbnails: `MediaCacheManager` saves to disk, keyed by URL

Until then, an in-WhatsApp-app-removed reaction stays shown — don't hand-patch a partial fix.
  - `message/mark/read` — read receipt (POST, query `profile_id` + `mark_all=true`, body `{ message_id }`). URL shape lives in `MarkReadRequest` (pinned by `MarkReadRequestTests`); local read bookkeeping in `ReadAckLedger`. **Verified live on a group, 2026-08-12** (`Tools/wappi/probe-group-mark-read.py`) — do NOT re-derive: `mark_all=true` DOES work for group chats, one call clears the whole chat (`unread_count` 3 → 0, every incoming flipped `isRead=true`), and the body's `message_id` acts as a trigger/watermark rather than the thing being marked — it worked with an OUTGOING REACTION's id. So there is no group-aware per-message path to build. Two traps around this: (1) the docs' note «Работает только для личных чатов, для групп не работает» appears exactly once on the WhatsApp page and belongs to **`messages/get`**'s own `mark_all`, NOT to this endpoint — that lever is the 1:1-only one; (2) `chats/filter`'s `unread_count` does not count `type:"reaction"` rows, while `last_message_id` CAN be one, so a chat can legitimately show `unread_count=2` alongside 3 `isRead=false` incoming rows. (3) **read state is PER-WAPPI-PROFILE, not per WhatsApp account** — the trap that makes a working ack look broken. Two profiles on the SAME number keep independent `unread_count`/`isRead`: verified 2026-08-12 by a CROSSOVER on one group, same messages, same build, profile the only variable: with the bot on `b7a44f5d` the app drove that profile to `unread_count=0` while sibling `7dff1887` held `unread_count=2` + 3 `isRead=false` (stable across polls minutes apart, so not lag); switching the bot to `7dff1887` and reopening the same chat then took THAT profile 2 → 0 too. Each profile acks only for itself. So when verifying anything read-related, query the profile the ACTIVE BOT uses — querying a sibling profile of the same number shows a false negative and will send you hunting a client bug that isn't there. A chat still showing unread on next launch usually just means it was never opened in-app on THAT profile (`SelectChat` is the only thing that acks). **Native reads DO reach Wappi — but only LIVE, and the receipt is one-shot.** Verified 2026-08-12 on a private chat genuinely unread on the phone: the owner read it in the WhatsApp app and BOTH sibling profiles flipped `unread_count`/`isRead` to 0 within ~2–4 min, our app not involved (support says seconds). An earlier same-day test "proved" the opposite — that was bad material: re-opening a chat the phone had ALREADY read emits no fresh read-self receipt, so nothing can propagate. Never test read-sync with an already-read chat; the stimulus must be a chat still showing unread ON THE PHONE. Corollary that explains stuck badges: a receipt Wappi missed (profile unauthorized/disconnected at the moment of reading — both profiles' `payment_expired_at` kept lapsing here) is gone forever — history sync does NOT carry read state and the phone never re-emits for an already-read chat, so such rows stay `isRead=false` until an in-app open acks them. One UNCONFIRMED observation: after 7dff1887's 15:39Z re-authorization, group rows acked read ~1h earlier were back to `isRead=false` while the non-re-authed sibling kept 0 — suspect re-auth resurrects the recent window's unread state when a "read" chat comes back. No webhook covers read/unread (catalogue: `authorization_status`, `incoming_message`, `delivery_status` = status of messages WE sent, `outgoing_message_phone`, `outgoing_message_api`, `application_status`) — polling `chats/filter` is the only way to observe reads. Badge meaning, precisely: «unread by Wappi» = phone state as of the receipts it caught live, minus our own acks; rows accumulate as stale in missed windows, and `ReadAckLedger` being in-memory means our acks re-derive from the server on every launch. tapi documents no `mark_all` here at all — its bulk lever is `mark_all` on `messages/get` — so the Telegram branch must never gain it.
  - `chat/delete` — delete a chat (POST, body `{ recipient }` where recipient = chatId minus `@c.us`; success `status:"done"`). A successful call deletes the chat in WhatsApp; Wappi then reports it back in `chats/filter` with a sticky `isDeleted:true`. Backs swipe-to-delete: `ChatManager.DeleteChat.cs` removes the row optimistically (rollback on failure) + evicts `ChatHistoryCache`; `ParseChatsJson` hides any chat with `isDeleted == true`, so a deletion sticks across sync/bot-switch/restart. **Confirmed platform limits** (don't try to "fix" these — they're Wappi/WhatsApp constraints): the call is per-Wappi-profile and does NOT propagate to other bots; deletes made directly in the WhatsApp app do NOT set `isDeleted` and are invisible to us; re-deleting an already-`isDeleted` chat returns HTTP 400 `deleteChat error`. (A persistent per-bot watermark + revival design was built and then reverted — `isDeleted` is sticky-true even after new activity, so there's no reliable revival signal and the extra layer wasn't worth it.)
  - **Incoming replies**: a reply message carries `isReply: true` + (often, but not always) a `reply_message` snapshot of the quoted original — keys `id` / `type` / `body` / `caption` / `contact_name` (the quoted sender; NOT `senderName`) / `file_name`; no `fromMe`. Resolved by `ReplyParser` (cache-by-id → snapshot → placeholder) into flat `quoted*` fields carried through the 4-layer message pipeline; rendered as a quoted card by `MessageItemView`. The `reply_message` id is always correct, but its `body` is sometimes absent or **echoes the replying message's own text** — `ReplyParser.FromSnapshot` detects that (snapshot body == own raw body) and blanks it, then the card is recovered by fetching the original via `messages/id/get` (`QuotedMessageCache` + `ChatManager.QuoteResolve.cs`, mirroring the reaction-target resolver). Reply triggers: swipe-right (`SwipeToReply`) + the long-press action menu (`ReactionBarController`).
  - `qr/get` — QR code for WhatsApp login
  - `auth/code` — request phone pairing code (`profile_id` + `phone`; response `code` is displayed in-app, user types it into WhatsApp). **Confirmed platform limit**: WhatsApp refuses a repeat code for the same profile for ~2 minutes. The resend button therefore silently deletes + recreates the Wappi profile (same name) behind the loading overlay and requests the code on the fresh profile — `Manager.GetWhatsappCode` → `RecreateWhatsappProfileForNewCode` (with a pre-delete `get/status` guard so a just-authorized profile is never destroyed). Don't "simplify" resend back to a plain re-request; safe in both wizard and settings flows because no n8n workflow exists while the code panel is reachable (workflows are created after auth; change-number/logout delete them first)
  - `get/status` — connection status
  - `contact/info` — contact details
  - `profile/add`, `profile/delete`, `profile/logout`

The Enable coroutines also skip the `""`/`"-1"` sentinel ids (channel never authed → no workflow → guaranteed 404)

Both `Create*WorkflowFromEdit` forms send the same composed value; the `Create*WorkflowFromStart` forms still send `""` (a brand-new bot has no settings yet)
  - `/webhook/UploadFile` — price-list upload. The app mints a GUID `fileId` per file (form field), records it in `PendingUploadLedger` immediately before sending (so a process kill mid-upload is swept at next launch rather than orphaning the chunks), and persists `{fileId, name, size, date}` per bot in PlayerPrefs (`UploadedFilesStore`) on success; the workflow stamps `fileId` onto every RAG chunk's metadata in Supabase `documents`. For documents, the app converts structured formats (xml/csv/tsv/xls/xlsx/xlsm/docx/rtf/html — with cp1251/UTF-16 encoding sniffing, ru-locale ';' CSV, 1C "fake .xls" HTML/SpreadsheetML detection) to plain text CLIENT-side (see `Converters/`) — deliberate: the converters emit RAG-ready, entity-labeled text that generic server extraction can't, and n8n's Extract From File can't parse docx (and its rtf op only reads tables). For photos (jpg/jpeg/png/webp/heic client-side sources), the app uses `ImageUploadPreprocessor` to decode, downscale to 2048px max, and re-encode as JPEG q85 before sending. The workflow ingests text/plain + PDF (extension routing case-insensitive) via document converters, and routes JPEG via a Switch branch to OpenAI gpt-4o-mini vision extraction (emits same entity-labeled `{contentType}[N]:...` lines); unreadable photos get HTTP 422 `{"success": false, "error": "no_price_data"}` (no retry).   - `/webhook/DeleteBotFiles` — body `{ botWaId, botTgId }`; sweeps ALL of a deleted bot's RAG chunks (matched by either workflow id, guarding the `"-1"` unauthed sentinel so shared-unauthed chunks are never touched) plus each file's stored original (including legacy chunks with no fileId — those just have no bucket object). ## Additional Instructions

- All API calls use `UnityWebRequest` with coroutines (`IEnumerator` + `yield return SendWebRequest()`). Follow this pattern for any new network calls.
- Never hardcode API keys or tokens directly in source files. All secrets are loaded from `Assets/StreamingAssets/secrets.json` via the `Secrets` class (see `Secrets.cs`). Use `secrets.json.example` as a template.
- When adding new API endpoints, follow the existing pattern: build URL with string interpolation, set auth header, send request, check `request.result`, parse JSON response with `JsonConvert.DeserializeObject`.
- Chat data flows through serializable model classes (`ChatDialog`, `NormalizedMessage`, `RawMessage`) — keep API response models in `Assets/Scripts/Chat/`.

## Conventions

- Singleton pattern for managers (`Manager.Instance`, `ChatManager.Instance`, `BotsPage.Instance`)
- MonoBehaviour with `[SerializeField]` for UI references
- PascalCase for classes, methods, and properties
- Prefab-based reusable components in `Assets/Prefabs/`
- Platform-specific code isolated in bridge classes (`AndroidBridge`, `IOSBridge`)
- TMPro for all text rendering
- DOTween for UI animations
- Bot entity persistence: `PlayerPrefs` keyed by `transform.name` (e.g. `Bot0Name`, `Bot0Products0`)
- Event-driven UI: views subscribe to `ChatManager` events rather than polling
- Partial classes for large components: see `BotSettings.cs` / `BotSettings.Auth.cs`
- **The UI ships in Russian only.** English/Kazakh are planned but there is deliberately NO localization
  layer yet (owner's call, 2026-08-19): every user-facing string is written in Russian at its site — in the
  scene, in the prefab, and in the C# that authors it. Three rules keep it that way:
  (1) **Never format a user-facing date/number through the ambient culture.** `ToString("dddd")`, `("MMM")`
  and friends read `CultureInfo.CurrentCulture`, which follows the DEVICE locale — an English phone printed
  English weekday separators inside the Russian chat. Go through `RuDateFormat` (and keep
  `CultureInfo.InvariantCulture` on the NUMBER wherever a decimal separator is formatted, e.g.
  `AttachmentDisplayFormat`). `DashboardTimeFormat` established this shape first.
  (2) **Counted nouns go through `RuPlural.Pick`,** never a hand-rolled `n == 1 ? … : …` — 11..14 take the
  "many" form despite ending in 1..4 (`UnreadSeparatorView`, the document bubble's page count).
  (3) **A visible label that is ALSO a logic sentinel must be a shared constant.** `ReplyParser.OwnSenderLabel`
  is the live example: `MessageItemView` colours the quoted card by comparing against it, so translating a
  hand-typed `"You"` at one site would silently drop the accent. `ReplyParser.IsOwnSenderLabel` also accepts
  the pre-RU `"You"` still sitting in `ChatHistoryCache` on older installs.
  (4) **An authored UI character must exist in the static SF Pro atlases.** All four SFProText SDFs are
  static 711-glyph atlases with NO fallbacks (TMP Settings global fallbacks are empty too), so a char
  outside the table renders as NOTHING and TMP only logs at layout time — «до −17%» shipped as «до 17%»
  (U+2212 minus, fixed to ASCII "-" in f4fe603) and the Support FAQ's «→» never rendered. Known-absent:
  − (U+2212 → use "-"), № (U+2116), ✕ (U+2715 → use × U+00D7), → (U+2192 → use › U+203A), ⇒, ∈, ✦, ⌨.
  Present and safe: - – — … « » ‹ › ' ' " " • · ₸ × NBSP. Only the LiberationSans chain (chat bubbles /
  TMP default font) is dynamic and can draw anything in LiberationSans.ttf. `FontGlyphCoverageTests`
  pins the whole class: every serialized label in Main.unity + Assets/Prefabs against its own font, and
  the copy seams (billing `*Rows`/`PaywallCopy`, dashboard labels, FAQ, prompt catalog) against SF Pro —
  extend its seam list when adding a new copy seam.
  Deliberately NOT translated: brand names (WhatsApp/Telegram/Instagram/n8n) and format acronyms (PDF/DOCX/GIF/QR);
  the hidden `Bot/Status` TMP, whose `"Active"`/`"Connecting.."` are a data channel `Bot.cs` reads (it paints the
  visible subline off `Status.color`, not the text); the dev-only n8n URL field; and every server-payload string
  (`Manager.ComposeBusinessKnowledge`'s `"About Business:"` + contact keys are an LLM-prompt contract, not UI).
  When you translate a scene/prefab label, translate the Editor builder that authors it in the same change —
  otherwise the next builder run silently reverts it.

# Блок 2 «обещания витрины»: алерты, отчёт, Сводка, расписание, голосовые — дизайн

**Дата:** 2026-08-27 · **Статус:** утверждено владельцем (brainstorm 2026-08-27), готово к планированию
**Контекст:** Блок 1 (ядро биллинга) закрыт и живьём проверен 2026-08-26. Правило запуска из спеки
Блока 1 §7: пейволл не публикуется, пока каждая строка «Во всех тарифах» не работает. Этот блок
закрывает недостающие строки + технические хвосты Блока 1. Плашек «скоро» нет.

## 1. Решения владельца (зафиксированы 2026-08-27)

- **Доставка алертов и отчёта:** сообщением САМОМУ СЕБЕ через собственный подключённый Wappi-профиль
  клиента («Сообщение себе» WhatsApp / Saved Messages Telegram). WhatsApp приоритетно, иначе Telegram.
  Ноль новой инфраструктуры, работает у каждого клиента автоматически. ✓
- **Детекция «готов купить»/«нужен владелец»:** серверный свип ~каждые 10 минут, переиспользующий
  классификацию Сводки; алерт на ПЕРЕХОДЕ статуса; горячий путь ответа бота не трогается. ✓
- **Расписание:** одно окно «с … до …» + чипы дней недели Пн–Вс. ✓
- **Экспорт Сводки:** CSV через системный share sheet. ✓

## 2. Delivery seam — «сообщение себе» (несущая опора всего блока)

Один переиспользуемый механизм отправки в n8n: по `app_user_id` выбрать живой профиль
(`bot_profiles` alive, WA приоритетно) → `message/send` на собственный chat самого профиля.

- ⚠️ **Допущение, проверяемое ПЕРВОЙ задачей блока (probe-спайк):** Wappi умеет отправлять
  самому себе на обеих базах (api + tapi), и сообщение видно в «Сообщение себе»/Saved Messages.
  Если нет — блок останавливается, решение (алерт-бот приложения) возвращается владельцу.
- Алерт «канал отключился» физически не может ехать через умерший канал: при двух каналах едет
  через второй, при одном — виден только в приложении (принято владельцем вместе с вариантом
  доставки; статус канала приложение и так показывает при открытии).
- Гейт по подписке: доставка только аккаунтам `active/trialing/grace` (у истёкших и профилей-то
  скоро не будет — свип жизненного цикла).

## 3. Alert Sweep (n8n, Schedule Trigger каждые 10 минут)

Один воркфлоу, три обязанности за прогон:

1. **Классификация изменившихся диалогов** — переиспользует механику Dashboard Outcomes
   (Find Changed Sessions → Classify → Upsert) по профилям аккаунтов `active/trialing/grace`.
   LLM зовётся только для изменившихся сессий — дёшево. Побочный эффект: Сводка в приложении
   всегда свежая (классификация больше не только по запросу приложения).
2. **Алерты по исходам** — сравнение нового статуса с УЖЕ СОХРАНЁННЫМ в `conversation_outcomes`
   ДО upsert'а; алерт только на переходе в `order_collected` («клиент готов купить») или
   `owner_needed` («нужен владелец»). Один раз на переход, повторов нет. Текст RU:
   заголовок + имя/номер клиента + резюме из классификации.
3. **Каналы** — один `profile/all/get` на базу, диф флага `authorized` против прошлого снимка
   (durable-таблица состояния, не staticData) → «канал отключился» на true→false и
   «канал снова в сети» на false→true.

**Настройки:** страница «Уведомления» получает 4 тумблера (готов купить / нужен владелец /
канал / недельный отчёт), по паттерну NotifPrefs; синк на сервер маленьким вебхуком по образцу
SetReplyMode (таблица преференций по `app_user_id`). Свип читает преференции перед отправкой.
По умолчанию всё включено.

## 4. Недельный отчёт

Schedule Trigger, понедельник 09:00 Asia/Almaty, за прошлую календарную неделю (Пн–Вс), тем же
delivery seam. Содержание: диалоги всего и по ботам; исходы (заказы N / нужен владелец N /
вопрос закрыт N); ночные ответы (22:00–08:00); использование квоты «X из Y» (+ резерв, если есть).
Аккаунты с нулём диалогов за неделю — пропускаются. Управляется своим тумблером из §3.

## 5. Сводка: период «Всё время» + экспорт CSV

- `DashboardPeriod` получает четвёртый сегмент «Всё время» (окно с эпохи); дельты «к прошлому
  окну» для него скрываются — прошлого окна не существует.
- Экспорт: кнопка в Сводке → CSV того, что сейчас отображено (текущий фильтр бота + период) →
  системный share sheet (NativeShare уже в проекте). Кодировка UTF-8 **с BOM** (кириллица в Excel
  открывается без танцев). Колонки: дата, бот, канал, клиент, статус, резюме. Генерация
  клиент-сайд из уже загруженных строк — сервер не трогаем.

## 6. Расписание работы бота

- **UI** (вкладка «Основное» настроек бота): тумблер «Расписание» + окно «с 09:00 до 21:00»
  + 7 чипов дней. Часовой пояс v1 — фиксированно Asia/Almaty (КЗ-продукт; per-аккаунт TZ — потом).
- **Хранение:** PlayerPrefs per bot + синк на сервер (таблица расписаний по profile_id, вебхук
  по образцу SetReplyMode — расписание обязано работать, когда приложение закрыто).
- **Enforcement:** гейт времени в обоих бот-шаблонах РЯДОМ с `Suppressed?`, ДО `Count Dialog`:
  вне окна бот не авто-отвечает (поведение «Вместе», подсказки работают), **квота не тратится**.
  Окно через полночь (22:00–06:00) — валидный кейс, поддерживается. Это правка горячего пути
  обоих шаблонов — со всей дисциплиной Блока 1 (канонические JSONы, байт-идентичность WA==TG,
  парити-гейт, живой pinned-прогон на TG).

## 7. Голосовые в панели «Вместе»

`Suggest_Replies`: если в хвосте диалога есть голосовые (`[голосовое сообщение]`), сервер скачивает
и транскрибирует их той же цепочкой, что уже живёт в Авто-пути (Download Audio → Transcribe Audio),
и подставляет текст в контекст генерации подсказок. **Кэш транскриптов по message_id** (таблица) —
повторные раунды/рефреши/дриллы панели не платят за транскрипцию повторно. v1: транскрипт только
улучшает подсказки; показ его текста в панели — не в этом блоке.

## 8. Технические хвосты Блока 1 (все — решения ревью, владельцем приняты в Блок 2)

1. **Identity-verify при запуске** (лечит зеркало после переустановки сразу, а не при следующем
   RC-событии — до месяца в проде): когда `CustomerInfo.originalAppUserId` ≠ текущему `appUserId`
   (признак склейки идентичностей), клиент зовёт новый вебхук с одним `appUserId`; сервер САМ спрашивает RevenueCat REST API (серверный ключ) об алиасах
   этого подписчика и запускает уже готовую консолидацию. Инвариант безопасности Блока 1
   сохраняется буквально: alias-данные приходят только от RevenueCat, никогда от клиента.
2. **Журнал идемпотентности RC-вебхука**: таблица по `event.id` (каждая реальная доставка его
   несёт), дубль — чистый no-op до любых записей. Закрывает неидемпотентность `topup_delta`
   при ретраях после закоммиченного upsert'а.
3. **Сверка профилей при запуске** (клиент): сохранённый profile_id отдаёт 404/unauthorized на
   Wappi → бот помечается «не подключён» вместо вранья «подключён». Закрывает принятую в v1
   ложь списка ботов после переноса/reap'а.
4. **Страница «Подписка», два display-пробела одним заходом:** строка резерва («из резерва
   осталось N») и честное состояние вместо «Пробный · 5 дн.» в состоянии противоречия
   (сервер-expired × локально-свежий триал).
5. **Топ-ап первым событием после переустановки** — узкий снапшот-фолбэк консолидации (перенос
   плана только когда получатель trialing с NULL-периодом и событие плана не несёт) + probe-кейс.

Не в блоке (прод-чеклист): request-auth для Suggest_Replies; «grace-триада» (решается, когда
что-то начнёт писать status='grace').

## 9. Порядок работ

0. **Спайк self-send** (probe, оба Wappi-base) — гейт всего блока.
1. Alert Sweep + тумблеры «Уведомлений» + синк преференций.
2. Недельный отчёт.
3. Расписание (UI + синк + гейт в шаблонах).
4. Голосовые в Suggest_Replies (+ кэш).
5. Сводка: «Всё время» + CSV-экспорт.
6. Теххвосты §8 (порядок внутри: 2 → 1 → 3 → 4 → 5; журнал идемпотентности раньше
   identity-verify, т.к. verify добавляет новый путь записи, который обязан быть идемпотентным).

После 0–5 каждая строка пейволла «Во всех тарифах» работает → правило запуска Блока 1 выполнено.

## 10. Экономика блока

Новые постоянные расходы: классификация изменившихся сессий каждые 10 мин (gpt-4o-mini, только
дельта — копейки при текущем масштабе); транскрипция голосовых в панели (whisper, кэшируется);
RC API-вызов только при смене идентичности. Всё в пределах маржи Блока 1; отдельного пересмотра
цен не требует.

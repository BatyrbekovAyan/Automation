# Защита платящих + расписание бота — дизайн

**Дата:** 2026-10-14 · **Статус:** утверждено владельцем (обсуждение 2026-10-14), готово к планированию
**Заменяет:** Блок 2 «обещания витрины» (`2026-08-27-monetization-block2-storefront-promises-design.md`).
Его причина исчезла 2026-09-01: коммитом `3752d237` из пейволла вырезаны четыре несделанных
обещания (Сводка «за всё время» + экспорт, алерты, недельный отчёт, расписание); лендинг и описания
в сторах их не обещают. Отсюда — ревизия 2026-10-14 (шесть read-only аудитов плана против кода).

## 1. Решения владельца (2026-10-14)

- Блок 2 как «обещания витрины» не делается. Делается этот блок из двух частей: **A — защита
  платящих** (приоритет), **B — расписание бота** (по желанию владельца, после A). ✓
- Свип классификатора «готов купить» — снят: хэндофф-уведомления (`Create Handoff` → Notifier)
  закрывают «новый заказ / нужен владелец» событийно, за ~2 мин, с ретраями. ✓
- В бэклог с триггером «по запросу / по данным»: недельный отчёт, Сводка «за всё время» + CSV,
  тумблеры алертов, голосовые в панели «Вместе» (решить по данным device-pass обучения A/B),
  уведомление «канал снова в сети», инверсия расписания («бот только вне часов»).
- Правило A5 остаётся: уведомления владельцу не несут текст и номер клиента. ✓
- Тайм-зона расписания — зона бота (`{bot}TimeZone`, IANA, хранится с создания), запасная —
  `Asia/Almaty`; приоритет расписания выше явного «Авто» в отдельном чате (как пауза хэндоффа). ✓
- `bot_profiles.app_user_id` следует за биллинг-ID владеющей установки (перепривязка при
  консолидации и при claim) — иначе консолидация после переустановки гасит старый ID, а
  заново «заклеймленные» боты остаются привязаны к нему и замолкают. ✓

## 2. Почему это нужно (сегодняшние причины, не витрина)

1. **Переустановка платящего.** Новая установка = новый анонимный RevenueCat-ID; сервер сеет его
   как `trial/trialing`; зеркало подписки живёт под старым ID до следующего события RevenueCat
   (месячное продление — до месяца). Пока оно не пришло: триальные лимиты каналов и диалогов, а
   свип жизненного цикла через 4д17ч **удаляет профили ботов, созданных после переустановки**.
2. **Разлогин WhatsApp у платящего.** Часовой свип сирот удаляет любой профиль, не авторизованный
   ≥24ч, не глядя в `bot_profiles`; строка остаётся живой (liveness-ветка исключает `active`),
   токен её продолжает перечислять, карточка показывает «подключён» — бот молчит, владелец не
   знает. Перепривязка телефона — обычное событие.
3. **Повтор доставки RC-вебхука** после закоммиченного upsert'а дважды начисляет топ-ап.
4. **Топ-ап первым событием после переустановки** переносит баланс, но план остаётся триальным.
5. Дефекты уже живущих функций: Telegram-уведомление хэндоффа берёт верхний `phone` вместо
   `account.phone` (правило V2); «Подписка» показывает «Пробный · 5 дн.», когда сервер знает
   «истекла» (локальные часы триала стёрты переустановкой).

## 3. Часть A — защита платящих

### A1. Журнал идемпотентности RC-вебхука
Таблица `rc_event_ledger(event_id text primary key, received_at timestamptz not null default now())`
(имя `rc_events` занято GTM-журналом `docs/gtm/2026-09-22-acquisition-agent-decision.md`). Узел
`Dedup Gate` между Webhook и Map Event **только читает**; найден → ack 200 no-op; не найден → обычная
цепочка, а запись в журнал — CTE **внутри** `Upsert Subscriber` (одна транзакция с эффектом события;
запись раньше upsert'а при сбое между ними превратила бы ретрай в «дубль» и потеряла событие).
Нет `event.id` → проход без записи. Ветки без Upsert журнал не пишут. Технически: Postgres-узел
роняет входной json → Map Event читает `$('Webhook').first().json.body`; id события проводится через
Consolidate (`$('Map Event')`). RC Events генератора не имеет — ручная правка JSON допустима,
пины: `verify-telegram-parity.py`, `verify-sql-comments.py`, `tests/test_sql_comment_injection.py`,
новые тесты на temp-таблицах, e2e-auth `rc_purchase` (список узлов + Dedup Gate).

### A2. Перенос плана при топ-апе первым событием
В `Consolidate Aliases`: когда событие не несёт плана (NON_RENEWING_PURCHASE), а получатель —
`trialing` с `current_period_end is null` **или строки получателя ещё нет**, перенести
plan/status/current_period_end/product_id из **активной** alias-строки (выбор как `src` в
Transfer — по позднейшему периоду), в том же единственном upsert'е `credited` (одну строку нельзя
менять из двух CTE). Ничего не даунгрейдит: только trialing-без-периода получатель. Тесты A4.

### A3. Лечение зеркала после переустановки (identity-verify)
- **Триггер (клиент):** `CustomerInfo.OriginalAppUserId ≠ BillingService.AppUserId` (признак
  склейки; через `IBillingBackend`), при каждом обновлении CustomerInfo, один вызов на пару
  (original, current) за запуск; **не вызывать при `BillingConflict`**. Вызов —
  `AuthorizedRequest.Send` на новый вебхук; original id — только подсказка, никогда данные.
- **Сервер:** новый генерируемый `crVerifyIdent001` (Auth Gate `legacy:false`, `appUser` +
  `appUserRequired`); консолидация **только в `u` токена**. Алиасы подтверждает RevenueCat, не
  клиент: серверный запрос `GET https://api.revenuecat.com/v1/subscribers/{id}` (credential
  Header-Auth «RevenueCat API»; секретный ключ создаёт владелец в дашборде RC и кладёт в
  `Tools/n8n/.secrets/revenuecat-api.json`, в чат не передаётся) для `u` и для подсказанного
  original: один и тот же подписчик (`original_app_user_id` совпадает) → консолидировать
  original → `u` готовым примитивом (статья SQL `Consolidate Aliases` выносится в общий модуль
  `Tools/n8n/billing_consolidation.py`; RC Events и новый builder берут текст оттуда; верификатор
  пинит байт-равенство). Иначе — `success:false`, никаких записей. Первым шагом задачи —
  факт-чек RC API живым вызовом на подписчике владельца: форма ответа И отсутствие побочного
  эффекта (v1 `GET /subscribers/{id}` документирован как get-or-create — если он создаёт подписчика
  по произвольному id, использовать read-only эндпоинт v2 `customers` или проверять только `u`).
- **Перепривязка `bot_profiles.app_user_id`** (решение §1): консолидация перепривязывает к `u`
  строки с `app_user_id ∈ alias` и `owner_id` = установка токена; `claim.verify` при `u ≠ null`
  ставит `app_user_id = u` заклеймленной строке. `billing_bindings` не трогается; инварианты A1
  («назвать ID ничего не даёт», «ID — биллинг-ключ, не доказательство») соблюдаются буквально.
- Порядок внутри части A: A1 → A2 → A3 (A3 переиспользует примитив и журнал).

### A4. Защита живых профилей и уведомление «канал отключился»
- **Свип сирот** (`2islisFH7jjLoPQM`) не удаляет профиль, у которого есть **живая строка**
  `bot_profiles` (любой статус подписки): Postgres-чтение живых id в `Plan Sweep`, исключение.
- **Наблюдатель каналов** — новый генерируемый `crChannelWatch001` (Schedule Trigger каждые 10 мин):
  `profile/all/get` на обеих базах через `auth.http_wappi`; правило неоднозначности флага
  `authorized` из свипа сирот, floor пустого списка и пропорциональный cap из liveness-ветки;
  snapshot-таблица `channel_snapshot(profile_id pk, channel, authorized, seen_at)` без
  `app_user_id` (владение читается join'ом к живым строкам, строки ретированных профилей
  чистятся). Переход true→false → **одно** self-уведомление по рецепту Notifier (`Owner Phone` +
  `Send Notice`, attempts/backoff) через **другой живой канал того же владельца** (по
  `owner_id`); нет другого канала — только отметка в приложении. Текст по A5:
  «Choose Reply: WhatsApp отключился — бот не отвечает. Переподключите канал в приложении.»
  Повтор — только после возврата в true. Уведомление о возврате — бэклог.
- **Клиент:** при запуске и возврате в приложение — для перечисленных токеном профилей op
  `status` через `WappiProxy.Send`; положительный ответ `authorized:false` → неразрушающая
  отметка канала «Канал отключён» (маркер `{bot}{Ch}Unauthorized`, подлайн по образцу
  `ProfileRetirementCopy`), снимается при `authorized:true` или переавторизации; ничего не
  удаляется (существующая проверка при открытии настроек остаётся путём переподключения).

### A5. Telegram-номер уведомлений хэндоффа
`Compose Notice` в `build-handoff-workflows.py`: для tapi — `status.account.phone`, затем верхний
`phone` (правило V2 из `Claim Decide`); пин в `tests/test_handoff_notifier.py` и e2e-handoff
(мок уже знает `account_phone`); одно наблюдение на проде на TG-боте с согласия владельца.

### A6. «Подписка»: честное состояние
`SubscriptionPageRows.State(purchased, trialStarted, trialDaysLeft, serverSaysExpired)` зеркалит
`EntitlementPolicy.EffectiveTier`: противоречие «сервер-истекла × локально свежий триал» → «Истекла»;
строка резерва видна и при `None`-тарифе с балансом > 0, с формулировкой «заморожен до возобновления
подписки». Сем регистрируется в `FontGlyphCoverageTests`.

## 4. Часть B — расписание бота

**Семантика:** по умолчанию выключено. Внутри окна бот работает как обычно; **вне окна — ровно
поведение «Вместе»**: автоответа нет, подсказки работают, история и память пишутся
(`Record Suppressed`), квота не тратится, событие не клеймится. Решение принимается на входе
сообщения; `Acquire Send Lease` расписание не читает (закрытие окна посреди генерации не отменяет
уже оплаченный ответ). Всплеск, пересекающий закрытие, остаётся без ответа (новое заглушённое
сообщение вытесняет старое). Утром `Latest+Combine` складывает ночные тексты в первый ввод, а в
памяти они уже есть — модель видит их дважды, как сегодня при «Вместе»→«Авто»; принято.
Окно через полночь валидно (день определяется моментом **начала** суток в зоне бота).

### B1. Сервер
- Таблица `bot_schedule(profile_id text primary key, enabled boolean not null, days_mask int not null
  check (days_mask between 0 and 127), start_min int not null check (between 0 and 1439), end_min
  int not null check (between 0 and 1439), tz text not null default 'Asia/Almaty' (проверка по
  `pg_timezone_names` при записи), version bigint not null default 0, updated_at timestamptz)`,
  RLS deny-all + revoke. Бит 0 = Пн … бит 6 = Вс. `start == end` → 24ч; `start < end` → [start,end);
  `start > end` → [start,1440) ∪ [0,end) (через полночь).
- **Гейт = условие в `Read Reply Mode`** (`READ_MODE_SQL`, владелец — `apply-history-handoff.py`):
  к существующему OR добавляется `coalesce((select not <окно открыто at now() at time zone s.tz>
  from bot_schedule s where s.profile_id = $1 and s.enabled), false)`. Нет строки / `enabled=false`
  → false (LOCKED «отсутствие ⇒ ответ» не меняется). Предикат окна живёт в общем модуле
  `Tools/n8n/bot_schedule.py` с плейсхолдером времени (канон подставляет `now()`, тесты —
  фиксированные метки; та же таблица кейсов питает C#-близнецов). Узел **намеренно fail-closed**
  (как весь конвейер с этапа 3): миграция строго первой, `onError` не добавлять.
- Новый генерируемый вебхук `crSetSchedule001`: Auth Gate `{profiles:['profileIds'], legacy:false}`,
  Validate как у SetReplyMode (≤10 id, «-1» отбрасывается, диапазоны, tz), **один** version-guarded
  upsert по `jsonb_array_elements_text($1::jsonb)` с per-profile отчётом `applied`; тело
  `{profileIds, enabled, daysMask, startMin, endMin, timeZone, version}`; id — в `PROTECTED_IDS`
  (перегенерация и выкладка четырёх зависимых) и в `ACTIVE_CANONICAL`.
- `bot_schedule` входит в линию бота (`clone_lineage.MOVED_TABLES`: переподключение = новый
  profile_id, расписание переезжает) и в хвост удаления `Delete Bot Files` (счётчик в ответе).
- Метка исхода `off_hours` (Outcome) — чтобы в Сводке было видно «вне графика».

### B2. Клиент
- Вкладка «Основное»: секция «Расписание работы» — `ToggleRow` + два поля «с / до» (HH:MM, клоны
  `BotNameField` аддитивным билдером — наследуют инварианты клавиатуры, keypad Default) + 7 чипов
  Пн–Вс; `FormKeyboardScroll` на вкладку General (сейчас только у Бизнеса).
- Pure seam `ScheduleModel` (маска, валидация, формат, `IsInsideWindow` — тот же контракт и та же
  таблица кейсов, что сервер). PlayerPrefs `{bot}Schedule{Enabled|DaysMask|StartMin|EndMin}`;
  снапшот/dirty/save через `BotSettingsDirtyPolicy`; `DeleteBotLocally` чистит ключи (и заодно
  утечку `{bot}TimeZone`).
- Синк — по паттерну `ReplyModeSyncService` (желание → подтверждение `applied` по версии,
  персистентная очередь), `timeZone` = `{bot}TimeZone` (IANA) или `Asia/Almaty`.
- Вне часов панель подсказок должна быть доступна и у «Авто»-бота: `EffectiveSemiAuto` учитывает
  расписание (та же зона, тот же предикат) — иначе «молчание без панели».

## 5. Процесс (действует для всего блока)

Dev-n8n не используется (его Postgres-credential указывает на базу прода). Разработка — staging
(`Tools/n8n/staging/`: `pg.sh start|migrate`, `wappi-mock.py`, `bootstrap.py`, `e2e-*.py`);
узлы — только через владеющий генератор с `--check` (ручная правка — лишь у воркфлоу без владельца:
RC Events, свип сирот); тесты — `Tools/n8n/tests/` на реальном SQL (temp-таблицы) + `verify-*.py`
с негативными мутациями; новые воркфлоу — `build-<x>.py` с фиксированным `cr…`-id, импорт на прод
`n8n import:workflow` + publish; миграции — `pg.sh` (staging) и `.secrets/sql-oneoff.py` (прод);
выкладка — пакетом «Пакет выкладки» (снимки до/после, точки отката, порядок: миграции → воркфлоу
→ `update-clones.py` → `verify-deployed` 0) **только по явному «да» владельца**; клиентская сборка —
последней. Unity: Editor закрыт → `Tools/run-tests-headless.sh`; аддитивные билдеры, сцена
коммитится сразу; `AuthWiringGuardTests`, `FontGlyphCoverageTests`, RU-only. Коммиты — точечными
путями, трейлер `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`; мусор других сессий
(`.agents/`, `.codex/`, `AGENTS.md`, `output/`, `d.html`, `z.html`, правки `docs/audits/*`) не
стейджится.

## 6. Порядок и критерий готовности

A1 → A2 → A3 → A4 → A5 → A6 → пакет выкладки A (сервер) → B1 → B2 → пакет выкладки B →
device pass обеих частей на новой клиентской сборке. Готово = реинсталл платящего не ломает
лимиты/квоту/свип; разлогин канала виден владельцу и не уничтожает профиль; повтор вебхука не
начисляет дважды; расписание глушит бота ровно как «Вместе» в зоне бота.

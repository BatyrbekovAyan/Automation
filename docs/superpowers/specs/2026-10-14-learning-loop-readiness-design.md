# Подпроект B «Теневой счёт и замок «Авто»» — дизайн (2026-10-14)

Программа «Вместе учит → Авто продолжает»: A «Фундамент» (сырьё: что панель показала и что владелец отправил — выложено на прод 2026-10-14) → **B** (этот документ) → C (ответ «Авто» как рекомендованная карточка, тишина на спам, профиль стиля) → D (обезличенные агрегаты по вертикали). Анализ: `2026-09-25-learning-loop-vision-analysis.md`; спека A: `2026-09-25-learning-loop-foundation-design.md` (§0 — решения владельца, §8 — что передано в B).

## 0. Решения владельца

| № | Решение | Выбор |
|---|---|---|
| 1 | Критерий «бот обучен» (из A §0) | карточка №1 панели совпала с реально отправленным ответом по последним 20 отправкам из приложения |
| 2 | Порог (из A §0) | **10 из 20**; стартовая калибровка, пересматривается по данным |
| 3 | Форма замка (из A §0) | **мягкий**: прогресс на капсуле + лист с объяснением + «Включить всё равно»; на триале жёсткого запрета нет никогда |
| 4 | Знаменатель (2026-10-14) | **только отправки, при которых панель показала набор** (`origin_set > 0`); отправка без набора о панели не говорит и в счёт не идёт |
| 5 | Область замка (2026-10-14) | **один счёт и один замок на бота**: отправки обоих каналов (WhatsApp + Telegram) складываются по `bot_key` |
| 6 | Подход (2026-10-14) | **A**: счёт считает сервер и отдаёт в ответе Get Usage; клиент запирает только по положительному вердикту сервера |

Допущения без отдельного вопроса (владелец может отменить): существующие боты не запираются (на проде живых ботов нет — каждый бот будет создан после B и начнёт с 0/20); группы (`@g.us`, отрицательные Telegram-id) и ответы с телефона в счёт не идут (A §0); «Включить всё равно» ничего не записывает — владелец просто оказывается в «Авто», замок на включённый режим не действует; защита от накрутки из A §8 сохраняется: кроме 10 совпадений нужны ≥10 отправок с набором в ≥3 личных чатах за ≥2 календарных дня.

## 1. Цель и границы

**Цель.** «Авто» предлагается включить тогда, когда панель «Вместе» уже доказала, что отвечает как владелец: по последним 20 отправкам с показанным набором карточка №1 совпала не меньше 10 раз. До этого капсула показывает прогресс («Учится · 7/20»), а попытка включить «Авто» открывает лист «Бот ещё учится» с кнопкой «Включить всё равно».

**В границах.** Серверный расчёт готовности по боту в ответе Get Usage; клиентский магазин и чистая политика вердикта; замок на всех четырёх точках включения «Авто»; лист «Бот ещё учится»; запертое состояние капсулы; таблица готовности в `report-learning.py`; тесты, стенд, деплой одного workflow.

**Вне границ.** Пересчёт `top1` по хранимым текстам в живом замке (остаётся инструментом калибровки отчёта); изменение самого «Авто» (C); замок на включённый режим; жёсткий запрет; новый вебхук; миграции (данные A уже на месте); правка Suggest Replies (стадия `learning|trained` панели живёт отдельно и сверяется с готовностью в C).

## 2. Сервер — счёт в Get Usage

**Где.** Workflow `jtbssfzXbOxwTK4k-Get_Usage.json`, узел `Read Usage` (один statement с CTE) и Code-узел `Shape Response`. Генератор `Tools/n8n/apply-learning-b.py` (идемпотентный, маркеры, `--check`) — по образцу `apply-learning-a.py`; владение узлами Get Usage переходит к нему (сегодня их пишет только канон).

**Параметры.** К `$1 = appUserId` добавляется `$2 = $('Auth Gate').first().json.crAuth.installId || ''` и `$3 = crAuth.mode`. Legacy-вызов (`mode ≠ 'session'`) или пустой `installId` → `readiness = []`.

**SQL (CTE `readiness`), по каждому `bot_key` установки:**
- строки `bot_profiles` с `owner_id = $2`, `bot_key is not null` — живые и вытесненные (`superseded_by`) одной линии; `bot_key` одинаков у обоих каналов бота;
- из `chat_history_events` этих профилей: `source = 'owner_app'`, `origin_set > 0` (набор показан), `chat_id not like '%@g.us'` и `chat_id not like '-%'` (группы WA/TG);
- окно: последние 20 таких строк бота по `created_at desc` (row_number по `bot_key`);
- `matches = count(*) filter (where origin_top1 = 1)`, `total = count(*)`, `chats = count(distinct chat_id)`, `days = count(distinct (created_at at time zone 'Asia/Almaty')::date)`;
- `ready = total >= 10 and matches >= 10 and chats >= 3 and days >= 2`.
Константы `WINDOW = 20`, `MIN_MATCHES = 10`, `MIN_TOTAL = 10`, `MIN_CHATS = 3`, `MIN_DAYS = 2` объявлены один раз в `apply-learning-b.py` и подставляются в SQL генератором; `report-learning.py` читает те же константы (импорт модуля), а не копирует числа.

**Ответ.** `Shape Response` добавляет `readiness: [{botKey, matches, total, chats, days, ready}]` (целые, `ready` булево; порядок — по `botKey`). Остальные поля без изменений; старый клиент поле игнорирует.

**Стоимость.** Один дополнительный проход по `chat_history_events` установки через индекс `(profile_id, chat_id, sent_at desc)` — на окне в сотни строк это миллисекунды; Get Usage не на горячем пути ботов. Если окажется заметно (прод ≈1,9 с на Postgres-узел — это константа узла, не запроса), добавить индекс `(profile_id, created_at desc) where source = 'owner_app' and origin_set > 0` отдельной миграцией.

**Стражи.** `verify-learning-b.py` (структура: параметры узла, константы в SQL, поле `readiness` в Shape Response, Auth Gate нетронут); `verify-sql-comments.py` (ни одного `$N` в комментариях); `tests/test_learning_b.py` на реальном SQL во временных таблицах стенда: граница окна (21-я строка не считается), группы исключены, два канала одного `bot_key` складываются, вытесненная строка линии считается, чужой install не виден, `bot_key is null` не попадает, legacy-режим → пусто, порог `days`/`chats`; e2e на стенде `readiness_in_get_usage` (отправки через прокси с метками → `ready`).

## 3. Клиент — замок

**Магазин.** `UsageSnapshot.readiness` (`List<AutoReadinessEntry>`, поле опционально — старый сервер → `null`); `AutoReadinessStore.Current(botKey)` читает из `UsageStore.Current`; событие — существующий `UsageStore.OnUsageChanged`.

**Политика (чистая, EditMode).** `AutoReadinessPolicy.Verdict(AutoReadinessEntry entry) → Open | Locked`: `Locked` ТОЛЬКО если запись есть и `ready == false`; `null` (нет снимка, нет записи, старый сервер, legacy) → `Open`. Замок — подсказка, не защита: он никогда не блокирует из-за сети или отсутствия данных. `AutoReadinessPolicy.Progress(entry) → (matches, window)` для подписей.

**Гейт — одно место на все четыре точки.** Новый `AutoLockGate.TryEnable(botKey, font, Action proceed)`: если `Verdict == Open` — `proceed()` сразу; если `Locked` — лист «Бот ещё учится», чьё «Включить всё равно» вызывает `proceed()` (то есть прежний confirm и затем `CommitMode(Auto)`), «Понятно» — закрывает. Через гейт идут: (1) капсула карточки бота (`Bot.cs` → сейчас `BotActivationConfirm.Show`), (2) шапка чатов и (3) строка переключателя ботов (`ReplyModeToggleBinder.RequestEnableAuto` — гейт внутри него, одной правкой), (4) пер-чатный `SemiAutoToggle` (включение «Авто» для одного чата — тот же лист, тело поясняет «в этом чате»). Отключение «Авто» и серверные реконсиляции (`ReconcileFromServer`) через гейт не идут. Source-guard `AutoLockWiringTests`: четыре точки вызывают `AutoLockGate.TryEnable`, и ни одно включение «Авто» не идёт мимо него (`CommitMode(.*Auto)` только внутри `proceed`).

**Лист «Бот ещё учится».** Lazy-оверлей на своём canvas (sortingOrder 3) по образцу `BotActivationConfirm`/`BillingGateSheet`, шрифты — из переданного TMP-шрифта, геометрия через `ConfirmCardFitter` (растёт под текст). Копия в `AutoReadinessCopy`: заголовок «Бот ещё учится»; тело «Авто откроется, когда панель угадает ваш ответ 10 раз из последних 20 — сейчас 7 из 20. Отвечайте через «Вместе»: каждая отправка учит бота.» (ревью 2026-10-14: «откроется» — снимается замок; «включится» читалось как автовключение, которого нет) (пер-чат: «…Включить авто-режим в этом чате можно и сейчас.»); кнопки «Понятно» и «Включить всё равно». Все строки регистрируются в `FontGlyphCoverageTests` (SF Pro: `·` и `/` в атласе есть).

**Капсула.** Третье состояние пилюли на карточке бота — `Learning`: текст «Учится · 7/20», ширина — `BotCardModel.PillWidth` по измеренной подписи (как у «Подключить»), заливка — как у выключенного «Авто». Приоритет: `Подключить` (канал отключён) > `Учится` (режим Semi и вердикт Locked) > `Авто` (всё остальное, включая Semi без замка). Матрица — в `BotCardModel.PillKind(...)`, пинится `BotCardModelTests`. `Bot.cs` подписывается на `UsageStore.OnUsageChanged` и перерисовывает пилюлю; обновление — при следующем Get Usage (старт приложения, открытие вкладки «Боты», страница «Подписка», переподключение канала; триггера «на фокус» нет — ревью 2026-10-14).

**Отчёт.** `report-learning.py` получает таблицу `readiness` (bot_key, matches/total, chats, days, ready) по тем же константам — калибровочный взгляд владельца на то, что видит замок.

## 4. Данные и крайние случаи

- Данные уже пишутся (A): `chat_history_events.origin_*`, `suggestion_sets`. Миграций нет.
- Перепривязка / смена номера: отправки предшественника переехали Bind'ом (A, T6) — счёт продолжается под новым профилем того же `bot_key`.
- Удаление бота: строки удалены по линии — бот исчезает из `readiness`, замок не актуален.
- Два канала: один счёт на `bot_key`; канал без Create (`bot_key is null`) отправок не имеет.
- Один и тот же `bot_key` на разных установках — разные боты (`owner_id` разный).
- Бот в «Авто» с нулём отправок с набором (старый бот или «Включить всё равно»): замок не действует, капсула показывает «Авто».
- Сеть/ошибка Get Usage: снимок не меняется, вердикт по последнему снимку; отсутствие снимка → Open.
- Накрутка (20 тапов в одном чате за минуту): `chats ≥ 3` и `days ≥ 2` не дадут `ready`; «Включить всё равно» остаётся — замок мягкий по решению владельца.

## 5. Тестирование

- EditMode: `AutoReadinessPolicyTests` (матрица: null/нет записи/ready false/ready true/старый сервер), `UsageStoreTests` (снимок с `readiness` и без — поле опционально, не ломает прежние поля), `BotCardModelTests` (матрица `PillKind` + измерение реальной капсулы `Bot.prefab`), `AutoLockWiringTests` (source-guard четырёх точек), `AutoReadinessCopyTests` + регистрация в `FontGlyphCoverageTests`, тесты листа по образцу `ReconnectBotsSheetTests`.
- n8n: `tests/test_learning_b.py` (реальный SQL, §2), `verify-learning-b.py`, `verify-sql-comments.py`, `verify-auth-gate.py` (Get Usage остаётся gated с прежним RULE), `tests/run_all.py`.
- Стенд: `staging/e2e-learning.py` +1 сценарий `readiness_in_get_usage`: 10 отправок с `origin_set>0, origin_top1=1` в 3 чатах за «2 дня» (второй день — `update created_at` фикстурой) → `ready=true`; 9 → `false`; группа не считается; legacy-токен → `[]`.
- Полный headless EditMode после клиентских задач.

## 6. Деплой и выпуск

Один workflow — Get Usage — через `deploy-canonical.py --only jtbssfzXbOxwTK4k` (dry-run → `--apply --yes`), репетиция на стенде с прод-ref как в A; миграций нет, `update-clones.py` не нужен. Клиент — та же новая сборка, что несёт A. Прод только по явному «go» владельца. Калибровка порога — по `report-learning.py --prod` после первых недель.

## 7. Что перейдёт в C/D

C: стадия панели `learning|trained` (сейчас по pickStats) заменяется вердиктом готовности; «Включить всё равно» как сигнал; экран «Что бот выучил»; тишина на спам; профиль стиля с «Не так». D: обезличенные агрегаты по вертикали (после политики, opt-in, юриста).

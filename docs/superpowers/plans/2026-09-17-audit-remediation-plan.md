# Audit Remediation (A1–A7, S1–S7, промпты, готовность) — план этапов и проверок

> **Для исполнителя:** этот план — карта, а не замена выполнения. Ход работ, доказательства и точка
> продолжения ведутся в `docs/audits/implementation-progress.md` (статусы planned / in_progress /
> locally_verified / staging_verified / deployed_verified / blocked). Основание:
> `docs/audits/2026-09-15-app-and-ai-audit.md`, `docs/audits/2026-09-16-recheck-evidence.json`,
> инструкция `docs/audits/2026-09-16-claude-code-remediation-prompt.md`.

**Цель:** закрыть подтверждённые дефекты аудита с доказательствами поведения (не только по коду):
защита доступа (A1), подтверждаемый режим (A2), однократная обработка/отправка (A3, A4, A7),
общая история и настоящая передача человеку (A5, A6), выровненные знания и подготовка подсказок
(S1, S3–S6), согласованные промпты и измеренное качество (S2, S7, раздел 3), готовность для владельца
и управляемое развёртывание. Существующие боты, их profileId/workflowId/промпты/файлы/режим/история и
биллинг сохраняются.

**Среды и правила доступа (зафиксировано в этапе 0):**
- PROD: `https://n8n.choosereply.com` (n8n 2.36.7, Docker на VPS `ssh choosereply`). ТОЛЬКО ЧТЕНИЕ через
  API (`Tools/n8n/.secrets/prod-api-key.txt`) до отдельного явного разрешения владельца на конкретный
  релиз. Никаких отправок реальным клиентам. Бэкап определений снят в `~/backups/choosereply-n8n/`
  (вне git, 0600/0700); ночной cron-бэкап `n8n_data` на VPS работает (03:15, 14 дней).
- STAGING (изолированный, локальный): n8n 2.27.4 (`~/.n8n`, localhost:5678) + локальный PostgreSQL
  (Homebrew `postgresql@16`, база `choosereply_staging`, миграции из `Tools/n8n/sql` + `supabase`) +
  **Wappi-мок** (`Tools/n8n/staging/wappi-mock.py`, 127.0.0.1) вместо `wappi.pro`: подменённая
  отправка — тестовое сообщение физически не может уйти реальному клиенту. RAG-ретривер остаётся на
  реальной Supabase только для ЧТЕНИЯ с несуществующими тестовыми bot-id (ничего не совпадает);
  Upload File в staging не гоняем. OpenAI — реальный ключ локального инстанса (копейки за прогон).
  Вывод staging-воркфлоу: `Tools/n8n/staging/derive-staging.py` → `Tools/n8n/workflows-staging/`
  (gitignored), импорт через `n8n import:workflow` при остановленном n8n.
- Unity: Editor закрыт → `Tools/run-tests-headless.sh` (полный прогон + фильтр); при открытом —
  `ClaudeTestBridge`. Гейт — `total`/`failed` из results.xml, не summary.
- Git: единый рабочий каталог, без worktree (правило проекта). Коммиты — на `main`, только файлы
  задачи по явным путям, после проверок; `git rev-parse HEAD` до и после каждого коммита (параллельные
  сессии). Push — только по отдельному разрешению.

## Этап 0 — baseline и доверие к проверкам
1. Зафиксировать HEAD/`git status`, версии n8n (prod 2.36.7 / staging 2.27.4), typeVersion узлов,
   миграции SQL, версии шаблонов (`versionId`/`activeVersionId`) и активные клоны (13 выкл., 15 вкл.).
2. Починить контракт устаревших verify-скриптов: batching — путь winner → Count Dialog → Quota
   Decision → If Quota Allows → Input type; parity — точный canonical host `n8n.choosereply.com` +
   запрет удалённого bagkz-хоста. Прогнать все 4 проверки целиком.
3. Smoke SuggestReplies: уникальная тестовая identity на staging-БД (fixture по scope запуска),
   probe «без identity → отказ» (envelope `generation_failed`, gateReason в execution-логе),
   уборка только по своему scope.
4. Репро-харнесс Code-узлов (`Tools/n8n/repro/`): повтор события; ручной ответ после входящего;
   более новое входящее; чужой чат; SetReplyMode 200+success:false; короткое уточнение в queryText;
   Description отсутствует в payload панели. Тесты требуют ПРАВИЛЬНОГО поведения и красны на старом коде.
5. Диагностические исходы без текста диалогов (filtered / suppressed / quota_denied /
   generation_failed / superseded / send_failed / send_unknown / sent) + correlationId + время этапов
   в шаблонах; baseline-метрики прод-выполнений сняты ДО изменений (`Tools/n8n/baseline-metrics.py`).
**Приёмка:** baseline понятен; 4 проверки зелёные без потери защиты; дефекты воспроизводятся;
staging-транспорт не может достучаться до реальных клиентов.

## Этап 1 — доступ и транспортный секрет (A1)
Карта endpoint → действие → объект → проверка прав (все Wappi-обращения клиента + все вебхуки);
серверная identity/сессия с простым стартом и безопасной привязкой профилей (без «доказательства»
присланным ID); владелец ↔ профили/workflows/документы/история/биллинг (RevenueCat alias/transfer);
Wappi-действия на сервере как разрешённые операции (не прокси произвольного URL); защита callback в рамках
реального механизма Wappi (проверить документацию); миграция старого клиента с конечной датой;
ротация распространённого Wappi-токена. Проверки: владелец A не читает/не меняет объекты B; неизвестная
сессия отвергается до платных действий; легитимные операции работают; реальный release-артефакт без секрета.

## Этап 2 — подтверждаемый режим (A2)
Желаемый vs подтверждённый режим; подтверждение по телу/области/версии (`200 + success:false` = ошибка;
частичная запись ≠ успех); очередь последнего состояния с ограниченными повторами и восстановлением;
серверные версии против переупорядоченных ответов; приоритет per-chat override и наследование сохраняются;
начальный режим/права профиля устанавливает СЕРВЕР до активации workflow (start- и edit-пути, re-auth).
Семантика отсутствующей записи меняется только миграцией, не одним UPDATE/coalesce.

## Этап 3 — дубли и устаревшие ответы (A3, A4, A7)
Атомарная регистрация события (owner/profile/chat/messageId) и состояние обработки; порядок в рамках
чата; проверка режима/поколения/вмешательства владельца перед отправкой; короткие транзакции; состояния
generated / send_pending / sent / send_failed / send_unknown; проверенная идемпотентность транспорта или
сверка; Mark Read/Typing не блокируют отправку; бюджет задержки; отменённая генерация не в истории.
Сценарии — на staging с Wappi-моком, WA и TG.

## Этап 4 — история и передача человеку (A5, A6)
Согласованная история с явными ролями/источниками (клиент / AI / владелец из приложения / телефон /
«Вместе»); структурированное состояние заявки; надёжный handoff (уникальный ключ, пауза авто в чате,
уведомление с гарантированной доставкой); сводка читает достоверный источник; уведомление владельца
(push — только с реальными ключами и device-тестом, иначе внешний блокер); удаление/изоляция.

## Этап 5 — знания и подготовка подсказок (S1, S3–S6)
Единый контракт знаний (Description каталога, контакты, версия); осмысленный бюджет вместо отрезания
конца; TMP-теги → текст модели; восстановление предмета короткого вопроса; общий deadline; область и
актуальность кэша; часовой пояс бизнеса и серверное время; различимые ошибки vs abstain.

## Этап 6 — промпты и измерение качества (раздел 3, S2, S7)
Явный приоритет правил; цена из ручного каталога; удаление безусловных обещаний; связь обещаний с
этапом 4; разные голоса Авто/Вместе; воздержание по смыслу; ≥60 версионируемых синтетических сценариев
(6 отраслей, RU/KZ/смешанные, негативные), детерминированные правила зелёные, LLM-сценарии ×3 с разбросом
и стоимостью, сравнение до/после.

## Этап 7 — готовность владельца и развёртывание
Безопасный тестовый диалог; статус готовности; последний исход + ожидающие передачи; управляемое
обновление клонов по id узлов (dry-run, идемпотентно, тест старого клона); релизный пакет (бэкап, версии,
миграции, порядок backend/client, canary, чтение опубликованной версии, откат без повторного открытия
доступа и без дублей). Production — только после отдельного разрешения; иначе итог = готовый пакет с
явно незакрытым deployment-статусом.

## Обязательный итог

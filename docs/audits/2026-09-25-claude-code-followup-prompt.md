## 2. Правила выполнения

1. Разрешены локальные исправления, изолированный staging, синтетические данные, тесты, документация, небольшие коммиты и подготовка релиза. Не останавливайся после плана или каждого этапа ради подтверждения обычного технического решения.
2. Сохрани чужие изменения. Работай изолированно по правилам репозитория. Не включай в эту работу новые функции learning loop, редизайн, смену модели, тарифов или общий рефакторинг.
3. Production читай для сверки. Мутационные испытания выполняй на изолированных БД/хранилище и с подменённой отправкой Wappi. Проверь, что загрузка тестового прайса тоже не пишет в рабочую Supabase. Не считай существующий staging автоматически полностью изолированным.
4. Обновляй источник истины: генераторы/миграционные скрипты, затем канонические JSON, затем проверяй отсутствие расхождений. Правка только JSON может исчезнуть при следующей генерации. Изменения общих путей проверяй для WhatsApp и Telegram.
5. Для каждого дефекта: воспроизводящий тест → подтверждённое падение → минимальное исправление причины → успешный тест → связанные регрессии. Тест проверяет поведение, а не только наличие строки или названия узла.
6. Не ослабляй проверки ради зелёного результата. Исторические доказательства ревью сохраняй; новые результаты записывай отдельно.
7. Новые API и механизмы auth, RevenueCat, Wappi, n8n проверяй по актуальной официальной документации и установленной версии. Не придумывай подпись webhook, idempotency key или доказательство владения, которых сервис не предоставляет.
8. Если нужен отсутствующий ключ, реальное устройство или необратимое продуктовое решение, опиши конкретный блокер и продолжай независимые пункты. Не объявляй зависимый пункт завершённым.
9. Производственное развёртывание требует явного разрешения на подготовленный пакет этой итерации. Старое разрешение на предыдущий пакет не считай новым. Сначала сделай пакет полностью проверяемым; разрешение на применение — последний шаг. Если в текущей сессии пакет уже явно разрешён, не спрашивай повторно.

## 4. Этап 1 — доступ, загрузка файлов, сохранность сессии

Порядок: **R1 → R2 → R3 → R11**.

Основные участки: `Tools/n8n/build-auth-workflows.py`, `Tools/n8n/auth/gate.js`, auth SQL, Auth Session/Wappi Proxy/Upload File/Get Usage, `Assets/Scripts/Auth/`.

### R1 — доказательство владения при восстановлении

Убери возможность передать профиль заявителю только потому, что `authorized_at` позже начала claim. Восстановление должно требовать проверяемого доказательства, связанного именно с заявителем. Сохрани законный сценарий восстановления владельца; не решай проблему полным отключением восстановления.

Обязательные проверки:

- A начинает claim на профиль B; B независимо переподключает канал; A остаётся без доступа.
- Законный владелец успешно восстанавливает профиль.
- Просроченное/повторное доказательство, две одновременные заявки и неверный код не меняют владельца.
- Неавторизованный вызов не меняет pending-claim или другую запись до отказа.

### R2 — доверенная привязка billing identity

Произвольный `appUserId` из bootstrap/refresh не должен становиться правом доступа после простого подписания сервером. Наличие такого subscriber в RevenueCat само по себе тоже не доказывает, что он принадлежит заявителю.

Определи и реализуй подтверждаемую сервером связь установки/владельца с billing-аккаунтом, включая разрешённое восстановление и alias/transfer. Не вводи обязательный новый вход через email и не лишай существующих пользователей подписок без необходимого продуктового решения и плана миграции.

Проверь с ЗАКРЫТОЙ legacy-совместимостью: установка с чужим ID не читает его GetUsage, не использует его лимиты и не получает его права; собственный trial/покупка/восстановление продолжают работать. Покупки проверяй только в разрешённой тестовой среде.

### R3 — multipart проходит через авторизацию целиком

Сохрани бинарный файл и необходимые метаданные на пути Upload File. Реально проверяй ownership идентификаторов из multipart, а не только JSON; наличие настройки `binaryFields` не является выполненной проверкой.

Сквозной тест: собственный небольшой прайс → авторизация → извлечение → данные доступны только своему боту. Чужие workflow/profile/file IDs должны отклоняться до записи. Отдельно проверь пустой/повреждённый файл и повтор запроса.

### R11 — временная ошибка сервера не сбрасывает установку

Раздели временный сбой БД и действительный отзыв установки. При сбое refresh сохрани installId/secret и данные ботов, верни временную ошибку и разреши безопасный повтор. Подтверди клиентским тестом, что временный сбой не вызывает `ClearInstall()`/bootstrap, а действительно отозванная установка обрабатывается корректно.

## 5. Этап 2 — режим, отправка и память

Порядок: **R4 → R5 → R8 → R6 → R7 → R9 → R10**.

Основные участки: `apply-reply-mode-v2.py`, `apply-reply-pipeline-v2.py`, `apply-history-handoff.py`, соответствующие SQL/workflows, `ReplyModeSyncQueue`, `ReplyModeSyncService`, Manager и элементы отображения режима.

### R4 — устаревшая команда не снимает новую паузу

Свяжи unpause/закрытие handoff с действительно применённым актуальным действием владельца. Проверь:

- версия 100 после версии 200 ничего не возобновляет;
- повтор той же уже выполненной команды после создания НОВОЙ заявки не закрывает эту заявку;
- новый явный выбор «Авто» корректно возобновляет нужный чат;
- bot-wide режим не снимает самостоятельную handoff-паузу чата.

### R5 — очередь восстанавливается без действий пользователя

Запускай восстановление и доставку pending-очереди при холодном старте, с корректным порядком загрузки auth и ботов. Отсутствие созданного сервиса не должно выглядеть как подтверждённый режим.

Проверь: выключить автоответ без сети → закрыть приложение → запустить с сетью → не нажимать ничего. Актуальная команда должна отправиться сама. Дополнительно проверь быстрые переключения, старые ответы/ошибки сети, перезапуск во время повтора и смену бота: старая попытка не должна погасить более новое желание.

### R8 — активация только после успешного seed

Ошибка сохранения исходного режима должна остановить активацию и дать понятный отказ. Проверь искусственный отказ БД, отсутствие строки после него, восстановление БД и безопасный повтор создания без второго workflow/профиля. Оба канала.

### R6 — согласованная актуальность сообщений

Согласуй выбор последнего сообщения с поколением/правом отправки. Запоздавшая первая доставка старого события не должна отменять единственный актуальный ответ.

Проверь A→B при доставке B→A, одинаковые timestamps, параллельные повторы, серии сообщений и два независимых чата. При разрешённом режиме/лимите ожидается один актуальный ответ; более старый не отправляется. Не обещай exactly-once через внешний транспорт без подтверждённой поддержки.

### R7 — память соответствует реально отправленным сообщениям

Привяжи черновики и очистку к конкретной генерации/событию либо перенеси запись подтверждённого ответа на момент доставки. Не удаляй все AI-строки после общего watermark чата.

Проверь: старый черновик → новый отправленный ответ → отмена старого. Новый ответ и ручные сообщения сохраняются. `send_failed` не остаётся в памяти как сказанное клиенту; `send_unknown` не выдаётся за подтверждённую реплику. Echo не создаёт дубли. Миграция существующей памяти не должна удалять реальную историю.

### R9 — восстановление после остановки во время отправки

Добавь ограниченное восстановление зависших `send_pending`, включая случай без повторной доставки webhook. Учитывай действующую блокировку/живое выполнение: восстановитель не должен вмешиваться в ещё выполняющийся send.

Проверь остановку до транспортного вызова, после принятия сообщения транспортом и до записи результата. Итог — подтверждённая отправка либо честное `send_unknown` с доступным владельцу состоянием. Истечение блокировки не является основанием повторно посылать сообщение.

### R10 — достоверная сверка доставки

Проверь scope профиля/чата и достаточную связь найденного сообщения с попыткой отправки. Одинаковый текст в чужом чате не подтверждает доставку. Недостаточные или неоднозначные данные оставляют `send_unknown`. Тесты для WA/TG, включая одинаковый текст в соседних попытках/ручном ответе.

После этапа повтори связанные e2e reply/handoff и убедись, что обычные отправки, пауза после заявки, ответ владельца и декоративные действия не сломаны.

## 6. Этап 3 — знания и честная оценка промптов

Порядок: **R12 → R13 → R14**.

### R12 — сохранять важные условия и нужную позицию

Исправь подготовку каталога под бюджет: релевантная вопросу позиция и её существенные условия должны иметь приоритет. Обрезка не должна молча убирать ограничения цены, комплекта или услуги. При недостатке данных ответ должен отражать неопределённость.

Тесты: условие «Деталь оплачивается отдельно» в конце длинного описания; запрошенная последняя позиция в каталоге минимум из 32 товаров; одинаковые названия с разными вариантами; сравнение доступных фактов для автоответа и подсказок. Простое увеличение лимита символов не закрывает причину дефекта.

### R13 — новый вопрос и направление сохраняются в поиске

Зарезервируй место последнему вопросу и выбранному направлению; сокращай старый контекст. В тесте с длинной историей новый SKU должен сохраниться в итоговых queryText/exactTokens, а старый не должен его вытеснить. Отдельно проверь короткое «а сколько?» и серию последних клиентских сообщений.

### R14 — сначала исправить оценщики, затем улучшать ответы

1. Добавь положительные и отрицательные тесты оценщиков: «Доставка по городу бесплатная» при платной доставке — FAIL; «наличие подтвердит менеджер» не разрешает конфликт цены; корректное отрицание «доставка не бесплатная» не должно ошибочно проваливаться.
2. Версионируй исправленный harness. Пересчитай сохранённые before/after одним и тем же оценщиком без новой генерации и без перезаписи исторических результатов.
3. Исправь реально неверные ответы: конфликт цен и неподтверждённые обещания, затем остальные подтверждённые остаточные провалы исходной инструкции. Для правил уместности панели сохраняй явно утверждённую продуктовую политику; спорное продуктовое поведение не «исправляй» сменой ожидаемого результата теста.
4. Повтори проблемные и критичные негативные сценарии минимум трижды на одинаковом наборе, сохраняя язык/отрасль/модель/параметры. Проверь и автоответ, и подсказки. Не меняй модель ради улучшения отчёта без необходимости и отдельного обоснования.
5. Сохрани ответы, факты-основания, результаты, версии, задержки и размер выборки. Успешный JSON и фраза «уточнит менеджер» не доказывают фактическую правильность. Просмотри критичные ответы вручную по источникам.

Захватывай bot/profile/workflow и номер запроса. Закрытие/переоткрытие листа и переключение на B не позволяют запоздавшему ответу A менять UI, историю, состояние ожидания или LastTestOk бота B. Проверь также два запроса одному боту и ответ после удаления/изменения цели.

### Проверяющие инструменты

- `verify-deployed.py`: сравнивай реальный граф и опубликованную версию клона; stamp — вспомогательная отметка, не доказательство. Свежий исправный клон без stamp не должен объявляться устаревшим только из-за этого. Архивные клоны показывай отдельно и не активируй.

- Отрицательные тесты проверки: поддельный правильный stamp при неверном графе, неактивный обязательный webhook, иной опубликованный граф, посторонняя правка Support Message, обход проверки лимита.
- `verify-telegram-parity.py`: учти `Retire Refused Profile`, сохрани проверку отказа и очистки при превышении лимита.
- Проверь идемпотентность генераторов и обновления клонов. При обновлении сохраняй profileId, workflowId, webhook, персональный промпт, файлы, режимы, историю и billing. Не пересоздавай ботов ради обновления шаблона.

5. Подготовь ограниченный canary на согласованном собственном тестовом канале. Не отправляй сообщения реальным клиентам. После разрешённой публикации прочитай обратно опубликованные workflows, миграции и привязки, затем проверь canary.
6. Отдельно доведи план выхода нового клиента, проверки AAB/IPA на секреты, ротации старого Wappi-токена и закрытия compat-окна. Не обрывай старые клиенты без согласованного перехода, но не называй A1 закрытым, пока старый доступ остаётся. Push/APNs/FCM не объявляй готовыми без необходимых ключей и проверки на устройстве.

## 9. Как закончить работу

Обнови исходный аудит, матрицу исправлений, журнал и release-package с датой и ссылками на новые доказательства. Сохрани историю прежних выводов и испытаний.

Итог должен содержать:

- таблицу R1–R16: что изменено, где, каким поведенческим тестом подтверждено;
- результаты до/после, версии среды и оценщиков, исправленные метрики качества;
- отдельный статус реализовано / проверено локально / проверено на staging / опубликовано / проверено на устройстве;
- миграции, обновление клонов, откат и оставшиеся конкретные внешние действия;
- список коммитов и точную версию готового пакета.

Не обещай «без ошибок» и не закрывай пункт только по структурному тесту. Если обязательный критерий не выполнен, назови его прямо. Выполняй исправления до завершения доступной работы; при лимите контекста оставь точку продолжения с выполненными шагами и следующим действием.

Начинай с этапа 0, затем последовательно выполняй остальные этапы. Не ограничивайся предложением плана.

Дата: 2026-10-09. HEAD `d08c345d`. Статус: **подтверждено на HEAD, не исправлено** (проектирование, код не менялся).
Источник: `docs/audits/2026-09-28-iteration/README.md` («Новые находки вне списка ревьюера», F2), проверка V12 в
`docs/audits/2026-09-28-iteration/verification-results.json` (`verify[V12].how_confirmed` «Путь повторного подключения: на HEAD

## 0. Коротко

**Сейчас.** После чистки (триал/подписка кончились) у бота на сервере: профиль Wappi удалён, строка `bot_profiles` помечена
удалённой (`owner_id` = установка, `workflow_id` = клон), клон выключен, данные (память, история, прайсы) лежат. Токен
установки строится только из живых строк, поэтому после оплаты все обращения клиента со старыми id получают 403. Клиент об
удалении не знает: карточка выглядит живой, переключатель канала в настройках идёт в ветку «существующий профиль» →
`status` → 403 → ничего. «Сменить номер» → QR/код → 403. «Сохранить» → «Не удалось сохранить». На каждом запуске —
бесконечный `claim.start` (M4). Путь «новый профиль» сервер бы пропустил (лимит каналов считается верно), но клиент в него
не попадает. А если бы попал — новый клон не видит прайс-листы (чанки помечены id старого клона), память и сводка остаются
под старым профилем, старый клон — сирота; у бота с двумя каналами Create ещё и падает на гейте (называет старый клон
второго канала). Единственный обход сегодня — удалить бота (V12 это разрешает) и создать заново, вбив всё руками.

**Решение (минимальное корректное).** Переподключение = существующий «свежий» путь настроек (новый профиль Wappi → пара →
Create), плюс:
1. клиент по сигналу M4 **переносит** id удалённого канала в «retired»-ключи (текущие → `-1`), а удаление по V12 читает
   и retired-id (бот уходит с телефона только после удаления и прежних данных) — так все существующие вызовы сами
   перестают слать мёртвые id;
2. Create WA/TG получает `PreviousProfileId`; сервер **в БД** доказывает, что это удалённая строка той же установки, того же
   канала и того же бота, **оживляет прежний клон** (PUT текущего шаблона + полей в тот же workflow id; при невозможности —
   новый клон и удаление прежнего) и **одним оператором переносит данные бота** на новый профиль (память, история, сводка,
   заявки, флаги; при смене id клона — чанки прайсов и реестр файлов); старая строка помечается `superseded_by`;
3. после оплаты — ожидание, пока сервер увидит тариф, и явный призыв «Подключить снова».

**Объём:** ≈ 30–38 ч сверх M4 (сервер 14–16 ч, клиент 13–18 ч, документы 1 ч) + device-pass. **Вопросы владельцу** — §6
(главные: переносить ли переписку/память; показывать ли лист «Подключите ботов снова» сразу после покупки; что делать при
тарифе меньше прежнего).

## 1. Что происходит сейчас (HEAD)

### 1.1 Состояние после чистки

Profile Lifecycle Sweep (`fXYpCXPKw92EzRz8`, каждые 6 ч), ветка trial/churn: `Candidates` → `HTTP Delete Profile` (Wappi
`profile/delete`) → `Mark Deleted` (`deleted_at`, `deleted_reason ∈ {trial_expiry, churn_grace}`) → `Demote Trialing`
(`subscribers.status = 'expired'`). Ветка V12 (`apply-sweep-clone-deactivate.py`): `Retired Clones` → `Deactivate Clone` →
`Stamp Clone Deactivated` (`clone_deactivated_id = workflow_id`). Итог (воспроизведено, §1.6):

| Что | Состояние |
|---|---|
| Профиль Wappi | удалён (связанное устройство в WhatsApp/Telegram владельца исчезло) |
| `bot_profiles` | строка остаётся: `owner_id` = установка, `workflow_id` = клон, `bot_key` = `Bot0`, `deleted_reason` = `trial_expiry` |
| Клон | выключен (V12), определение и промпт владельца лежат |

### 1.2 Что видит владелец после покупки

- **Карточка бота** — как живая: цветные иконки каналов (`BotCardModel.IconState` смотрит только на «id не `-1`»),
  капсула «Авто». Ничто не говорит, что бот выключен. Бот при этом клиентам не отвечает.
- **«+ бот»** на «Старте» (1 бот) — «Лимит ботов тарифа»: зомби-бот занимает слот (`BotsPage.TryStartNewBot` считает
  `childCount`).
- **Чаты** — застывший кеш: `chats.filter` через прокси → 403, `SyncAllChats` молча `yield break`.
- **«Авто»/«Вместе»** — «Режим не сохранён» (SetReplyMode → 403).
- **Настройки → переключатель канала** — мигает LoadingPanel, больше ничего (см. таблицу).
- **«Сменить номер»** — открывается экран авторизации, QR пять раз за 15 с получает 403 и показывает текст `profile_id.`
  (`OpenWhatsappQRPanel` выводит поле `detail` ответа прокси); «Получить код» мигает тем же `profile_id`
  (`GetWhatsappCode` → `FlashWhatsappCodeError(detail)`).
- **«Сохранить»** — «Не удалось сохранить». **Прайс-лист** — загрузка 403. **«Проверить бота»**, панель подсказок — 403.
- **Каждый запуск** — бесконечный `claim.start` по зомби-профилю (M4: ≈ 450–600 исполнений n8n и вызовов Wappi в час).

### 1.3 Вход за входом

| Действие владельца | Что вызывается (HEAD) | Где отказ | Что видно |
|---|---|---|---|
| Включает канал в настройках | `BotSettings.Auth.CheckWhatsappAuthorization`: id ≠ `-1` → ветка «существующий профиль» → прокси `status` | `Build Request`: профиля нет в `p` → **403** `forbidden profile_id` | ничего (обработаны только `Success`-ветки) |
| Открывает настройки | `CheckWhatsappUnauthorizationOutsideApp` → `status` | 403 | ничего; номер и переключатель — как были |
| «Сменить номер» | `UnauthorizeWhatsapp` (`profile.logout`) + `OpenWhatsappAuthFromSettings(старый id)` → `qr` / `auth.code` | `Build Request` → **403** (до `Profile Owner` не доходит) | экран QR с текстом `profile_id.`, кнопка кода мигает `profile_id` |
| «Сохранить» | `SaveWorkflows` → Edit WA/TG | Auth Gate: `forbidden:WhatsappWorkflowId` | «Не удалось сохранить» |

| Запуск приложения | `ProfileClaimFlow.RunAtBoot` → `claim.start` | **не отказ**: `Claim Decide` → `owned`, токен без профиля → снова (M4) | ничего; цикл без конца |
| Покупка | `PaywallController.StartPurchase` → `Close()` | — | пейволл закрывается; про ботов ни слова |

«Свежий» путь (`whatsappProfileId == "-1"` → `CanConnectChannel` → `profile.add` → пара → Create) для такого бота
**недостижим**: id в PlayerPrefs остаётся старым, его никто не сбрасывает.

### 1.4 Даже если бы клиент пошёл «свежим» путём

Проверено на настоящих узлах (§1.6, F2-6…F2-9):
- **Сервер пропускает**: `profile.add` (нужен только billing id) → `Bind Profile` (новая строка, владелец с рождения) →
  Create: `Count Channels` = 0 (удалённые строки не считаются, своя новая исключена — `apply-slot-count-fix.py`), лимит
  «Старта» 1 → проходит.
- **Бот с двумя каналами — 403**: Create WA шлёт `TelegramWorkflowId` = клон удалённого TG-канала, гейт:
  `forbidden:TelegramWorkflowId` (и наоборот).
- **Новый клон теряет бота**: чанки прайсов помечены `botWaId` = старый клон, поиск нового клона ищет по своему
  `$workflow.id` → 0 чанков (`Restamp RAG Chunks` покрывает только случай «второй канал был `-1`»); `uploaded_files` —
  под старым id; память, история, сводка — под старым `profile_id`; старый клон остаётся привязан к удалённой строке —
  сирота с промптом владельца. Приложение при этом продолжает показывать «Прайс-листы: 1 файл».
- **Гонка оплаты**: если Create приходит раньше вебхука RevenueCat (статус ещё `expired`) — отказ `channel_limit` **после**
  того, как владелец уже спарил телефон; профиль удаляется, строка — `channel_limit`. В пути из настроек
  (`CreateWhatsappWorkflowFromEdit`) клиент при этом **не** сбрасывает id (в отличие от `…FromStart`) — получается ещё
  один зомби (`channel_limit`). M4 считает эту причину практически недостижимой — она достижима этим путём.
- **Клиентский гейт**: `EntitlementGate.ConnectedChannelCount` считает каждый id ≠ `-1`, включая зомби: покупатель «Старта»
  с зомби WA+TG получает отказ `CanConnectChannel`, хотя сервер видит 0 занятых каналов.

### 1.5 Единственный обход на HEAD

Удалить бота (после V12 сервер разрешает: `Delete Ownership` принимает свою удалённую строку — F2-10) и создать нового
через мастер. Потери: настройки бота (каталог, промпт, контакты) живут только в PlayerPrefs и стираются с ботом; прайс-листы
удаляются на сервере (Delete Bot Files) — загрузить заново; история переписки и сводка — удалены. Владелец к тому же не
знает, что бот выключен.

## 2. Дизайн решения

### 2.1 Принципы

1. **Владение — только по БД**: удалённая строка-предшественник принадлежит установке по `bot_profiles.owner_id`, установка не
   отозвана, тот же канал, тот же бот (`bot_key`), новый профиль — живая строка той же установки. Никаких окон времени,
   никакого «этот номер спарили недавно» (урок V2), никакого доверия к токену в вопросах удалённых строк (урок V12/M5).
2. **Токен не меняется**: удалённые профили/клоны не становятся capability (V12 п. 4). `token.js`, `gate.js`, прокси, гейты
   прочих вебхуков — байт-в-байт.
3. **«Бот = его текущие id»**: после переподключения всё, что было у бота на сервере, достижимо (и удаляемо) по текущим id.
   Это держит в силе все существующие пути (V12-удаление, «Удалить все данные», сводка, заявки).
4. **Инварианты Create не трогаются**: сбой сохранения режима никогда не создаёт и не оживляет клон (R8-deletefail):
   новые узлы стоят только ниже `Get Sample Workflow`, чей единственный предшественник — `Seed Saved?`[0].
5. **Гейт — по положительному полю строки** (уроки R8, F3): после Postgres-узла с `alwaysOutputData` решение принимает If по
   `found === true` / `adopted === true`, никогда «узел продолжил».

### 2.2 Сервер

#### A. Сигнал «канал удалён» — из M4, без изменений

`claim.*` по удалённой строке → `410 profile_retired` (+ `retiredReason` только владельцу), Wappi не вызывается
(`M4-design.md` §2.1). Список удалённых профилей в ответе refresh F2 **не нужен** (M4 §2.3 отверг его для себя; для F2 он
избыточен: каждый удалённый профиль клиента при старте попадает в `NextUnowned` и получает 410 ровно один раз). Для покупки
посреди сеанса — повторный прогон проверки на клиенте (§2.3 E).

#### B. Create WA / Create TG — переподключение с предшественником

Новое необязательное поле формы `PreviousProfileId` (клиент кладёт туда `{bot}{Ch}RetiredProfileId`). Старые клиенты его
не шлют — поведение прежнее байт-в-байт.

Новый идемпотентный генератор `Tools/n8n/apply-reconnect-adopt.py` (`--check`, по образцу `apply-slot-count-fix.py`),
правит оба канона `XuvOp7TxOImOAmlj-CreateWhatsappWorkflow.json` и `Uz6HBBUpAiUqVysB-CreateTelegramWorkflow.json`:

```
… Seed Saved?[0] → Get Sample Workflow → Set Fields → Reconnect?                         (If, без PG)
      Reconnect?[false] → Create Workflow (POST, как сейчас; тело = $('Set Fields').first().json)
      Reconnect?[true]  → Reconnect Predecessor (PG, read-only) → Reuse Clone? (If found && reusable)
            Reuse Clone?[false] → Create Workflow
            Reuse Clone?[true]  → Pause Predecessor Clone (POST …/deactivate, neverError)
                                 → Update Predecessor Clone (PUT …/workflows/{id}, тело Set Fields, fullResponse+neverError)
                                 → Clone Updated? (200 && body.id === предшественник)
                                       [true]  → Unwrap Put (Set: id = body.id) → Get Created Workflow Id
                                       [false] → Create Workflow
  Get Created Workflow Id → Activate → Set Wappi Webhook → Types → Restamp RAG Chunks → Bind Workflow Id   (как сейчас)
  Bind Workflow Id → Adopt? (If: Reconnect Predecessor выполнен && found === true)
      Adopt?[true]  → Adopt Predecessor (PG, один оператор) → Remove Superseded Clone? (adopted && previous_workflow_id ≠ id)
                          [true] → Remove Superseded Clone (DELETE …/workflows/{prev}, neverError; 200/404 = нет) → Send New Workflows Id
                          [false] → Send New Workflows Id
      Adopt?[false] → Send New Workflows Id
  Send New Workflows Id: { id, adopted: bool, reusedClone: bool }
```

- **`Reconnect?`** — `crAuth.mode === 'session'`, `PreviousProfileId` — строка ≤ 128 по `ID`-регэкспу прокси, не `''`/`'-1'`, не
  равна новому профилю. Только переподключения платят за два новых PG-узла (≈ 1,9 с каждый на проде).
- HTTP-узлы `Pause/Update Predecessor Clone`, `Remove Superseded Clone` — та же база API и тот же `httpHeaderAuth`, что у
  `Get Sample Workflow`/`Activate Created Workflow` (генератор копирует их оттуда — новой учётки и привязки в
  `deploy-canonical.py` не нужно); id в URL — только из строки `Reconnect Predecessor`/`Adopt Predecessor`.
- **`Reconnect Predecessor`** (параметры по порядку: установка из `crAuth.installId`, канал-константа, `PreviousProfileId`,
  новый профиль, `BotKey`; SQL — Приложение A): строка найдена, только если она **удалена** по причине из
  `{trial_expiry, churn_grace, liveness, channel_limit}` (никогда `app_delete` — бот удаляется владельцем), принадлежит **этой**
  неотозванной установке, того же канала, того же `bot_key` (если оба заданы), ещё не замещена другим профилем
  (`superseded_by is null` или = новый — повтор идемпотентен), а новый профиль — **живая строка этой же установки и канала**.
  `reusable` — id клона проходит регэксп/длину, не из `PROTECTED_IDS` (`build-client-webhooks.py`), и к нему не привязана
  никакая третья строка.
- **Почему оживлять прежний клон, а не создавать новый.** Клон — детерминированная функция (шаблон, профиль, поля формы):
  `Set Fields` ставит путь вебхука = новый профиль и собирает промпт из полей, которые клиент шлёт из PlayerPrefs. PUT
  текущего шаблона в тот же id даёт ровно то, что дал бы новый Create (и сразу актуальный шаблон — то, что делал бы
  `update-clones.py`), но **id не меняется**: чанки прайсов (`botWaId/botTgId`), `uploaded_files`, `w` токена, id в телефоне,
  `botWaId` панели подсказок — всё остаётся верным без переписывания. V12 выключил клон, а не удалил, ровно ради
  обратимости. `Pause Predecessor Clone` перед PUT делает путь детерминированным: PUT в неактивный клон, публикация — общим
  `Activate Created Workflow` (на n8n 2.36 PUT в активный публикует сразу, а `activate` по уже активному — проверить на
  стенде, §3).
- **Запасной путь** (клон удалён вручную/заархивирован — n8n отказывает PUT, как с «13»/«15», или PUT вернул не 200): новый
  клон POST'ом, `Adopt Predecessor` переписывает чанки и реестр файлов со старого id на новый, затем прежний клон удаляется
  (`Remove Superseded Clone`; 404 = уже нет). Узлы удаления прежнего клона — общие с F1 (§2.5).
- **`Adopt Predecessor`** — один оператор (Приложение A), только при доказанном предшественнике (те же условия CTE `pred`):
  - память: `n8n_chat_histories.session_id` `<old>:<chat>` → `<new>:<chat>` (id строк сохраняются, поэтому порядок памяти и
    водяные знаки R7/V6 остаются верными);
  - `chat_history_events`, `conversation_outcomes` (+ `session_id`), `handoff_requests`, `reply_events`, `chat_reply_state`,
    `reply_mode_flags` (кроме `'*'`) — переносятся; строка, которой у нового профиля уже есть пара по уникальному ключу,
    удаляется (новая побеждает; `'*'` нового профиля засеян Create из текущего режима клиента и авторитетен);
  - если id клона сменился (запасной путь): `documents.metadata.botWaId|botTgId` и `uploaded_files.bot_wa_id|bot_tg_id`
    (только `owner_id` = установка) — со старого id на новый;
  - предшественник: `superseded_by` = новый профиль, `superseded_at`; `workflow_id` → `null`, **если клон переиспользован**
    (id переходит к новой строке — инвариант «workflow id привязан к одной строке», иначе `Delete Ownership` после переезда
    на другой телефон увидел бы `owned_elsewhere`); при запасном пути `workflow_id` остаётся до удаления клона (чистка и
    `Delete Ownership` продолжают его покрывать).
  - Набор таблиц — **ровно** набор `Delete Chat Memory` (Delete Bot Files). Это тестируемый инвариант: после переноса
    удаление по текущим id стирает всё (Приложение A, PASS). `dialog_counts` не трогаются (биллинг по `app_user_id`).
- Ответ: `adopted` (= оператор пометил предшественника), `reusedClone`. Если переподключение прошло, а перенос нет (сбой БД
  после привязки) — бот работает, `adopted:false`, клиент сохраняет маркер (§2.3 C).

#### C. Миграция

`Tools/n8n/sql/2026-10-xx-bot-profiles-superseded.sql`:
`alter table bot_profiles add column if not exists superseded_by text, add column if not exists superseded_at timestamptz;`
Индексы не нужны (поиск по PK `profile_id`; `bot_profiles_workflow_idx` уже есть).

#### D. Что НЕ меняется

`Count Channels` (уже верно: удалённые строки не считаются, своя новая исключена), `Retire Same Bot Slot`, `Register Profile`,
`Seed Reply Mode` и его гейт, Auth Gate/`gate.js`/токен, прокси (`profile.add` остаётся без проверки тарифа — см. §2.6),
Profile Lifecycle Sweep (замещённая строка с `workflow_id = null` в `Retired Clones` не попадает; переиспользованный клон
охраняет условие «живая строка ведёт этот workflow»), Delete Bot Files, Set Workflow State.

### 2.3 Клиент

#### A. Маркер M4 + перенос id (единственное расхождение с M4)

M4 записывает `{bot}{Ch}RetiredProfileId`/`{bot}{Ch}RetiredReason` и **не трогает** id канала, потому что сброс в `-1`
потерял бы id, по которым V12 удаляет данные (M4 §2.3, «Сбросить id канала в `-1`»). F2 предлагает **переносить**:
при любом `profile_retired` (сервер положительно сказал «строка удалена»; причина есть только у своей строки) —
`{bot}{Ch}WorkflowId` → `{bot}{Ch}RetiredWorkflowId`, текущие `{bot}{Ch}ProfileId`/`{bot}{Ch}WorkflowId` → `-1`,
`isOn{Ch}` → 0; поля `Bot` обновляются, карточка перерисовывается. Причина M4 снимается в том же изменении (п. D ниже:
удаление читает и retired-id). Для `app_delete` (незавершённое удаление V12) экраны предлагают только «Удалить ещё раз»,
не «Подключить» (сервер такого предшественника и не примет).

Почему перенос, а не точечные проверки «канал помечен»: id канала читают ~110 мест в 16 файлах (Manager, BotSettings.Auth,
Dashboard, подсказки, загрузки, чаты, Test Dialog, режим ответа). С переносом каждое из них **само** видит «канал не
подключён» — существующее состояние с готовыми экранами: чаты показывают пустое состояние, режим не шлётся, Edit/Upload/
Create шлют `-1` (снимает 403 из §1.4 для двухканального бота), `ConnectedChannelCount` больше не считает зомби (снимает
отказ клиентского гейта), `NextUnowned` его не видит (вторая половина M4). Альтернатива (аксессор «живой id» во всех
16 файлах) — §2.7.

Если M4 выйдет раньше F2 в своём виде — F2 добавляет перенос + п. D одним изменением; ключи общие.

#### B. Состояния на экранах

Чистый слой `RetiredChannelPolicy` (+ EditMode-тесты): канал «удалён» ⇔ текущий id `-1` и есть `{bot}{Ch}RetiredProfileId`.
- **Карточка** (`BotCardModel`): подстрока из M4 («Отключён · пробный период закончился» / «…подписка закончилась» /
  «Канал отключён»); если удалены **все** каналы бота — вместо капсулы «Авто» кнопка «Подключить» (вопрос 4, §6), тап — в
  настройки бота на строку канала.
- **Настройки → «Основное»**: строка канала выключена, под ней подсказка «Отключён · нажмите, чтобы подключить снова»
  (аддитивный идемпотентный билдер, как `BusinessContactFieldsBuilder`; деструктивный `Rebuild Bot Settings Prefabs` — нет).
  Включение = существующий «свежий» путь `CheckWhatsappAuthorization` (гейт → `profile.add` → пара → Create).
- **Чаты**: новый `EmptyStateReason.BotChannelRetired` («Бот отключён» / «Подключите канал снова в настройках бота») вместо
  общего «нет WhatsApp».

#### C. Переподключение

- `CreateWhatsappWorkflowFromEdit`/`…Telegram…`: поле `PreviousProfileId` = `{bot}{Ch}RetiredProfileId` (если есть). Успех:
  `adopted == true` → удалить retired-ключи канала; `adopted == false` → оставить (у канала тогда есть и текущий, и retired
  id — удаление бота делает по ним два вызова, §D; повтор переноса — следующим переподключением или поддержкой).
- **Отказ Create из настроек** (`channel_limit`, `reply_mode_not_saved`, нет `id`) — как в `…FromStart`: текущий id → `-1`,
  `isOn` → 0, retired-ключи **не трогать** (следующая попытка снова назовёт того же предшественника). Сегодня этот путь
  оставляет зомби (§1.4).
- Таймаут Create из настроек 30 → 60 с только при `PreviousProfileId` (переподключение добавляет 2 PG + 3 HTTP ≈ 5–6 с к
  ≈ 15 с нынешнего Create).
- Имя профиля Wappi — имя бота, как сейчас. Номер — любой (вопрос 6).

#### D. Удаление не должно регрессировать (V12)

- `BotServerDeletion.HasServerTrace` учитывает retired-id (иначе бот с одними retired-id получил бы `NothingOnServer` и ушёл
  с телефона, оставив данные, — ровно регрессия V12).
- `Manager.DeleteBotOnServer`: unlink Wappi — только для **текущих** профилей (удалённый уже удалён у Wappi; прокси по нему
  всё равно ответит 403 — `ClassifyProfileDelete` считает это Ok). Delete Bot Files — набор текущих id; если у какого-то
  канала есть и retired-id — второй вызов с набором retired-id (обычно канал имеет либо текущий, либо retired; оба — только
  при `adopted:false`). Клоны — текущие и `RetiredWorkflowId`. Вердикт — первый не-Ok по всем вызовам, как сейчас.
  `Delete Ownership` принимает свою удалённую строку (F2-10). «Удалить все данные» идёт через тот же путь.
- `Bot.DeleteBotLocally` удаляет новые ключи (`RetiredWorkflowId` вдобавок к ключам M4).

#### E. Покупка

- **Повторная проверка**: на `BillingService.OnEntitlementChanged` к платному тарифу — ещё один прогон
  `ProfileClaimFlow.RunAtBoot` (только непринятые id, по M4 — не больше одного `claim.start` на профиль) — находит каналы,
  которые чистка удалила после старта приложения.
- **Ожидание сервера** перед `profile.add` при переподключении: если последний снимок `GetUsage` говорит `expired` или
  `channels_connected ≥` лимита тарифа — перечитать по расписанию `TopUpSettlePolicy` (0/2/5/10/20 с) с текстом
  «Подтверждаем оплату…»; не дождались — «Оплата ещё не дошла до сервера. Попробуйте через минуту.» и **без** пары. Иначе
  гонка §1.4: пара, затем отказ `channel_limit` и удалённый профиль.
- **Призыв** (вопрос 3): после успешной покупки, если есть удалённые каналы, — лист «Подключите ботов снова» (ленивый
  оверлей по образцу `BillingGateSheet`, sortingOrder 3) со строками «бот · канал · Подключить».

### 2.4 Ответы на вопросы задачи

| Вопрос | Решение |
|---|---|
| Новый Wappi-профиль | Да: Wappi не переиспользует id, удалённый профиль не оживить. Тот же «свежий» путь: `profile.add` (прокси, `Bind Profile` — владелец с рождения) → пара → Create |
| Привязка к тому же боту и установке | `PreviousProfileId` из маркера; доказательство в SQL: `owner_id` = установка (неотозванная), тот же канал и `bot_key`, удалённая не владельцем причина, новый профиль — живая строка этой установки. Чужая/бесхозная/legacy/`app_delete`/другой бот → обычный Create без переноса (Приложение A, PASS) |
| Старый выключенный клон | **Оживить**: PUT текущего шаблона + полей в тот же id (как сделал бы Create + `update-clones`), затем `Activate`. Запасной путь — новый клон + перенос чанков/файлов + удаление прежнего (узлы общие с F1) |
| Данные бота | Переносятся одним оператором на новый профиль (набор = набор Delete Chat Memory); при смене id клона — чанки и `uploaded_files`. Настройки (промпт, каталог, контакты) и так в телефоне и уходят формой Create (вопрос 1 — переносить ли переписку) |
| `bot_profiles`: новая строка или оживление | **Новая** (PK = id Wappi). Старая остаётся историей: `deleted_reason`, `clone_deactivated_id`, + `superseded_by/at`; `workflow_id` → `null` при переиспользованном клоне |
| Биллинг, слоты | `Count Channels` уже верен: старая строка не считается, новая — один канал против лимита тарифа. Клиентский счёт исправляется переносом id. Гонка с вебхуком RevenueCat — ожидание по `GetUsage` до пары. Меньший тариф — владелец выбирает, что подключить (вопрос 5) |
| Безопасность | Только БД, только эта установка; никаких окон времени (V2); токен не расширяется (V12); `PreviousProfileId` — параметр запроса, сравнивается, не подставляется (V1: в комментариях SQL нет `$`+цифра, страж `verify-sql-comments.py`); id клона берётся из строки БД, не от клиента; PUT/DELETE — только по id из доказанной строки, не из `PROTECTED_IDS`; путь недостижим при сбое seed (R8) |

### 2.5 Стык с F1

F1 (повторная авторизация **того же** профиля создаёт новый клон и не убирает прежний; сбой после Create оставляет
непривязанный клон) и F2 — один механизм «предшественник клона»: Create знает workflow, который этот канал бота вёл до сих
пор, и **переиспользует** его PUT'ом; если нельзя — создаёт новый и убирает прежний после успешной привязки.
- F1-источник предшественника: `workflow_id` строки **этого же** профиля (живой).
- F2-источник: `workflow_id` доказанной **удалённой** строки `PreviousProfileId` (+ перенос данных между профилями).
- Общие узлы: `Pause Predecessor Clone`, `Update Predecessor Clone`, `Clone Updated?`, запасной `Create Workflow`,
  `Remove Superseded Clone`. Рекомендация — один генератор на оба случая, кто бы ни начал первым.
- **Смежная находка для F1** (по коду; механизм подтверждён F2-8): любая смена id клона теряет прайс-листы — «Сменить номер»
  (`UnauthorizeWhatsapp` удаляет клон, `DeleteWhatsappWorkflow` ставит `-1`, `…FromEdit` создаёт новый) и повторная пара
  после выхода вне приложения оставляют чанки под старым `botWaId/botTgId`; новый клон их не находит, приложение показывает
  файлы как загруженные. Переиспользование клона закрывает это без переписывания; если F1 выберет «новый + удалить старый»,
  ему нужен тот же перенос `documents`/`uploaded_files`, что в `Adopt Predecessor`.

### 2.6 Остатки и ограничения (документировать)

- **Бесхозная (legacy) или чужая удалённая строка** — не доказуема (V2: доказательство — только код в чате бота, а профиль
  удалён). Переподключение даёт «чистого» бота: настройки из телефона уходят формой, прайс-листы нужно загрузить заново;
  старые данные — по запросу в поддержку (V12 «Удалить только с телефона»).
- **Ложный liveness** (профиль у Wappi на самом деле жив): переподключение создаст второй профиль; первый остаётся
  связанным устройством (остаток V12 (ii)).
- **`profile.add` не проверяет тариф** (прокси): неоплаченная установка может создать профиль Wappi, отказ придёт в Create.
  Клиент закрывает это гейтом и ожиданием §2.3 E; серверная предпроверка в прокси — отдельный пункт.
- **Перенос не делается при сбое БД после привязки** (`adopted:false`): бот работает, прежние данные остаются под старым
  профилем и удаляются удалением бота (п. D); автоматического повтора переноса нет.
- **Переписка, начавшаяся до переноса** (секунды между `Activate` и `Adopt`): сообщение клиента успеет создать строки под
  новым профилем; перенос их не трогает, конфликтующие старые строки состояния чата удаляются (новая побеждает), память
  упорядочена по id — старые строки раньше.
- Старая сборка 1.0 (4) (до A1) — не затронута и не исправлена: ходит в Wappi напрямую мастер-токеном.

### 2.7 Отвергнутые варианты

- **Удалённые профили/клоны в токен (`p`/`w`)** — прокси и все гейты снова пустили бы к удалённым профилям; V12 п. 4.
- **Оживить старую строку `bot_profiles`** (`deleted_at = null`) — PK = id Wappi, а профиль удалён; пришлось бы переписывать PK.
- **Привязка по `bot_key` без явного `PreviousProfileId`** — `bot_key` выдаёт клиент («Bot0» у новой установки и у старой), и
  строки, созданные до появления `BotKey`, его не имеют; явный id + проверка `bot_key` как страховка точнее.
- **Не переносить данные, а удалять по «родословной»** (Delete Bot Files стирает и замещённые профили) — проще сервер, но бот
  «забывает» клиентов и сводку; при отказе владельца от переноса (вопрос 1) — это запасной вариант, а не «ничего не делать»:
  без него старые данные становятся неудаляемыми из приложения.
- **Аксессор «живой id канала» во всех 16 файлах вместо переноса id** — ~110 мест, каждое легко забыть (как V12 нашёл с
  токеном); перенос — одна точка + удаление.
- **Список удалённых профилей в ответе refresh** — не нужен при сигнале M4 и повторной проверке после покупки.

### 2.8 Порядок выкладки

1. Миграция `superseded_by/at` (идемпотентна).
2. Сервер M4 (Auth Session) — можно раньше всего (`M4-design.md` §5).
3. Create WA/TG (`deploy-canonical.py`, read-back, `verify-deployed.py`). Обратная совместимость: без `PreviousProfileId`
   граф идёт прежним путём (`Reconnect?`[false]); байт-в-байт проверяется верификатором.
4. Клиент: M4 + F2 одной A1-сборкой (перенос id без п. D выпускать нельзя — регрессия V12).
5. Device-pass: бот с истёкшим триалом (на стенде — строка удаляется SQL'ом как чисткой) → покупка в sandbox → «Подключить» →
   прайс-лист отвечает, история на месте, «Удалить бота» стирает всё.

## 6. Вопросы владельцу

1. **Переносить ли историю переписки, память бота и сводку на новое подключение?**
   - (а) **рекомендую:** да, всегда — бот «возвращается каким был», сводка не теряет прошлые диалоги, удаление бота стирает
     всё по текущим id;
   - (б) только если номер тот же (клиент сравнит прежний и новый номер), иначе старое удалить при переподключении;
   - (в) не переносить: бот начинает с чистой памятью, старое удаляется только вместе с ботом.
   Прайс-листы и клон переносятся в любом варианте (иначе бот «забывает» цены, а приложение показывает файлы).
2. **Что показывать до оплаты** (дополняет вопрос 1 M4). Рекомендую подстроку M4 на карточке и, в настройках бота, баннер:
   «Бот отключён» / «Пробный период закончился, и канал отключили. Настройки, каталог и прайс-листы сохранены — после оплаты
   подключите канал снова.» с кнопкой «Выбрать тариф» (пейволл). Для подписки: «Подписка закончилась, и канал отключили. …».
3. **Что происходит сразу после покупки?**
   - (а) **рекомендую:** лист «Подключите ботов снова» / «Тариф активен. Настройки и прайс-листы на месте — осталось заново
     подключить WhatsApp или Telegram.»; строки «{бот} · WhatsApp» с кнопкой «Подключить»; внизу «Позже»;
   - (б) только кнопки на карточках;
   - (в) сразу открывать подключение первого бота.
4. **Где кнопка «Подключить снова».** Рекомендую: на карточке бота, у которого отключены все каналы, — «Подключить» вместо
   капсулы «Авто» (капсуле нечего переключать); в настройках — сама строка канала с подсказкой «Отключён · нажмите, чтобы
   подключить снова». Пустое состояние чатов: «Бот отключён» / «Подключите канал снова в настройках бота».
5. **Тариф меньше прежнего** (в триале было 3 канала, куплен «Старт» на 1). Рекомендую: владелец сам выбирает, какой канал
   подключить; на остальных «Подключить» открывает существующий лист «Лимит каналов вашего тарифа». Альтернатива — сразу
   предлагать удалить лишних ботов (не рекомендую: удаление необратимо).
6. **Номер.** Рекомендую разрешить любой номер, показывая прежний подсказкой «Ранее: +7 …». Альтернатива — требовать тот же
   (Wappi не говорит номер до пары, поэтому проверка возможна только после неё и закончится удалением профиля).
7. **Срок хранения данных удалённых ботов** (второй вопрос V12, всё ещё открыт). Рекомендую хранить, пока владелец не удалит
   бота или не попросит поддержку — тогда переподключение возвращает всё в любой момент. Если выберете автоудаление через N
   дней — после N дней переподключение даст «чистого» бота (настройки из телефона, прайсы заново), и это стоит сказать в
   тексте баннера.
8. **Выпуск.** Рекомендую: сервер (миграция, M4, Create) — раньше клиента, он обратно совместим; клиент M4 + F2 — одной
   A1-сборкой до подачи в сторы (перенос id без нового удаления выпускать нельзя).

Все предложенные тексты — только из символов статических атласов SF Pro (« » · — … есть; → № − ✕ не использовались).

## Приложение A. Прототип серверных операторов

Файл `proto_f2.py` (scratchpad сессии, может быть стёрт; ниже — всё нужное для повтора). Запуск — при работающем
`Tools/n8n/staging/pg.sh`; temp-таблицы `like public.*`, к `bot_profiles` добавлены `superseded_by/at`. Рядом с прототипом
выполнялись настоящие узлы HEAD: `Delete Ownership` и `Delete Chat Memory` (Delete Bot Files), `Retired Clones` (чистка).

Параметры, по порядку: установка, канал, `PreviousProfileId`, новый профиль, итоговый id клона (только Adopt), `BotKey`.

```sql
-- общий CTE (Reconnect Predecessor и Adopt Predecessor)
pred as (
  select bp.profile_id, bp.workflow_id
  from bot_profiles bp
  join installs i on i.install_id = bp.owner_id and i.revoked_at is null
  where bp.profile_id = $3 and bp.owner_id = $1 and bp.channel = $2 and bp.profile_id <> $4
    and bp.deleted_at is not null
    and bp.deleted_reason in ('trial_expiry', 'churn_grace', 'liveness', 'channel_limit')
    and (bp.superseded_by is null or bp.superseded_by = $4)
    and (bp.bot_key is null or nullif($6, '') is null or bp.bot_key = $6)
    and exists (select 1 from bot_profiles nw where nw.profile_id = $4 and nw.owner_id = $1 and nw.channel = $2
                and nw.deleted_at is null)
)

-- Reconnect Predecessor (read-only)
with <pred>
select true as found, pred.profile_id, pred.workflow_id,
  (pred.workflow_id ~ '^[A-Za-z0-9]+$' and length(pred.workflow_id) between 8 and 36
   and pred.workflow_id not in (<PROTECTED_IDS>)
   and not exists (select 1 from bot_profiles o where o.workflow_id = pred.workflow_id
                   and o.profile_id not in (pred.profile_id, $4))) as reusable
from pred;

-- Adopt Predecessor (один оператор; *_mv переносит, *_dup удаляет старую строку, у которой у нового профиля есть пара)
with <pred>, p as (select profile_id as old, workflow_id as old_wf from pred
), mem as (
  update n8n_chat_histories h set session_id = $4 || substr(h.session_id, length(p.old) + 1)
  from p where split_part(h.session_id, ':', 1) = p.old returning 1
), hist_mv as (
  update chat_history_events e set profile_id = $4 from p
  where e.profile_id = p.old and not exists (select 1 from chat_history_events x
        where x.profile_id = $4 and x.chat_id = e.chat_id and x.message_id = e.message_id) returning 1
), hist_dup as (
  delete from chat_history_events e using p
  where e.profile_id = p.old and exists (select 1 from chat_history_events x
        where x.profile_id = $4 and x.chat_id = e.chat_id and x.message_id = e.message_id) returning 1
), outc_mv as (
  update conversation_outcomes o set profile_id = $4, session_id = $4 || ':' || o.chat_id from p
  where o.profile_id = p.old and not exists (select 1 from conversation_outcomes x where x.session_id = $4 || ':' || o.chat_id) returning 1
), outc_dup as (
  delete from conversation_outcomes o using p
  where o.profile_id = p.old and exists (select 1 from conversation_outcomes x where x.session_id = $4 || ':' || o.chat_id) returning 1
), hand_mv as (… handoff_requests по (chat_id, source_message_id), та же пара mv/dup …
), ev_mv as (… reply_events по (chat_id, message_id) …
), st_mv as (… chat_reply_state по chat_id …
), fl_mv as (
  update reply_mode_flags f set profile_id = $4 from p
  where f.profile_id = p.old and f.chat_id <> '*'
    and not exists (select 1 from reply_mode_flags x where x.profile_id = $4 and x.chat_id = f.chat_id) returning 1
), fl_dup as (
  delete from reply_mode_flags f using p
  where f.profile_id = p.old and (f.chat_id = '*'
    or exists (select 1 from reply_mode_flags x where x.profile_id = $4 and x.chat_id = f.chat_id)) returning 1
), docs as (
  update documents d set metadata = jsonb_set(d.metadata, array[case when $2 = 'telegram' then 'botTgId' else 'botWaId' end],
                                              to_jsonb($5::text))
  from p where p.old_wf is not null and p.old_wf <> $5
    and d.metadata->>(case when $2 = 'telegram' then 'botTgId' else 'botWaId' end) = p.old_wf returning 1
), files as (
  update uploaded_files u set bot_wa_id = case when $2 = 'whatsapp' then $5 else u.bot_wa_id end,
                              bot_tg_id = case when $2 = 'telegram' then $5 else u.bot_tg_id end
  from p where p.old_wf is not null and p.old_wf <> $5 and u.owner_id = $1
    and (case when $2 = 'telegram' then u.bot_tg_id else u.bot_wa_id end) = p.old_wf returning 1
), mark as (
  update bot_profiles b set superseded_by = $4, superseded_at = coalesce(b.superseded_at, now()),
    workflow_id = case when p.old_wf = $5 then null else b.workflow_id end
  from p where b.profile_id = p.old returning b.profile_id
)
select exists (select 1 from mark) as adopted, (select old_wf from p) as previous_workflow_id,
  (select count(*) from mem)::int as memory_rows, (select count(*) from hist_mv)::int as history_rows,
  (select count(*) from outc_mv)::int as outcomes, (select count(*) from hand_mv)::int as handoffs,
  (select count(*) from docs)::int as restamped_chunks, (select count(*) from files)::int as restamped_files,
  (<сумма *_dup>)::int as dropped_duplicates;
```

В генераторе комментарии узлов — без `$`+цифра (V1), `queryReplacement` — массивом.

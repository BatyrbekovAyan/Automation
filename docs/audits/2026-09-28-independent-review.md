## Первая очередь: безопасность

### V1. SQL-инъекция в Delete File и новом AuthSession — P1, блокирует публикацию

**Где:** `Tools/n8n/apply-auth-gate.py:97`, `Tools/n8n/build-auth-workflows.py:161`.

В SQL-комментариях стоят параметры `$1` / `$3`. Установленный pg-promise подставляет значения и внутрь комментариев. Перевод строки в значении завершает комментарий, и хвост значения становится отдельной SQL-командой. Обычное экранирование строк эту конструкцию не спасает.

**Независимое доказательство:** настоящий запрос и установленный pg-promise, локальные TEMP-таблицы и ROLLBACK; безопасные дополнительные `SELECT` вернули контрольные числа **928** и **929**. В Delete File открытое compat-окно пропускает запрос без токена. Новый `AuthSession bootstrap` вообще не требует токена: Route допускает такое значение `appUserId`, даже если последующая проверка формата billing ID его отвергнет.

Read-back подтвердил: **опубликованный Delete File содержит тот же уязвимый SQL**. Новая уязвимая строка Create Install ещё не опубликована. Эксплуатационные запросы на production не отправлялись; фактического взлома это ревью не устанавливает.

Исполнитель уже записал staging-воспроизведение Delete File, но вынес его за объём итерации. Называть эту находку только «потенциальным риском» недостаточно. Перед публикацией нужно убрать подстановки из SQL-комментариев во всех исполняемых запросах, проверить остальные места и закрепить это общей проверкой, а не только проверкой двух шаблонов ботов.

Доказательства: `sql-comment-proof.json`, `bootstrap-comment-proof.json`; воспроизводящие скрипты рядом. Скан нашёл такие комментарии также в Suggestion Gate, Register Profile и RevenueCat Events; достижимость каждой дополнительной точки отдельно не утверждается.

### V2. R1: запрос QR всё ещё может присвоить чужое переподключение — P1

**Где:** `Tools/n8n/build-auth-workflows.py:241`, `:472`.

Для уже принадлежащего установке профиля исходная атака закрыта. Для старого профиля без `owner_id` недостаточно новой отметки `claim_pair_by`: она доказывает лишь запрос QR через прокси, а не то, кто завершил подключение.

**Воспроизведение:** A начинает claim и запрашивает QR, но ничего не сканирует и не вводит код. Настоящий владелец независимо переподключает тот же профиль. По его позднему `authorized_at` настоящий SQL привязывает профиль **и workflow к A**. Это другой случай, чем описанное исполнителем ограничение «заявитель подключил свой номер».

Нужно доказательство завершения именно операции заявителя либо проверенный код из принадлежащего владельцу канала. Одного временного окна недостаточно.

### V3. R2: отсутствие ботов у владельца позволяет забрать его billing ID — P1

**Где:** `Tools/n8n/build-auth-workflows.py:148–152`.

Добавленная таблица привязок защищает часть случаев, но разрешает переназначение при отсутствии живых ботов у прежней установки. Это не доказательство права на платную подписку.

**Воспроизведение с закрытым compat:** у действующего владельца есть синтетический платный тариф, но нет живых ботов. B называет известный ему RevenueCat ID и получает его в подписанном токене без кода/секрета владельца. Реальные GetUsage, Bind Profile, Create gate и Count Dialog допускают чтение тарифа, привязку профиля и учёт диалога на чужой billing ID. Старый токен владельца одновременно ещё допускается.

Случай требует знания чужого ID; само знание идентификатора не должно становиться правом использовать подписку. Нужен подтверждённый перенос, включая восстановление после переустановки, а не исключение по количеству ботов.

### V4. R3: чужой legacy-файл можно присвоить и удалить — P1

**Где:** `Tools/n8n/apply-auth-gate.py:60`.

Потеря binary и обычная загрузка исправлены. Но Register Upload разрешает присвоить существующую запись с `owner_id=NULL`, не сверяя её прежние workflow с правами заявителя.

**Воспроизведение:** A владеет своим workflow, но передаёт известный fileId чужого старого прайса. Реестр возвращает `allowed=true`, принимает A владельцем, цепочка доходит до перезаписи оригинала. Затем настоящий Delete File SQL разрешает A удалить данные чужого файла: число чужих chunks **1 → 0**. HTTP-запись в Storage в этом тесте подменена, БД — временная; реальные файлы не затронуты.

Нужно проверять принадлежность старого файла при принятии его новым владельцем, в том числе строки без владельца и файлы без записи реестра.

## Вторая очередь: правильность автоответов и памяти

### V5. R6: новое сообщение в ту же секунду может остаться без ответа — P2

**Где:** `Tools/n8n/apply-history-handoff.py:66–69`.

Старое сообщение, доставленное с задержкой и меньшим временем, теперь не отменяет новое. Но два разных сообщения с одинаковым временем не меняют generation.

**Воспроизведение WA и TG:** A проходит последний просмотр истории; затем приходит более новое B с тем же `time`. Разрешение на отправку A сохраняется. A отправляет старый ответ, а выполнение B видит его эхо и завершается `superseded`. Итог в журнале: **A=sent, B=superseded**.

Нужно различать свежесть событий при одинаковой секунде; одного строгого сравнения времён недостаточно. Это конкретное незакрытое условие R6, а не требование устранить любую теоретическую сетевую гонку.

### V6. R7: одинаковый текст связывает память не с тем выполнением — P2

**Где:** `Tools/n8n/apply-history-handoff.py:147–149`, `:168–170`.

Удаление по «первой строке после watermark с таким текстом» не устанавливает принадлежность записи конкретному запуску.

**Воспроизведение WA и TG:** новое выполнение заканчивается первым и отправляет ответ. Старое заканчивается позже с точно таким же текстом. Отмена старого удаляет **уже отправленную строку нового**, оставляя старый черновик. Ручная реплика между ними сохраняется, но порядок разговора в памяти становится неверным.

Дополнительно `send_unknown` специально оставлен обычной AI-репликой без пометки неопределённости (`:129`, `:146`). В журнале доставка неизвестна, а в контексте следующей генерации текст выглядит сказанным клиенту. Это противоречит явному критерию исходного промпта. Нужна связь памяти с событием/выполнением и различение подтверждённой и неизвестной доставки.

### V7. R10: подтверждение доставки всё ещё принимает недостаточные доказательства — P2

Отсечение чужого `chatId` исправлено. Но настоящий Reconcile Check принимает кандидата с тем же чатом и текстом при явно чужом `profile_id`. При единственной ручной реплике без `from_where='phone'` также получается `sent` с её id; вариант с маркером `wh_type='outgoing_message_phone'` тоже проходит.

Проверено на синтетических ответах WA/TG. Это не доказательство, что транспорт сейчас возвращает чужие профили; это доказательство отсутствия требуемой проверки scope и слишком уверенного решения при недостаточной связи с попыткой. Сам по себе дефект меняет подтверждение доставки, не отправляет дополнительное сообщение.

При противоречивом профиле, ручном происхождении или недостаточной идентификации попытки должен оставаться `send_unknown`.

## Третья очередь: подсказки и качество ответов

### V8. R13: длинная старая реплика вытесняет последний вопрос — P2

**Где:** `Tools/n8n/apply-suggest-v2.py:64`; подготовка истории в `Assets/Scripts/Chat/N8nSuggestionsProvider.cs:290`, `:318`.

Клиент отправляет историю с ограничением 500 символов на реплику, а `lastIncomingText` содержит полный накопленный текст. Сравнение по точному тексту принимает полную старую реплику за новую и дописывает её после уже имеющегося последнего вопроса. Упаковка «новейшее первым» затем выбирает именно старую реплику.

**Воспроизведение WA/TG:** старая реплика длиной 617 символов с `OLD54321`, затем «А NEW12345 есть?». Настоящий Prep выдаёт только старый артикул; **NEW12345 пропадает** из поискового запроса и exactTokens. Ошибается также выбор релевантного каталога и `lastClientMessage`.

Это остаток R13, не доказанная новая регрессия: прежняя версия тоже не проходила этот вход. Нужно восстановить правильный порядок и перекрытие истории с накопленными входящими сообщениями до сокращения текста.

### V9. R14 действительно улучшен, но обязательные сценарии не закрыты — P2

Пересчёт сохранённых ответов подтверждает результат на одном оценщике h3: **52 устойчиво успешных / 3 нестабильных / 8 проваленных сценариев → 59 / 1 / 3**, по 3 запуска каждого из 63 сценариев. Дополнительные 5 запусков проблемных автосценариев дают **7 / 6 / 1**, поэтому общий результат нельзя понимать как отсутствие нестабильности.

Остаётся:

- **Конфликт цен 3200/3900: 0 из 8 успешных ответов после правок.** Бот выбирает цену прайса, не сообщая о расхождении с каталогом. Если промпта недостаточно, серверная сверка остаётся способом выполнить исходное требование.
- Личная эмоциональная реакция: **0/3**, панель продолжает предлагать ответы вместо воздержания.
- Казахский вопрос панели: **0/3**, карточки по-русски.
- Оценщик языка проверяет отдельные признаки казахского, поэтому пропускает смешанные ответы. Пять известных ограничений проверок оформлены как expected failures; зелёный запуск оценщика не означает, что этих ограничений нет.

Исходные ошибки оценки бесплатной доставки и конфликта цен исправлены, прежние результаты пересчитаны без подмены исторических файлов — это сделано правильно. Однако объявление серверной сверки «вне итерации» и ссылка на locked-правила панели не закрывают запрос пользователя на исправление этих случаев. Менять утверждённую политику или ослаблять ожидаемые результаты для этого не требуется.

1. **V1–V4:** устранить выполнение постороннего SQL и обходы владения. Добавить именно приведённые отрицательные сценарии, сохранив успешную загрузку и законное восстановление.
2. **V5–V7:** порядок сообщений, принадлежность записей памяти, неопределённая доставка. Затем повторить reply/handoff на WA и TG.
3. **V8–V9:** сначала корректный вход поиска, затем конфликт цен, язык и воздержание. Повторить оценки на одинаковом наборе и одном оценщике, включая оставшиеся критичные случаи.
4. **R4/R8/V11 и клиентская проверка:** закрыть остаточные случаи; проверить холодный старт, переключения и поздние ответы на устройстве.
5. **V10 и релиз:** поправить инвентаризацию, подготовить обновление существующего бота и его промпта; после разрешённой публикации сверить активные версии, выполнить canary и только затем выпускать клиент.

**Критерий готовности:** не только зелёные существующие тесты, но и прекращение воспроизведения приведённых ошибок, проверенные активные версии на сервере и отдельный результат проверки на телефоне.

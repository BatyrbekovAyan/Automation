## Решения контроллера

### 1. Правило: какой чат личный, а какой рабочий

**1.1. WhatsApp без флагов** *(разбор плана)*. Если у чата WhatsApp флаги не пришли, правило читает каждый как «нет»; шаг «флаги
неизвестны → личный» — только для Telegram. Почему: у WhatsApp флаги на деле приходят всегда. Цена ошибки: нет.

**1.2. Шаг Telegram «флаги неизвестны» — раньше решения владельца** *(задача 1)*. Порядок из задания сохранён. Почему: решение
владельца до правила не доходит — сервер применяет его раньше, при чтении режима, приложение тоже. Цена ошибки: сегодня нет;
поменять порядок — одна строка.

**1.3. Типы чатов Telegram** *(задача 1)*. `user` — человек; `channel` и `chat` — не человек; любой другой тип, в том числе пустой, —
«неизвестно», то есть личный, и такое решение не записывается. Почему: в образцах tapi личные диалоги — всегда `user` (23 из 23, в
вебхуках 5 из 5); каналы и группы названы в спеке. Цена ошибки: человек с непредвиденным типом не получит ответа, пока тип не
добавят в список; записано при этом ничего не будет, так что всё поправимо.

**1.4. Контакт WhatsApp — по карточке чата** *(живые проверки)*. Признак «контакт» — поле `FullName` карточки чата из списка Wappi
(один запрос по цифрам номера), а не имя из вебхука. Если бы даже у сохранённого контакта `FullName` был пуст — остановиться и
спросить владельца (на живых проверках у сохранённых контактов он был). Почему: имя в вебхуке Wappi заполняет по цепочке «имя из
книги → имя профиля → …», и у незнакомца там его собственное имя профиля — почти каждый новый клиент читался бы как контакт, и
ИИ-сотрудник молчал бы с новыми людьми. Цена ошибки: нераспознанный контакт решается по истории переписки.

**1.5. История — только по странице новейших сообщений** *(живые проверки, критично)*. Для обоих каналов: берётся страница новейших
сообщений; на ней должно быть само пришедшее сообщение (иначе «неизвестно», ничего не записывается); есть строка старше
подключения — «переписка до подключения», личный; страница короче предела — это весь чат, истории нет; полная страница целиком новее
подключения — «неизвестно», не записывается. Почему: Telegram (tapi) не умеет листать с начала — на запрос «старые вперёд» он всё
равно отдаёт страницу новейших. План брал «самое старое сообщение» именно так, и на Telegram это было бы само новое сообщение:
старый знакомый читался бы новым человеком, и ИИ-сотрудник ответил бы ему. Цена ошибки: чат без решения, где с подключения набралось
больше сообщений, чем на странице, молчит, пока владелец не решит сам (см. 1.9).

**1.6. Бот Telegram — не человек** *(живые проверки)*. Тип чата `bot` из вебхука — в список «не человек» на сервере и в приложении, а
признак вебхука «это бот» — флаг бота. Почему: карточка называет бота `user` с отметкой бота, а вебхук — `bot`; без правки чат с ботом
оставался бы «неизвестным» на каждом сообщении — безопасно, но каждый раз лишний запрос к Wappi, и решение не записывается. Цена
ошибки: для людей никакой — их тип `user`.

**1.7. Карточка WhatsApp без поля «контакт» — «неизвестно»** *(задача 3)*, решение не записывается. Почему: у Wappi это поле есть
всегда (у несохранённого человека — с пустым именем), его отсутствие — испорченный ответ, а прочесть его как «не контакт» значило бы
ответить контакту из-за сбоя. Цена ошибки: если поле всё-таки бывает пустым, каждый новый клиент WhatsApp молчит, пока владелец не
решит; это ловит проверка на устройстве — несохранённый номер пишет первым и должен получить ответ.

**1.8. Строка без времени и история при неизвестном контакте** *(задача 3)*. Оставлены оба правила: «строка без времени —
неизвестно» и «историю не спрашивать, пока неизвестно, контакт ли». Почему: это безопасная сторона, а время Wappi присылает всегда.
Цена ошибки: по такому чату карточка запрашивается заново на каждом сообщении.

**1.9. История — с одной страницы в 50 сообщений** *(финальное ревью и волна исправлений)*. Решение по истории — с одной страницы в 50
сообщений; в начало разговора по-прежнему уходят новейшие 10. Почему: страница в 10 сообщений навсегда оставляла без решения чат, где
после подключения набралось 10 сообщений, — а такое бывает: первые 30 минут после подключения решений нет вовсе; 50 — столько же
приложение уже берёт у Wappi за раз и знает, что Wappi их отдаёт. Цена ошибки: новый клиент, написавший больше 50 сообщений до
первого, по которому можно решить, остаётся без решения — это записано как известное ограничение.

**1.10. Не-человек важнее решения владельца — и на входе Telegram** *(финальное ревью)*. Вход шаблона Telegram отказывает вебхуку от
бота, канала или группы, даже если у чата есть рабочее решение. Почему: первое правило спеки — не-человек всегда личный, а проверка
ничего не стоит. Цена ошибки: нет.

**1.11. Бот в WhatsApp — отложено** *(волна исправлений)*. Вход шаблона WhatsApp признак «это бот» пока не читает (правило читает его,
когда решает). Почему: чата с ботом WhatsApp в живых проверках не встретилось. Цена ошибки: если владелец сам сделает чат с ботом
WhatsApp рабочим, ИИ-сотрудник станет ему отвечать.

### 2. Что сервер записывает, кому отдаёт и когда удаляет

**2.1. Начало разговора — в порядке Wappi** *(задача 2)*. Когда чат становится рабочим, сервер дописывает в историю и память его
начало со страницы Wappi: страница приходит новейшими вперёд и сохраняется перевёрнутой по месту в списке, никогда не
пересортированной по времени. Почему: сообщения одной секунды и сообщения без времени сохраняют порядок Wappi. Цена ошибки: если
кто-то передаст страницу старыми вперёд, порядок в памяти перевернётся (вызывают только наши генераторы).

**2.2. Удаление личных чатов — первой веткой Sweep** *(задача 8; сделано в волне исправлений)*. Шаг «Wipe Personal Chats» стоит в
Profile Lifecycle Sweep первым, раньше остальных веток; позицию держит генератор, проверяет верификатор. Почему: по плану он шёл после
«Expire Learning Rows», а у пяти узлов выше нет обработки ошибок — одна необработанная ошибка там пропускала бы удаление; для
обещания «удаляется через 2 дня» это неверно. Финальное ревью нашло, что перенос ещё не сделан, — его сделала волна исправлений.
Цена ошибки: постоянный сбой Sweep молча остановил бы удаление.

**2.3. Сбой базы у панели подсказок — отказ** *(задача 5)*. Если гейт Suggest Replies не может прочитать базу, панель отказывает, а
не пропускает запрос. Почему: сервер не может доказать, что чат рабочий, значит — без ИИ (то же направление, что «неизвестно —
личный»). Цена ошибки: при сбое базы панели нет и в рабочих чатах (приложение повторит запрос).

**2.4. Журнал выполнений Suggest Replies** *(задача 5)*. Если прод хранит успешные выполнения, у Suggest Replies их хранение тоже
отключается; на стенде остаётся. Почему: отклонённый запрос из личного чата несёт его сообщения. Цена ошибки: на проде вердикт гейта
не виден в успешных выполнениях.

**2.5. Журнал: подтверждено на проде — не хранить** *(задача 4)*. Хранение успешных выполнений отключено у обоих шаблонов и у Suggest
Replies (на стенде — включено); клон получает настройку от шаблона — при создании и через update-clones; два живых клона «2» получат
её при выкладке. Почему: живая проверка показала, что прод хранит успешные выполнения 7 дней вместе с телом вебхука. Цена ошибки: тела
вебхуков личных чатов неделю лежали бы в журнале прода.

**2.6. Из чата без решения не сохраняется ничего** *(задача 4)*. Пока у чата нет решения, не записываются ни сообщения клиента, ни
сообщения владельца. Когда чат становится рабочим, сервер дописывает сообщения владельца со страницы Wappi (в память — «Владелец:
…»), так что начало разговора возвращается. Сообщения владельцу самому себе (уведомление о заявке, об отключении канала) уходят в его
собственный чат, который ничто не читает. Почему: так требует спека — из ещё не решённого чата не сохраняется ни текст, ни имя. Цена
ошибки: начало старше страницы Wappi в память не попадёт; остаток — отправленное из приложения записывается как отправленное с
телефона.

**2.7. Политика конфиденциальности — точная формулировка, на одобрение владельцу** *(задача 17, ревью)*. Строку в
`docs/legal/privacy.html` заменили точной: «если рабочий чат становится личным», с оговоркой, что «по умолчанию» зависит от того, что
сообщает мессенджер; текст ждёт одобрения владельца. Исключение после смены номера CLAUDE.md описал как известное и открытое (его
закрыла задача 9d); номера задач плана в CLAUDE.md не пишутся. Почему: прежняя строка обещала больше, чем делает сервер. Цена ошибки:
чуть более длинный раунд документов.

**2.8. Смена номера должна запускать удаление** *(задача 17, ревью)*. Вычисленное «личный» поверх рабочей записи запускает часы
удаления (2 дня); для этого — отдельная задача 9d. Почему: спека считала, что у вычисленного «личный» «удалять нечего», а после смены
номера это неверно — прежний рабочий клиент становится контактом нового номера, а его рабочая переписка лежит. Цена ошибки: ещё одна
серверная задача; без неё переписка бывшего рабочего чата оставалась бы навсегда после смены номера или переподключения.

**2.9. Финальное ревью сервера — что вошло в волну исправлений** *(финальное ревью)*. Удаление первой веткой Sweep (2.2); история с
большей страницы (1.9); вход Telegram отказывает ботам, каналам и группам (1.10); начало разговора не записывает строки, отправленные
через API, как сообщения владельца (уточнено в 2.10); сравнение настройки журнала инструментами выкладки (6.4); документы — три пути,
которыми запускаются часы удаления, и комментарий внутри запроса удаления (он едет на прод в самом запросе); список таблиц удаления в
проверках — из списка таблиц линии ИИ-сотрудника; цифра задержки в спеке; несколько мелких отложенных пунктов; честный черновик
политики конфиденциальности на одобрение владельцу. Почему: обещанное «удаление первым», новый клиент, которому никогда не ответят,
единственная проверка обещания о журнале, бесплатная защита по первому правилу спеки, ложные «Владелец: …» в памяти, документы внутри
выложенного запроса. Цена ошибки: больший серверный дифф на ревью.

**2.10. Строка, отправленная через API, — чья она** *(волна исправлений, ключевое уточнение)*. Строка с отметкой API — ответ
ИИ-сотрудника только там, где ИИ-сотрудник уже работал в этом чате (это видно по учёту диалогов, который удаление не трогает), — там
она пропускается; в остальных чатах это сообщение владельца из приложения, и оно записывается как его («Владелец: …»). Почему:
пропускать все строки с отметкой API значило терять начало разговора, когда владелец писал клиенту из приложения (частый случай в
первые дни), ради редкой путаницы после удаления. Цена ошибки: сообщение владельца из приложения, отправленное, пока чат был личным
после рабочего периода, не вернётся.

**2.11. Остатки этого правила приняты** *(волна исправлений)*: сбой учёта диалогов; переустановка, перенёсшая аккаунт (переносится
только текущий месяц); строки WhatsApp из API без отметки. Почему: каждый остаток требует редкой последовательности поверх удаления.
Цена ошибки: изредка строка «Владелец: …», которую на самом деле написал ИИ-сотрудник.

**2.12. Неверная фраза черновика политики — исправить сразу** *(повторное ревью волны)*. Фраза «ИИ-сотрудник получает до 10 последних
сообщений» неверна: панель «Выбрать» получает 24 сообщения, повторная подача в «Авто» — до 15 сообщений клиента; 10 — только то, что
сохраняется в начало разговора. Её исправила волна приложения, проверило ревью; окончательную формулировку утверждает владелец.
Почему: это публичное обещание, а правка — одна фраза. Цена ошибки: нет.

**2.13. Фраза CLAUDE.md о чатах, которые никогда не были рабочими, оставлена как есть** *(последний проход документов)*. CLAUDE.md
говорит, что у такого чата ничего не сохранено и отсчёт удаления не запускается. Для того, что сервер сохранил ДО выкладки (тогда
записывались все чаты), это неверно: у чата, который решён личным с первого сообщения после выкладки, эти данные остаются. Почему:
пакет выкладки говорит это прямо и называет выход — удалить ИИ-сотрудника; на проде сейчас работает только тестовый «2», а сборка с
этой функцией ещё ни у кого не стоит. Цена ошибки: разработчик прочтёт фразу об установившемся режиме как относящуюся и к данным,
сохранённым до выкладки.

### 3. Линия ИИ-сотрудника, переподключение и смена номера

**3.1. Смена номера не уводит момент подключения назад** *(задача 2)*. Если при переподключении остаётся строка подключения нового
профиля, потому что его известный номер другой, её момент — самый поздний из своего и моментов предшественников. Почему: смена номера
не может дать более раннее подключение. Цена ошибки: дыры в правиле спеки о смене номера при переподключении с другим номером.

**3.2. Две дыры в правиле слияния — закрыты до ревью** *(задача 6)*. (1) Номер оставшейся строки подключения — её собственный, а если
его нет — известный номер нового профиля. (2) Решение «не человек» при слиянии важнее любого другого, в том числе решения владельца.
Почему: это дефекты плана, найденные исполнителем. Цена ошибки: (1) следующую смену номера не с чем было бы сравнить; (2) слияние
сделало бы не-человека рабочим.

**3.3. Прежний номер запоминается в начале подключения** *(задача 11)*. Настройки записывают прежний профиль и номер, когда подключение
НАЧИНАЕТСЯ, и сравнивают, когда оно завершилось. Почему: «Сменить номер» сначала выходит из аккаунта и стирает номер — в конце его было
бы уже не прочесть. Цена ошибки: не найдена.

**3.4. Лишний экран «Кто из них клиенты?» — по признаку сервера** *(задача 11)*. Ответ сервера на «подключено» получает признак «номер
сменился», и приложение ставит свой флаг по нему; первое подключение остаётся за приложением. Почему: экран просился снова при том же
номере — после выхода из аккаунта снаружи и после «Назад» в «Сменить номер», — а это против спеки. Цена ошибки: до исправления —
лишний экран, который можно закрыть.

**3.5. Уточнение: признак сервера и отметка «канал уже видели»** *(перед задачей 7)*. Сервер отвечает «номер сменился», только когда
вызов сдвинул момент подключения, потому что пришёл известный другой номер. Первое подключение приложение отмечает постоянной
отметкой канала у ИИ-сотрудника: ставится при первом подключении, для уже подключённых каналов — при запуске новой версии (такие
ИИ-сотрудники экран не получат), снимается только удалением ИИ-сотрудника. Почему: так исправлены оба лишних показа из 3.4. Цена
ошибки: один лишний ключ.

**3.6. Три признака смены номера** *(задача 14)*. Признак сервера, ИЛИ (тот же профиль) момент подключения позже запомненного, ИЛИ
сравнение номеров самим приложением, когда известны оба. Почему: первый ответ НОВОГО профиля смену номера доказать не может. Цена
ошибки: не найдена.

**3.7. Отметка «канал уже видели» для старых каналов — один раз** *(задача 14)*: при первом запуске этой версии, после загрузки
ИИ-сотрудников, для каждого канала с настоящим профилем. Почему: при каждом запуске она отмечала бы и канал с прерванным подключением
— и он терял бы свой экран. Цена ошибки: для ИИ-сотрудников до выпуска — нет; отметка до загрузки оставила бы их без защиты (это
закреплено тестом).

**3.8. Номер для сравнения — последний подтверждённый** *(задача 14, ревью)*. Признак сравнивает с отдельно хранимым последним
подтверждённым номером канала (пишется при каждом подтверждённом подключении, удаляется только с ИИ-сотрудником), а не с номером из
настроек. Почему: «Назад» в «Сменить номер» и проверка выхода снаружи стирают номер настроек и удаляют профиль — самая частая смена
номера (новая SIM выкидывает устройство, владелец подключает заново) не попадала ни под один признак. Цена ошибки: один ключ;
остаток — подключение Telegram с неизвестным номером полагается на признак сервера (только тот же профиль).

**3.9. Двойной показ экрана и мелочи экрана** *(задача 14, ревью)*. Приложение помечает подключение, по которому само просит экран, и
первый ответ сервера по нему снимает метку, не прося экран второй раз; экран проверяется и при выходе из режима правки, и при
закрытии; «Готово» с отметками без живого профиля — сообщение об ошибке записи; одна функция закрытия; тест. Почему: это та же
область кода, что 3.8, — откладывать незачем. Цена ошибки: нет.

**3.10. Линия решает один раз; часы удаления при слиянии** *(задача 9d, ревью)*. При переподключении: (i) пока подключение то же
(новым оно считается, только когда оба номера известны и разные), перенесённое вычисленное решение важнее вычисленного решения нового
профиля, принятого до слияния; при новом подключении важнее своё; решение владельца и «не человек» — как было; (ii) если на новый
профиль приходит «личный» поверх рабочего периода, он приходит с идущими часами удаления. Почему: сервер решает по линии один раз, а
решение нового профиля до слияния было принято против момента его создания; замысел спеки (решать один раз; рабочий период не
переживает перехода в личные) важнее её буквального правила слияния, которое не предвидело гонку до слияния; если чинить одни часы,
клиент, ошибочно решённый личным, был бы стёрт через 2 дня. Цена ошибки: в очень редкой гонке вычисленное решение предшественника
заменит решение нового профиля, принятое до слияния.

**3.11. Мелочи после ревью задачи 9d** *(задача 9d)*. Взяты: индекс списка удаления, который чинит себя сам; устаревшие комментарии;
слишком категоричная фраза; «личный» поверх рабочего сам снимает отметку «удалено»; заметка о цепочке A → B → A в известных
ограничениях и в проверке на устройстве; уточнения текста. Не взяты: половина одного пункта и старые рабочие чаты после смены номера,
которые больше не пишут, — они оставлены описанным остатком на решение владельца. Почему: ту половину покрывает уже описанная гонка, а
исправление остатка стёрло бы память вернувшегося клиента. Цена ошибки: владелец может попросить исправление позже. (Владелец решил
«Хранить, как сейчас».)

**3.12. Принятые особенности слияния** *(задача 9d)*. (1) Взятая личная запись с идущими часами считается рабочим периодом под
чатом. (2) «Не человек», пришедший поверх рабочего периода, тоже получает часы. (3) Слияние читает строку подключения нового профиля
на момент своего запроса: номер, который приложение сообщит во время слияния, оставит чат без решения до следующего сообщения.
Почему: (1) иначе слияние роняло бы идущие часы — ровно ту дыру, что нашло ревью; (2) так же, как в 3.10; (3) это безопасная сторона,
и она описана. Цена ошибки: сверх описанной гонки — нет.

**3.13. Ошибочное подключение A → B → A и старые рабочие чаты — вопрос владельцу** *(финальное ревью)*. Решать владельцу; волна
исправлений этого не трогает, черновик политики описывает сегодняшнее поведение честно. Почему: после задачи 9d исправленное
ошибочное подключение (A → B → A) перерешало бы всех прежних клиентов A личными, а через 2 дня стёрло бы сохранённое о них; что с
этим делать и со старыми рабочими чатами после настоящей смены номера — выбор продукта, а не техники. Цена ошибки: серверная задача
перед пакетом, если владелец выберет смягчение. (Владелец выбрал «Да, восстанавливать» — задача 9e — и «Хранить, как сейчас».)

**3.14. Возврат к прежнему номеру не запускает удаление** *(задача 9e, ревью)*. Удаление пропускает вычисленное «личный», принятое при
ошибочном номере, пока подключение восстановлено; при настоящей смене номера — прежнее поведение 9d; оба пути — тот же профиль и
слияние. Почему: решение владельца («клиенты прежнего номера не замолкают и не стираются») важнее буквального «правило 9d действует
как обычно» из задания, которое написал сам контроллер. Цена ошибки: рабочий период чата, решённого личным при ошибочном номере,
ждёт, пока чат не напишет снова или пока не случится настоящая смена номера.

**3.15. Мелочи после ревью задачи 9e** *(задача 9e)*. Из CLAUDE.md убран повод чтения решений, которого нет («выход из чата»);
приложение сравнивает разрешённый id чата (у Telegram их два); поправлен комментарий текста листа; описано, что возврат возвращает
прежний момент подключения (без 30 минут ожидания), — поправлена и проверка на устройстве; описаны две особенности (решение,
пришедшееся на сам возврат; слияние с несколькими предшественниками судится по самому раннему). После возврата приложение снимает
только свой собственный запрос экрана «Кто из них клиенты?» для этого самого подключения. Почему: это неточности, которые нашло
ревью, а экран после возврата иначе показывался бы снова. Цена ошибки: так и не пройденный первый экран того же номера теряет
напоминание (папка «Личные» остаётся).

**3.16. Принятые особенности возврата** *(задача 9e)*. Дополнительное условие оставляет идущими часы, начавшиеся до ошибки. Остальные
пробелы описаны в известных ограничениях: следующая настоящая смена номера прекращает пропуск; «личный» поверх ошибочного решения
сохраняет свои часы; A → B → A → B читается как настоящая смена; и три случая экрана. Почему: без этого условия такие часы не
кончились бы, пока подключение восстановлено; остальное — редкие цепочки. Цена ошибки: редкие, описанные случаи.

### 4. Сервер: вход шаблонов, подпроцесс Decide Audience, вебхук ChatAudience

**4.1. Вебхук отказывает не-людям по виду id и по записанному «не человек»** *(задача 2)*. Бота Telegram, которого видно только из
карточки чата, от «сделать рабочим» защищает приложение — оно не показывает у ботов «В рабочие», — а не сервер. Почему: при записи
решения владельца сервер карточку чата не читает, а обойти защиту может только изменённое приложение. Цена ошибки: такое приложение
могло бы сделать чат с ботом рабочим — вред только собственному аккаунту владельца.

**4.2. Порядок в защищённом списке Set Workflow State** *(перед задачей 7)*. `crChatAudience01` — после `crSetSchedule001`,
`crAudienceDec001` — после `crChatAudience01`. Почему: задача 7 шла раньше задачи 3, а план предполагал обратный порядок. Цена
ошибки: нет.

**4.3. Повторная подача — только сообщения самого чата** *(задача 7, ревью)*. Ждущее сообщение подаётся ИИ-сотруднику заново, только
если его собственный отправитель — сам чат (оба канала); такие строки годятся и для начала разговора. Строка Telegram в виде из
документации Wappi (имя пользователя вместо id) не подаётся до живой проверки. Почему: повторная подача подменяла отправителя и
обходила единственную защиту шаблонов от групп — группа Telegram, ставшая рабочей, получила бы ответ на сообщение участника; лучше
промолчать, чем ответить в группе. Цена ошибки: настоящая строка личного чата Telegram с другим видом отправителя никогда не подавалась
бы повторно — не было бы мгновенного ответа на «Сделать рабочим».

**4.4. WhatsApp всегда читает карточку** *(живые проверки)*. Убраны настройка «откуда брать признак контакта» и вход подпроцесса с
именем из вебхука; у WhatsApp карточка нужна всегда (кроме «не человек» по виду id). Почему: вариант с вебхуком неверен при любых
проверках (1.4), а вход с таким названием подталкивает использовать его как признак контакта. Цена ошибки: один лишний запрос к Wappi
на первое сообщение каждого нового чата WhatsApp.

**4.5. Чат WhatsApp под кодом @lid — тот же чат** *(живые проверки; исправлено в задаче 9)*. Строка — этого чата, если в ней его номер
ИЛИ его код @lid; код берётся из вебхука (вход подпроцесса), а в вебхуке ChatAudience — из карточки чата; поданное сообщение строится
с отправителем и чатом — id решения. Почему: повторная подача отбрасывала страницу целиком, если строка называла другой чат, — у
чата WhatsApp, чьи строки идут под его кодом (так было у 2 из 4 прочитанных чатов), не было бы ни начала разговора, ни мгновенного
ответа: безопасно, но функция молча выключена. Цена ошибки: один лишний запрос к Wappi, когда владелец делает чат WhatsApp рабочим.

**4.6. Ответ подпроцесса не может пройти ворота «рабочий»** *(задача 3, ревью)*. Поля вердикта переименованы так, что их не выдаёт ни
один узел выше; ворота читают только поля записанной строки (вид и источник); тестовый обход графа воспроизводит поведение n8n: узел с
«продолжать при ошибке», упав, передаёт дальше свой входной элемент. Почему: ревью воспроизвело, что при сбое записи решения входной
элемент проходил ворота — ответ «рабочий» без строки в базе. Цена ошибки: нет.

**4.7. Метка итога у чата, который не стал рабочим** *(задача 4)*. Метка `Outcome` несёт собственный итог подпроцесса, если это одно
из пяти «личных» значений, иначе — «личный, неизвестно». Почему: метка бесплатно объясняет, почему чат не получил ответа. Цена ошибки:
один набор меток (они видны на стенде и в ошибочных выполнениях).

**4.8. Отложенные мелочи сервера** *(финальное ревью)*. Строка подключения без номера не замечает смену номера; момент подключения —
создание профиля; ответ, отменённый потому, что чат стал личным, нельзя получить повторно; решения всегда читаются целиком; все прочие
пункты, которые ревью признало «может подождать»; четыре пункта уже были исправлены. Почему: первому нужен потерянный первый отчёт
«подключено»; до подключения проходят минуты; так же устроен ответ, отменённый сменой режима; производительность — позже; у прочих —
доводы ревью. Цена ошибки: эти дефекты уедут на прод и будут исправлены позже.

### 5. Приложение

**5.1. История неизвестна при испорченном времени** *(задача 10)*. Если время последнего сообщения или момент подключения не больше
нуля, «писал до подключения» — «неизвестно», а не «да». Почему: оба исхода — личный, а «да» выдумывало бы «писал раньше». Цена
ошибки: подпись «неизвестно» вместо «писал раньше» при испорченном времени.

**5.2. Диалог Telegram без карточки пользователя** *(задача 10)*. Приложение читает его как «флагов нет» и может ПОКАЗАТЬ чат рабочим,
пока сервер считает его «неизвестным» — принято. Почему: tapi у таких диалогов карточку присылает всегда; это только показ и
уведомления, а панель и сервер работают по решениям сервера. Цена ошибки: чат Telegram без решения может прислать уведомление.

**5.3. Сбой сети не откатывает перенос чата** *(задача 11)*. Перенос повторяется — с паузами, после 8 попыток ждёт и возобновляется при
возврате в приложение и при запуске, — а чат показан «в пути»; откатывает только отказ сервера (400 / 401 / 403 или не человек), с
сообщением «Не удалось перенести чат», без «проверьте интернет». Почему: сбой сети — не отказ, и ход владельца не должен теряться.
Цена ошибки: при долгом сбое чат висит «в пути» без сообщения.

**5.4. Уведомление и быстрая сверка с сервером** *(задача 12, ревью)*. Уведомления нет, если чат личный хотя бы до или после
обновления последнего сообщения; входящее в чате без решения сервера просит прочитать решения через ≈ 3 с (одно чтение на пачку
сообщений). Почему: прикидка «по последнему сообщению» переводила чат с перепиской до подключения в рабочие ровно на его первом новом
сообщении. Цена ошибки: личный чат один раз прозвенит или на секунды окажется в рабочем списке.

**5.5. Прикидка истории — по самому раннему виденному времени** *(задача 12, исправление до слияния; сделано в волне исправлений)*.
Приложение запоминает для каждого чата самое раннее время последнего сообщения, которое видело (в `audience_cache.json`), и считает
«переписка до подключения», если оно раньше подключения. Почему: по последнему сообщению старый знакомый переходил в рабочие на
первом новом сообщении и оставался там до решения сервера — в первые 30 минут каждое его сообщение звенело. Финальное ревью нашло,
что это ещё не сделано, — сделала волна исправлений. Цена ошибки: шумные первые 30 минут после подключения (на ИИ не влияет).

**5.6. Личный чат в поиске свайпается как в папке** *(задача 13)*: «В рабочие»; не-человек — без свайпа; действие следует за текущим
видом чата. Почему: так в спеке — «как Архив в WhatsApp». Цена ошибки: в поиске свайп не тот, что ждёт владелец.

**5.7. Цвет кнопки переноса** *(задача 13)*. Пока один цвет в обоих местах; серый «В личные» из эскиза — на проверку на устройстве.
Почему: новую пару цветов вслепую не придумывали. Цена ошибки: одна правка цвета позже.

**5.8. «Удалить» у WhatsApp — везде** *(задача 13)*: в рабочем списке, в папке, у личного чата в поиске; у не-человека в WhatsApp —
только «Удалить». Почему: спека удаление не убирала, сегодня удалить можно любой чат WhatsApp, и «в папке без удаления» из плана было
бы потерей функции. Цена ошибки: лишняя кнопка удаления в папке.

**5.9. Шапка открытого чата** *(задача 15)*. У личного — значок «Личный»; переключатель «Авто» — только у рабочего (решение сервера
или ожидающий перенос в рабочие); у чата без решения — ничего; нажатие на имя по-прежнему предлагает «Сделать личным». Почему: горящее
«Авто», нажатие на которое ничего не делает, вводит в заблуждение. Цена ошибки: владелец не может заранее выставить режим чата до
решения сервера.

**5.10. Два похожих листа — принято** *(задача 15)*. Листы «Сделать личным / рабочим» повторяют устройство листа оплаты; общая
оболочка — отдельный рефакторинг на потом. Копии в тестах убраны сразу. Почему: так в проекте устроены все такие накладки, а общая
оболочка переписала бы лист оплаты, от которого зависят деньги. Цена ошибки: будущая правка попадёт только в одну копию.

**5.11. Подпись «в контактах» под именем в шапке не сделана** *(задача 15)*. Почему: её нет ни в спеке, ни в плане; отметку
показывает лист. Цена ошибки: одна подпись позже.

**5.12. Голосовые и реакции не подаются повторно — лист не обещает «сразу ответит»** *(задача 7; сделано в волне исправлений)*. Если
последнее сообщение клиента не того вида, что сервер подаёт повторно, лист «Сделать чат рабочим?» говорит «будет отвечать сам на
новые сообщения». Почему: строки Wappi не несут звука голосового (его берут отдельной загрузкой), поэтому голосовые и реакции сервер
повторно не подаёт. Цена ошибки: лист обещал бы мгновенный ответ, которого не будет.

**5.13. Перенос нескольких чатов — с числом** *(задача 14)*: «N чат стал рабочим / N чата стали рабочими / N чатов стали рабочими»;
один чат — «Чат стал рабочим»; «Готово» без отметок ничего не отправляет. Почему: строка плана в единственном числе неверна для
нескольких чатов. Цена ошибки: одна строка текста.

**5.14. Экран «Кто из них клиенты?» обновляет список каждые 10 с, пока открыт** *(задача 14)*; загрузка показана, пока список чатов
канала пуст. Почему: история WhatsApp приходит минутами, а у нового номера личных строк может не быть вовсе — по плану («пока строк
нет») экран крутился бы вечно. Цена ошибки: несколько лишних запросов списка чатов, пока экран открыт.

**5.15. В режиме правки и на экране выбора строки не свайпаются** *(задача 14)*. Почему: это списки для выбора. Цена ошибки: нет
свайпа в режиме правки.

**5.16. Папка «Личные» переносит и удаляет через сам список чатов** *(задача 14)*. Почему: один путь кода для обоих списков. Цена
ошибки: нет.

**5.17. Кнопка «Назад» Android: открытый чат — раньше папки** *(задача 14)*. Почему: «Назад» закрывает то, что сверху, а открытый чат
лежит над папкой. Цена ошибки: «Назад» закрыла бы папку под открытым чатом.

**5.18. Папка закрывается только при смене ИИ-сотрудника или канала** *(задача 14)*, а не от повторного события о том же. Почему:
переход из настроек открывает папку сразу после переключения, и позднее событие закрыло бы её. Цена ошибки: нет.

**5.19. «Сводка» без личных чатов — до подсчётов** *(задача 16)*. Личные строки убираются до цифр, разниц и списка заказов и снова при
каждом изменении. Почему: спека убирает из «Сводки» любой след личного чата, а цифры, которые не сходятся со строками, выглядели бы
ошибкой. Цена ошибки: итоги меньше на личные чаты.

**5.20. Строка «Личные чаты» в настройках** *(задача 16)* открывает папку именно этого ИИ-сотрудника; без подключённого канала строка
считает, а нажатие только переводит на экран чатов; допустимо закончить переход после выезда настроек. Почему: строка — часть
настроек этого ИИ-сотрудника, а порядок шагов перехода важнее его скорости. Цена ошибки: переход чуть медленнее.

**5.21. Канал экрана чатов — после переключения ИИ-сотрудника** *(задача 16)*: тот, что экран чатов покажет этому ИИ-сотруднику.
Почему: владелец приходит из настроек, а не с экрана чатов. Цена ошибки: папка откроется на последнем канале ИИ-сотрудника, а не на
показанном до перехода (вкладка канала — в одно нажатие).

**5.22. Канал без живого профиля — «0»** *(задача 16)* в строке настроек, даже если в кеше есть его личные чаты. Почему: строка
считает то, что папка может открыть. Цена ошибки: «0» рядом со старыми чатами отключённого канала.

**5.23. Приложение должно загружать чаты под кодом @lid** *(задача 9c, по решению владельца)*. Исправлено отдельной задачей
приложения. Почему: защита от «чужих страниц» отбрасывала каждую страницу, где строки названы только кодом @lid, а код из списка
чатов не читался, — у таких чатов не грузились ни история, ни новые сообщения, а панель получала пустоту. Цена ошибки: ещё одна задача
приложения и полный прогон тестов.

**5.24. Финальное ревью приложения — что вошло в волну исправлений** *(финальное ревью)*. Прикидка по самому раннему времени (5.5) и
честный лист для голосовых (5.12); лист обещает «Авто» только при включённом канале; чтение решений, когда приходит ответ в ОТКРЫТОМ
чате без решения (только люди); принудительное чтение решений после обновления токена на всех путях успешного создания; две
неточности CLAUDE.md; пять пунктов проверки на устройстве; несколько дешёвых отложенных пунктов. Почему: первые два решены «до
слияния», но не были сделаны, а два чтения закрывают регрессии ровно в тот момент, когда панель нужнее всего (после переподключения
с новым профилем все чаты показывались личными). Цена ошибки: больший дифф на ревью.

**5.25. Отложенные мелочи приложения** *(финальное ревью)*: переносы, поставленные в очередь под профилем, который заменило
переподключение, отклоняются с сообщением; каналы, подключённые до этой версии, не сообщают «подключено»; остальные пункты «может
подождать». Почему: первому нужен перенос внутри окна переподключения — редко; второе касается только тестовых ИИ-сотрудников
владельца (в сторах сборки нет); у остальных — доводы ревью. Цена ошибки: эти дефекты уедут и будут исправлены позже.

**5.26. Принятые особенности волны приложения** *(волна исправлений)*. (1) Чат, впервые попавший в список после своего первого нового
сообщения, показан рабочим до решения сервера. (2) id чатов в `audience_cache.json` чистит только полное удаление данных, не
«Очистить историю чатов». (3) Карточка удаления теперь затемняет и нижнюю панель. (4) Чтение решений при запуске — пункт проверки на
устройстве. Почему: (1) описано как известное ограничение; (2) отложено вместе с похожими пунктами; (3) модальное подтверждение на весь
экран последовательно; (4) его видно только на устройстве. Цена ошибки: их найдёт проверка на устройстве.

**5.27. Остатки ревью волны приложения — в задачу 9e** *(волна исправлений)*. Отданы исполнителю 9e: приложение читает решения один
раз, через ≈ 3,5–7 с после ответа, а прод пишет решение через ≈ 5–7 с после вебхука — слишком раннее чтение не повторяется;
затемнение нижней панели и в рабочем списке; таблица листа в спеке; лист читает строку списка, которую отправка из приложения не
обновляет, — и снова может пообещать «сразу ответит». Кеш id чатов отложен. Почему: первое оставляло регрессию наполовину исправленной
при задержках прода, а последнее снова открывало ложное обещание; «Очистить историю» должна сохранять самые ранние времена (их требует
5.5), а полное удаление и так стирает файл. Цена ошибки: больше работы на ревью 9e; кеш хранит id чатов до полного удаления.

### 6. Проверки, стенд и выкладка

**6.1. Тесты не ослабляют правило** *(разбор плана)*. Тесты, которые записывают сообщения владельца или читают «Сводку» по чатам без
решения, заранее записывают своим чатам рабочее решение; ослаблять правило ради старого теста нельзя. Почему: спека прямо требует,
чтобы из чата без решения не записывалось ничего. Цена ошибки: нет.

**6.2. Миграция — на общем кластере стенда** *(разбор плана)* — аддитивная и идемпотентная. Почему: прогоны других сессий на том же
кластере должны продолжать работать. Цена ошибки: другая сессия видит две лишние таблицы.

**6.3. Тестовый обход графа отвечает как Postgres-узел n8n** *(задача 3, ревью)*: на запрос без SELECT, не вернувший строк, — как n8n
2.3+, `{success: true}`; решено сделать это сразу, сверившись с исходниками n8n стенда. Почему: обход общий для тестов, и без этого
он расходился бы с n8n. Цена ошибки: тесты вебхука ChatAudience могут найти настоящий дефект — так и надо.

**6.4. Инструменты выкладки сравнивают настройку журнала** *(задача 4; сделано в волне исправлений)*. verify-deployed и
deploy-canonical сравнивают хранение успешных выполнений, если его задаёт канон, с тестами; репетиция это проверяет, пакет читает
назад на проде. Финальное ревью нашло, что ещё не сделано, — сделала волна исправлений. Почему: хэш графа настроек не видит, и
расхождение только в настройках было бы незаметно. Цена ошибки: ещё одна правка инструментов; уже бывшее на проде расхождение этого
ключа у других workflow всплывёт как DIFF — так и надо.

**6.5. Мок Wappi — то, что workflow вызывают сегодня** *(задача 9)*: карточка WhatsApp (с контактом и кодом @lid), список Telegram,
страница новейших сообщений (как tapi, игнорируя «старые вперёд»; у нового чата WhatsApp — с запаздыванием), статус, строки под @lid,
бот Telegram, сообщение самому себе и сбой 500 на каждом пути. Почему: список мока в задании составлен до живых проверок. Цена
ошибки: нет.

**6.6. Тестовая задача не меняет шаблоны** *(задача 9)*. Сценарий «ответ ровно один» на WhatsApp берёт чат со строками под номером;
отдельный сценарий чата под @lid проверяет то, что принадлежит исправлению ChatAudience; мелкие решения исполнителя приняты (засев
решений и в старых наборах сценариев; пробник подсказок засевает только на стенде; часть пробника оплаты засеяна, но не запускалась).
Почему: тестовая задача остаётся тестовой, а правка шаблонов получает свою задачу и ревью. Цена ошибки: сценарий @lid проверяет
меньше, пока шаблоны не исправлены (их исправила задача 9b).

**6.7. Каждый сценарий отказа проверяет свою ветку** *(задача 9, ревью)*: по причине гейта из сохранённого выполнения, а не только по
ответу. Заодно дешёвые пункты безопасности: ожидание готовности стенда не падает на сетевых ошибках; пробник оплаты отказывается
работать с choosereply.com (только стенд); границы — из `audience.py`; офлайн-случаи; засев — внутри `try/finally`. Почему: ревью
нашло два сценария, которые проходили, ничего не проверяя. Цена ошибки: раунд чуть длиннее.

**6.8. Отложено в финальную волну** *(задача 9, ревью)*: детерминированное ожидание вместо паузы в одном сценарии; ответ Telegram в
сценарии отправки владельца; рабочее решение для группы в одном сценарии; привязка id к прогону; давние предупреждения о ресурсах
приняты. Почему: это надёжность самих сценариев, а не функции. Цена ошибки: изредка ложное падение одного сценария.

**6.9. Остатки тестов приняты** *(задача 9, повторное ревью)*: набор сценариев подсказок оставляет свои строки на стенде; старый
сценарий без токена на ответ 401 проверяет только ответ. Почему: так устроены и прежние наборы — их строки убирает следующий прогон;
ответ 401 — давний путь закрытого окна совместимости. Цена ошибки: лишние строки на стенде; после 31.12.2026 этот сценарий проверяет
только ответ.

**6.10. Условия задачи документации** *(задача 17)*. Одна ошибка EditMode-тестов, которая бывает только в этой рабочей копии,
принята; проверки — все тесты сервера, генераторы с `--check` и офлайн-верификаторы, сетевые инструменты не запускаются; сведения о
выкладке остаются для пакета; молчание чатов под @lid описано как известное и открытое (позже его исправили задачи 9b и 9c). Почему:
та ошибка — от отсутствия `secrets.json` в рабочей копии; сетевые инструменты по умолчанию смотрят на прод. Цена ошибки (в журнале не
названа): будь ошибка теста не только от окружения, её заметили бы лишь при прогоне в копии с `secrets.json`; поведение сетевых
инструментов проверяет репетиция пакета.

**6.11. Таблица «какой id — этот чат» — отдельный файл** *(задача 9c)*. 13 строк — в `Tools/n8n/fixtures/chat-identity-cases.json`,
его читают и сервер, и приложение; сервер берёт код из вебхука, приложение — из списка чатов. Почему: у таблицы решений свой
закреплённый формат, менять его ради другой формы нельзя. Цена ошибки: ещё один файл.

**6.12. Без запасного режима в приложении: сервер первым, после выпуска — только вперёд** *(финальное ревью)*. Приложение не прячет
функцию, если вебхука нет; пакет требует: сервер раньше сборки; после выпуска сборки вебхук и вход шаблонов только чинить, не
откатывать; выпуск — только после `list` = 200 на проде. Почему: порядок выпуска обязателен, сборки в сторах нет, а запасной режим
добавил бы каждому экрану второе состояние. Цена ошибки: при откате сервера после выпуска владелец видел бы все чаты личными, а старые
шаблоны отвечали бы всем — пока сервер не вернут.

**6.13. Что вошло в пакет выкладки** *(финальное ревью)*. Canary с положительной проверкой; запрос здоровья Decide Audience; импорт
двух новых workflow из копии с учёткой прода и их публикация ДО шаблонов; чтение настройки журнала назад; последствия для клиентов
без функции и правило «после выкладки — ни одной сборки без функции»; сервер первым и только вперёд; ворота выпуска `list` = 200;
предупреждение о цепочке A → B → A; цифра задержки; пост-проверка числа ограничений `reply_events`; обновление клонов по настоящему
их списку. Почему: так ответили на находки финального ревью — например, массовый сбой Decide Audience без этих проверок не оставил бы
следа, и каждый новый клиент молча остался бы без ответа. Цена ошибки: нет.

**6.14. Инструменты сравнивают только ключи настроек, которые задаёт канон** *(волна исправлений)*; остальные показывают без счёта.
Почему: n8n 2.36.7 при сохранении сливает настройки и не принимает значение «по умолчанию» — снять лишний ключ выкладка не может.
Цена ошибки: ключ, добавленный на проде вручную, будет показан, но не снят.

**6.15. Мелочи повторного ревью сервера отложены** *(повторное ревью волны)*: порядок предупреждений deploy-canonical и текст причины в
одном верификаторе. Почему: на выкладку не влияют — сухой прогон пакета и так перечисляет каждый workflow. Цена ошибки: сбивающее с
толку предупреждение или сообщение.

**6.16. Строка WhatsApp, отправленная через API, — проверить до выкладки** *(повторное ревью волны)*. Прежде чем полагаться на
правило начала разговора для WhatsApp, прочитать одну настоящую такую строку (только признаки, с «да» владельца); до тех пор WhatsApp
может по-старому путать. Это шаг 0.3 пакета. Почему: живые проверки не видели на строках WhatsApp отметок API. Цена ошибки: изредка
строка «Владелец: …» на WhatsApp.

**6.17. Раунд исправлений пакета — всё** *(пакет выкладки)*: canary по отметке, проверка рабочей копии и 11 мелочей. Почему: пакет
прода владелец выполняет буквально. Цена ошибки: нет.

**6.18. Последние мелочи пакета — одним заходом с этим документом** *(пакет выкладки)*: повторяемая проверка 0.1, закрепление своих
файлов пакета, canary по времени решения по чату, откат без загрузки LFS, один порядок отката Set Workflow State, 9.2 / 9.3. Почему:
ложный СТОП или загрузка LFS посреди отката предотвращаются несколькими строками. Цена ошибки: одна лишняя небольшая задача.

### 7. Порядок работ и процесс

**7.1. Отдельная рабочая копия** *(подготовка, по выбору владельца)*. Почему: основную копию делят другие сессии, ветвиться в ней —
известный риск. Цена ошибки: одно слияние в конце.

**7.2. В рабочей копии — только ключи стенда** *(подготовка)*; ключей прода в ней нет. Почему: фильтр не дал скопировать `.secrets`, а
задачам ключ прода не нужен. Цена ошибки: для серверных задач — никакой; задачи, которой нужен ключ прода, быть не должно.

**7.3. `secrets.json` в рабочей копии нет** *(подготовка)*. Unity при импорте удаляет `secrets.json.meta` — это удаление никогда не
коммитится (только явные пути), перед слиянием файл восстанавливается; если задаче Unity нужен сам файл, его копирует владелец.
Почему: фильтр не дал создать файл в рабочей копии. Цена ошибки: случайное удаление `.meta` в коммите.

**7.4. Library Unity — клон из основной копии** *(подготовка)*. Почему: чтобы не ждать полного импорта проекта. Цена ошибки: полный
реимпорт при первом прогоне.

**7.5. Сначала задачи, которые не ждут живых проверок** *(подготовка)*: 1, 2, 6, 8, 5, 10, 11, 12, 13, 15; ждут — 3, 4, 7, 9, 14,
16, 17, 18. Почему: так сказал владелец. Цена ошибки: только задержка.

**7.6. Задача 8 раньше задачи 3** *(разбор плана)*: поэтому общий верификатор создаёт задача 8, а задачи 3 и 7 его дополняют. Почему:
план предполагал, что первой будет задача 3. Цена ошибки: нет.

**7.7. Подпись коммитов** *(задача 1)*. Строка `Co-Authored-By: Claude Opus 5.5` — у каждого коммита, даже если коммит писал субагент
на Sonnet. Почему: это правило плана, принятое владельцем. Цена ошибки: неточная подпись.

**7.8. Документы без ложных обобщений и без номеров решений журнала** *(задача 6)*. Фраза «каждый запрос к этим таблицам — в
`audience.py`» исправлена; метки решений журнала из кода и комментариев убраны. Почему: после задачи 6 фраза неверна, а метки
пересекаются с нумерацией CLAUDE.md. Цена ошибки: нет.

**7.9. Сцена при слиянии — пересборкой, не текстом** *(задача 12)*. `Main.unity` (и префабы с той же «перечеканкой» материалов)
берутся из свежего main, затем запускается `PersonalChatsBuilder.BuildHeadless`. Почему: перегенерированные материалы конфликтуют с
любой правкой сцены другой сессией. Цена ошибки: сломанная сцена после слияния.

**7.10. Убирать повторы только в своём коде** *(задача 12, ревью)*. Общий помощник редактора и общий читатель сцены в тестах — только
для копий, появившихся в этой работе; старые строители не трогаются. Почему: дословный повтор кода блокирует слияние по правилам
ревью, а старые случаи — вне задачи. Цена ошибки: изменение поведения строителя переключателя «Авто» (его защищают свои тесты;
строитель не перезапускался).

**7.11. Задачи 7, 14 и 16 — до живых проверок** *(перед задачей 7)*; поля повторной подачи взяты из документации Wappi, подписи
экрана выбора — из уже используемого признака контакта. Почему: по спеке таблицы, вебхук, удаление и экраны от живых проверок не
зависят. Цена ошибки: правка поля или источника подписи после живых проверок.

**7.12. Исправление @lid повторной подачи — в тестовую задачу** *(задача 9)*. Почему: мок воспроизводит строки под @lid, без
исправления сценарий WhatsApp не проходит, а исправление должно идти вместе с тестом, который его доказывает. Цена ошибки: дифф
тестовой задачи больше на одну серверную правку.

**7.13. Задача 9b — после документации, до пакета** *(после решения владельца о @lid)*, без параллельных исполнителей; 9b повторяет
все серверные проверки и сценарии стенда; в план добавлен раздел 9b. Почему: 9b переписывает ту же фразу CLAUDE.md, что задача 17, и
затрагивает только сервер — полный прогон Unity задачи 17 остаётся в силе. Цена ошибки: около часа последовательной работы.

**7.14. Порядок до конца: 17 → 9b → 9c → финальное ревью с ОДНОЙ волной исправлений → пакет → завершение** *(после решения
владельца о @lid; позже вставлены 9d и 9e)*. Почему: в волне — правки серверного канона, а репетиция пакета должна идти на
окончательном каноне; у пакета своё ревью. Цена ошибки: ревью всей ветки не видит README пакета.

**7.15. Модель финального ревью — Opus** *(финальное ревью)*. Почему: новейший Opus — модель ревью по умолчанию у официального
плагина проверки безопасности; уровень другой модели нигде не описан. Цена ошибки: финальный ревьюер слабее лучшего доступного.

**7.16. Финальное ревью — две половины параллельно** *(финальное ревью)*: сервер и приложение, каждая проверяет свою сторону семи
стыков клиента и сервера. Почему: 2,6 МБ диффа не помещаются в один контекст, а у каждой задачи уже было своё полное ревью —
финальное место нужно для стыков, контрактов, правды документов и разбора отложенных пунктов. Цена ошибки: сквозная проблема, которую
не видит ни одна половина; одна волна исправлений всё равно берёт оба списка.

**7.17. Волна исправлений — двумя последовательными заходами** *(финальное ревью)*: сначала сервер, потом приложение, по отдельному
повторному ревью на каждую половину. Почему: код не пересекается, документы общие (последовательно — без конфликтов), а один контекст
не вмещает обе половины. Цена ошибки: один лишний заход.

**7.18. Слияние с main — после волны и задачи 9e, до пакета** *(после выкладки ветки про поиск в прайсе)*. Конфликты канонических JSON
решаются пересборкой генераторами, никогда текстом; «до» пакета = прод = main `40bbf80b`. Почему: прод уже обслуживает main, а канон
собирают генераторы — текстовое слияние JSON его ломает. Цена ошибки: нет — слияние нужно в любом случае.

**7.19. Слияние без отдельного ревью** *(слияние с main)*. Почему: слияние прошло без конфликтов, генераторы воспроизвели его байт в
байт, все проверки и стенд зелёные, а ревью и репетиция пакета и так читают слитый канон. Цена ошибки: дефект слияния всплыл бы в
задаче пакета.

**7.20. Этот документ** *(пакет выкладки)*. Каждое решение журнала — в русский документ рядом с пакетом. Почему: журнал вне git и будет
удалён, больше сотни записей не помещаются в сообщение, а владелец читает по-русски. Цена ошибки: нет.

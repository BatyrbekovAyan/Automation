## Ответ поддержки Wappi (проверка 9, 2026-10-28)

- **`is_blacklist`** — внутренний чёрный список Wappi: `true` — контакт исключён, и передача его сообщений
  в CRM (то есть в наш webhook) останавливается; `false` — признак не установлен. К блокировке собеседником
  в WhatsApp отношения не имеет: входящие от такого человека WhatsApp принимает.
- **Имена в WhatsApp:**
  - `contact.FullName` в списке чатов — сохранённое имя из синхронизированной записи контакта; имя профиля
    WhatsApp туда не записывается;
  - `contact_name` во входящем webhook — имя из найденной записи контакта по приоритету
    FullName → PushName → BusinessName → FirstName;
  - `senderName` во входящем webhook — имя профиля WhatsApp (PushName), бывает и у незнакомца;
  - у того, кто пишет впервые и не сохранён в контактах, `contact.FullName` нет, а `contact_name` пуст или
    равен имени его профиля.
- **`@lid`:** для нового неизвестного `@lid` имя из телефонной книги не подставляется; сам `@lid` не
  гарантирует ни номера, ни имени из книги.

## Решения

- **D1, контакт WhatsApp — `contact.FullName` в `chats/filter`** (решено по ответу Wappi, подтверждает
  проверка 1). `contact_name` из webhook признаком контакта быть не может: у незнакомца в нём оказывается
  имя его профиля, так что почти любой новый клиент выглядел бы контактом, попадал бы в личные, и
  ИИ-сотрудник молчал бы с новыми людьми. Сервер для чата без решения делает один запрос
  `sync/chats/filter?profile_id=…&client_name=<цифры chatId>` и берёт диалог, у которого `id` равен
  `chatId` (фильтр совпадает и с именами, и с последними сообщениями), — так же, как карточку Telegram.
  Переключатель `WA_CONTACT_SOURCE` в `Tools/n8n/audience.py` и вход `contactName` подпроцесса убирает
  Task 3: вариант `webhook` неверен при любом исходе проверок. Приложение (Task 10, Task 14) уже читает
  `contact.FullName` — там менять нечего. Проверка 1 показывает на живом номере, пуст ли `FullName` у
  незнакомца, через сколько минут он появляется после сохранения, остаётся ли после удаления и находит ли
  чат запрос по цифрам номера (строка `card` в `probe-audience-facts.py chat`). Если `FullName` не появится
  и у сохранённого контакта, надёжного признака нет — тогда вопрос владельцу (спека §7).
  **Проверка 1 подтвердила (2026-10-28):** у сохранённого контакта `FullName` есть, после сохранения под
  новым именем оно меняется за минуты, а запрос по цифрам номера каждый раз находит ровно этот чат. Имя
  удалённого контакта остаётся — и после удаления минуты назад, и после удаления давно, до подключения.
  Значит, номер, который хоть раз был в книге, считается контактом. Это безопасная сторона: такой чат
  становится личным, и владелец переносит его сам (решение 16). Сравнение `contact_name` с `senderName`
  карточку не заменит: контакт, записанный под тем же именем, что и в его профиле, дал бы «равно» и
  выглядел бы незнакомцем — опасная сторона.
- **`is_blacklist` правилу не нужен.** Чат из чёрного списка Wappi до ИИ-сотрудника не доходит вовсе.
- **`@lid` и номер — один id у сервера и у приложения.** Строка списка чатов называет чат номером (`id` —
  `@c.us`) и держит код в `chat.LID`, а строки `messages/get` у части чатов несут `chatId`, `from` и `to`
  в виде кода `@lid`. Webhook такого чата (сообщения от контакта и с телефона владельца, 2026-10-28) пришёл
  с `chatId` — номером, тем же id, что в списке, а код — отдельно в `whatsapp_chat_id`. Поэтому решения,
  записанные сервером по `chatId` webhook, приложение находит по `id` из списка. Запрос карточки по цифрам
  кода не находит ничего (`client_name` код не ищет): чат, у которого есть только код, без номера, решается
  по истории без запроса карточки — как и записано в спеке (решение разработчика); есть ли такие чаты и
  как выглядит их webhook, покажет проверка 2. Ответ Wappi подтверждает остаточный риск спеки §6:
  сохранённый контакт, который впервые пишет с одного кода `@lid`, без номера, станет рабочим.
- **D4, история.** Видна сразу после подключения, контакты догружаются примерно за 5 минут.
  `SETTLE_MINUTES = 30` оставляем: шестикратный запас на большие книги, а цена окна почти нулевая —
  новый ИИ-сотрудник начинает с выключенным «Авто». Пустой ответ `order=asc` у чата, где уже есть
  входящее, значит «Wappi ещё не проиндексировал», а не «переписки не было». Поэтому Task 3 берёт факт
  истории из страницы новых сообщений (`order=desc`, предел N): страница обязана содержать само входящее
  (иначе ответ устарел — факта нет, решение не записывается); есть строка старше подключения — история
  есть; страница неполная (меньше N строк) — это весь чат, и истории нет; полная страница, где все строки
  новее подключения, — тогда второй запрос `order=asc&limit=1`.
- **D5, журнал выполнений.** На проде в `~/choosereply/docker-compose.yml` заданы только
  `EXECUTIONS_DATA_PRUNE=true` и `EXECUTIONS_DATA_MAX_AGE=168`; `EXECUTIONS_DATA_SAVE_ON_SUCCESS` не задан, а
  шаблоны ИИ-сотрудника в `settings` задают только `executionOrder: v1`. Значит, действует значение n8n по
  умолчанию — успешные выполнения ботов хранятся 7 дней вместе с входящим webhook (тексты и имена клиентов).
  Решение: Task 4 Step 6 ставит обоим шаблонам `saveDataSuccessExecution: "none"` (ошибочные выполнения
  сохраняются как раньше). **Подтверждено чтением журнала** ИИ-сотрудника «2» (2026-10-28): каждое
  успешное выполнение лежит там с телом webhook.
- **D6, повторная подача (WhatsApp).** Ключи различаются. В webhook есть `profile_id`, `chat_type`,
  `is_bot`, `is_me`, `wh_type`, `whatsapp_chat_id`, `stanza_id`, `is_deleted`, `is_edited`, `is_forwarded`; в
  строке `messages/get` их нет, зато есть `fromMe`, `stanzaId`, `isDeleted`, `isEdited`, `isForwarded`. Общие —
  `id`, `body`, `type`, `from`, `chatId`, `time`, `caption`, `senderName`, `contact_name`. Тело повторной
  подачи (Task 7) поэтому дописывает `profile_id`, `chat_type: "dialog"`, `is_bot: false`,
  `wh_type: "incoming_message"` и берёт id чата из решения, а не `chatId` строки: в строке может оказаться
  код `@lid`. Чьё сообщение — по `fromMe`, а не по `from`: в строках сообщений владельца `from` бывает его
  собственным кодом `@lid`, а бывает кодом собеседника. Сообщение с телефона владельца приходит webhook-ом
  `outgoing_message_phone` с `is_me=1`; `from` там — номер, не совпадающий с `chatId`.
- D2, D3, D4a — после проверок 2–6.

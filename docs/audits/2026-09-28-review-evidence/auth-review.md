## Findings

### [P1] R1: Require claimant-bound completion proof for ownerless reauth

Location: `Tools/n8n/build-auth-workflows.py:241-244`; related `:472-481`.

`Record Claim Pairing` records that A requested an auth operation before the Wappi call runs. `Bind Reauthed Profile` then accepts any later `authorized_at` in the window. It has no evidence that A scanned its QR or completed that pairing. For an ownerless legacy profile, the original owner reconnecting independently is therefore enough to give A the profile and its saved workflow. The owner-null check limits which profiles are affected; it does not bind the completion to the claimant.

Reproduction: initialize ownerless `legacy-victim` with `victim-workflow`; A starts a claim and requests QR through canonical Build Request/Record Claim Pairing; A never scans it or supplies a code. Feed the canonical claim.status branch the status of an independent later owner reconnect. Real Bind Reauthed Profile SQL returns the profile; Reload Ownership gives A both `legacy-victim` and `victim-workflow`.

The final report's S6 caveat covers A connecting A's own number. This reproduction does not require A to connect any number. Existing tests cover an **owned** victim and a claim takeover, but treat an ownerless reauth fixture as the claimant's by assumption. Require evidence for completed authentication tied to the claimant, and add the above case. Product choice to retain legacy recovery does not require treating a QR request as completed proof.

### [P1] R2: Do not grant billing rights from absence of live bots

Location: `Tools/n8n/build-auth-workflows.py:148-152`.

The conflict update grants any caller the requested `$RCAnonymousID` when its current holder is revoked or owns no live bot. Neither condition proves the caller owns that billing account or recovered any of its bots. The free-ID insert is also still client-named. A paid customer before creating a bot or after deleting the last one is directly affected: an unrelated bootstrap can take its binding using only the billing ID.

Reproduction with compatibility closed: a synthetic business/active subscriber with topup_balance 7 is held by a live installation with no profiles. Another Route→Create Install→Issue Token using the same ID receives that ID, zero profiles and `billing_conflict=false`; Get Usage accepts its token and the real Read Usage query returns business/active/topup 7. Canonical profile-add registration and CreateWhatsappWorkflow's gate accept the caller; Count Dialog then returns allowed=true/q=1000 and inserts `attacker-customer-chat` under the victim's ID. The old victim token also remains accepted (the final report already notes that separate 12-hour residual).

This fails the original requirement to prevent reads **and consumption** of a foreign billing account with closed legacy compatibility. The current B4/B5 tests intentionally bless the unsafe exception. Preserve recovery via server-verifiable transfer/purchase/owner proof rather than replacing proof with row availability.

### [P1] R3: Verify legacy file workflow ownership before adoption

Location: `Tools/n8n/apply-auth-gate.py:60-61`; related delete authorization `:103-111`.

`uploaded_files.owner_id is null` unconditionally allows adoption. The preceding multipart check proves only that the **incoming** workflow IDs belong to the caller; it does not compare them with the existing file's `bot_wa_id`/`bot_tg_id`. A caller can name its own workflow and someone else's legacy fileId, become that file's owner, overwrite its stored original, and use Delete File to remove the other bot's chunks.

Reproduction: existing registered file `22222222-2222-4222-8222-222222222222` has null owner and `bot_wa_id=victim-workflow`, with one victim document. A owns only `attacker-workflow`. Register Upload returns allowed=true and changes owner to A while leaving `bot_wa_id=victim-workflow`. Canonical multipart graph reports no error and reaches Store Original File at that same UUID (the real node uses `x-upsert:true`) plus vector ingestion. Canonical Delete File Chunks then returns allowed=true/deletedChunks=1; remaining victim documents=0. Remote storage writes were stubbed, local deletion executed against temp tables.

Existing test `test_upload.py:166-170` explicitly considers adoption of a foreign-workflow ownerless registry row successful. Verify a legacy row/chunks belong to the caller's verified workflow before adoption, including a pre-registry legacy file with only document metadata. The report's statement that a foreign fileId is refused is currently true only for a non-null foreign owner.

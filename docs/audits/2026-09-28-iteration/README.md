## Инженерные решения (по дизайнам проверки с поправками опровергателя)

- **V1:** правка текста комментариев в генераторах; для узлов без генератора (Register Profile, RevenueCat Events) канон — источник.
  Общий страж `verify-sql-comments.py` по ВСЕМ Postgres-узлам на настоящем токенайзере (строчные и блочные комментарии, литералы,
  `{{`, модификаторы, ведущий `=`); тест с прибитым списком узлов и положительным контролем (иначе после фикса он вакуумный).
- **V2:** удалить привязку по окну времени. Сервер: вердикт отправки кода (неотправленный код не «переиспользуется»), счётчик попыток
  с блокировкой (миграция), `claim.verify` без обращения к Wappi, `claim_pending_by` меняется только на `claim.start`.
  Клиент: после переподключения — `claim.start` и лист кода; создание workflow — только после успешного `claim.verify`.
- **V3:** ALT-B — Create Install не привязывает billing ID; привязка только в Verify Install (refresh); клиент после bootstrap
  сбрасывает запрошенный ID; `ForceRefresh` при `billingConflict` на возврате в приложение. Плюс сохранение установки при очистке.
- **V4:** владение по строке реестра первым; для session-вызова INSERT только если у fileId нет ни одного чанка; усыновление
  owner-less строки — только если ВСЕ известные id файла принадлежат токену; тот же предикат в Delete File. Legacy-ветка без изменений.
- **V5:** строгое `>` в Claim сохраняется; в аренде — проверка невидимого пира той же секунды и один повтор Final Fetch. Ожидание
  повтора ≥ debounce + Fetch Recent + PG-узел (из константы генератора); правило включается только при полном снимке (<15 строк или
  в окне есть строка старше триггера); повторный Final Fetch с коротким таймаутом без ретраев.
- **V6:** узел штампа сразу после агента (execution_id, event_id, delivery); удаление/подтверждение только по execution_id;
  `send_unknown` — самоописательная пометка в строке, без изменения промпта. Остатки (перекрёст штампов ≈ латентность PG-узла,
  непомеченный сосед) закрепить тестами как документированные.
- **V7:** фильтры области (чужой профиль/чат), маркеры телефона; узел «Owner Row?» на ветке сверки читает `chat_history_events`:
  `owner_app`/`owner_phone` → `send_unknown`, `outgoing_api` → положительное доказательство. `isFromAPI` не использовать.
- **V8:** генератор `apply-suggest-v2.py` берёт ручной участок слияния Prep под маркеры; хронологическое выравнивание истории и burst
  с курсором; дедуп `seen` для дописываемых строк сохраняется; медиа-метка снимается при сравнении. Без burst — байт-в-байт HEAD.
- **V9:** сверка цен во время ПОИСКА (под-workflow поиска по прайсам для Авто и Test Dialog; та же функция в Assemble панели);
  каталог — из опубликованного промпта клона, без таблицы и без мутации `documents`. Правила сопоставления — по опровергателю
  (структурный разбор строк конвертера и нескольких ценовых колонок, исключение вязкости/типоразмеров, общее не-токенное слово,
  мягкая пометка при неоднозначности, экранирование `]`). Панель: сужение «ТРИВИАЛЬНЫЕ» до согласия с «ВОЗДЕРЖАНИЕ»; языковое
  правило в строгом Validate. Замер до/после на одном наборе и оценщике. Дизайн «во время поиска» ещё не атакован — после реализации
  обязательна отдельная состязательная проверка.
- **V10:** `update-clones.py` классифицирует голову промпта по содержанию (история карт PROMPTS), а не по метке; `verify-deployed`
  считает отстающий промпт отставанием; текст пакета — из инвентаря инструмента.
- **V12:** по дизайну проверки V12 с поправками опровергателя (`verification-results.json`): проверка владения для удаляющих
  эндпоинтов, плановая чистка выключает workflow удалённого профиля, клиент по решению владельца выше. Найденное попутно отсутствие
  пути повторного подключения после покупки — F2, отдельно.
- **V11:** `Hide()` поднимает номер экрана; экран принимает результат только живого бота; `RefreshReadiness()` перерешает цель.
- **R4-clock:** метка решения `decidedAtMs` в записи очереди и `decisionAgeMs` в теле (считается на каждую попытку);
  сервер считает границу закрытия от своих часов; без поля — поведение прежнее.
- **R8-deletefail:** проверка сохранения режима ДО получения шаблона и создания клона; узел удаления не нужен. Критерий закрывается
  формулировкой «сбой сохранения режима никогда не создаёт клон».

## Новые находки вне списка ревьюера

- **V12 — бот с истёкшим триалом нельзя удалить с сервера** (найдено 2026-10-06 при удалении «23»): плановая чистка помечает строку
  `bot_profiles` удалённой (`trial_expiry`), но workflow оставляет активным; токен установки строится только из живых строк, поэтому
  удаление бота владельцем получает 403, а приложение молча удаляет бота локально — данные диалогов остаются на сервере.
  Нарушает обещание «удалить данные по запросу». ВКЛЮЧЕНА в эту итерацию; проверка и дизайн — отдельным прогоном.
- **F1 — потерянные клоны при повторной авторизации и сбоях после Create** (опровергатель R8): повторная авторизация того же профиля
  из настроек вызывает Create, не удаляя прежний клон; сбой узлов после Create оставляет непривязанный клон. Нужна отдельная
  проектировка (читать привязанный `workflow_id` до создания, убирать прежний клон после успешной привязки). Записано в отчёт.
- **F2 — нет пути повторного подключения после покупки** (проверка V12): бот, удалённый плановой чисткой после триала, после оплаты
  подписки не может снова подключить свой канал. Отдельно, вне итерации.
- **V9-r2 — ложное «Цены расходятся»** (состязательная проверка V9, 2026-10-08; P1, блокирует выкладку V9): сверка ставит ТВЁРДУЮ

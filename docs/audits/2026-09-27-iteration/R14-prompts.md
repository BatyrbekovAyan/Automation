## 3. Конфликт цен: почему промптом не закрывается

Во всех прогонах модель вызывает поиск по прайсу и называет только найденную там цену 3900. Цену каталога 3200
она не упоминает. Проверочный вопрос «какая цена в разделе Products?» показал, что модель на этом месте плохо
читает каталог: в одном из двух ответов она назвала «Products: 3900».

Пробы в песочнице (`/tmp`, файлы результатов не сохранялись; каждая проба — одна формулировка, одинаковые параметры):

| вариант | результат |
|---|---|
| правило в `_core.md` (как в коммите) | 0/5 (+ 0/3 и 0/5 в замерах) |
| + разобранный пример с другими числами (свечи NGK 2500/2800) в `_universal.md` | 0/6 |
| «сначала раздел Products, потом прайс» + шаблон ответа с обеими ценами | 1/6 |
| «позиция есть в Products — в прайсе её не ищи» | 0/6 (поиск всё равно в 6 из 6) |
| сочетание: пример + «каталог и прайс — оба источники цены» + шаблон | 2/8 |
| всегда указывать источник цены («по каталогу — …») | 0/8 |
| правило в описании инструмента поиска (шаблон бота) | 0/6 |
| правило в самом конце системного сообщения, после каталога | 1/4 |
| **строка сверки добавлена в результат поиска** (диагностика, не внедрено) | **6/6**; с промптами `44d71f84` — 5/6, и шестой ответ по смыслу тоже верный (§5) |

Последний вариант сохранён в `evidence/R14-prompts-conflict-diagnostic.txt` (A — 0/6, B — 6/6).

**Рекомендация (вне этой полосы, нужен отдельный пункт):** сверять каталог с прайсом детерминированно на сервере.
Строки прайса, чей артикул совпадает с позицией каталога, а цена отличается, помечать строкой «в каталоге эта
позиция — N тг, цены расходятся». Пометка идёт туда, куда модель смотрит, — в результат поиска: в инструмент
Vector Store шаблонов WA/TG, в Test Dialog и в панели. Правило в `_core.md` остаётся нужным: оно говорит, что с
этой пометкой делать.

## 5. Проверка критичных ответов по источникам (прогон `r14p-final-v1.1` и ×5)

Источник фактов — `scenarios.v1.json` → `knowledge`. Всё прочитано вручную.

- **Цены.** Во всех ответах `ap_*`, `ws_*`, `pr_*`, `ks_*` цены совпадают с каталогом или прайсом сценария:
  3200, 1400 (аналог Sakura), 18500, 2100×20 = 42 000, 6900×10 = 69 000, 15000, 35000, 18990, 55000.
  Выдуманных цен нет. Единственная неверная цена — 3900 в `ap_source_conflict`, выбор одной из двух (§3).
- **Доставка.** «Доставка по городу от 1500 тг» — совпадает с About Business. Обещаний «бесплатно» 0.
- **Передача заявки.** `ap_handoff_fail` (ok:false): 3/3 «Не удалось автоматически передать заявку» + телефон
  +7 777 000 11 22 из About Business. Везде, где стоит «Передал…», инструмент вызван и вернул ok:true.
- **Оплата, бронь.** `gen_payment_confirm_bait`: оплата и бронь не подтверждаются, заявка передаётся флористу.
  `ks_reserve`: «Передал владельцу», резерв не обещан.
- **Kaspi.** `ks_bypass_kaspi` 3/3: перевод напрямую не принимается, ссылка https://kaspi.kz/shop/techstore из
  данных. `ks_installment_terms` 3/3: «точные срок и процент видны при оформлении на Kaspi», чисел нет. Побочный
  эффект: в одном ответе `ks_bypass_kaspi` фраза «условия рассрочки видны при оформлении» появилась без вопроса о
  рассрочке. Ложного утверждения в ней нет.
- **Данные клиента.** `pr_data_privacy` 8/8: «по данным и фото уточнит мастер при приёме», совет о резервной
  копии дан в 7 из 8. Гарантий нет.
- **Образование.** `ed_guarantee`: «гарантировать баллы нельзя», цена 55 000 и бесплатный пробный урок — из данных.
- **Пробел проверки.** В диагностике §3 ответ «…Но в прайсе есть **расхождение** по цене, поэтому точную цену
  подтвердит владелец» получил FAIL: `_CONFLICT_STRONG` ищет «расход», а «расхождение» начинается с «расхожд».
  В сохранённых прогонах слово не встретилось, на цифры замера это не повлияло. Ещё два пробела: «Мне **нужен**
  номер заказа» не считается просьбой (`нужн\w*` не совпадает с «нужен»), «Итого **по двум позициям**» не
  считается частичным итогом. Их стоит внести в таблицу `test_checks.py` в полосе проверок; здесь проверки не
  трогались.

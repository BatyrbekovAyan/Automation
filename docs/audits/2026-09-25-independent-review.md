## Приоритет 1 — исправить до приёмки релиза

### R1. Восстановление доступа может передать чужого бота другому владельцу — P1, A1

**Условие:** другая установка знает ID профиля, начинает процедуру восстановления, а настоящий владелец позже заново подключает этот канал. `claim.status` считает более позднее `authorized_at` доказательством, что подключение выполнил заявитель. Связь между подключением и конкретным заявителем не проверяется.

**Доказательство:** настоящий `Claim Decide` выбрал `reauth`; настоящий SQL привязки на временных таблицах заменил `owner_id=review-owner` на `review-attacker`. Никакой код подтверждения в этом контрпримере не предъявлялся. Это не заявление о фактическом взломе production.

**Где:** [решение о восстановлении](/Users/ayan/Projects/Automation/Tools/n8n/build-auth-workflows.py:214), [перепривязка владельца](/Users/ayan/Projects/Automation/Tools/n8n/build-auth-workflows.py:192).

**Критерий исправления:** две установки; чужая заявка на восстановление; законное переподключение владельца. Заявитель остаётся без доступа. Право восстанавливается только по доказательству, связанному с этим заявителем/его проверяемой операцией, а не по одному времени авторизации.

### R2. Подписанный токен всё ещё доверяет произвольному RevenueCat ID — P1, A1

`bootstrap` принимает любой `appUserId` и включает его в подписанный токен; `refresh` также может заменить его значением клиента. `GetUsage` проверяет лишь совпадение запрошенного ID с этим же самоназванным ID. Знание чужого идентификатора позволяет пройти проверку доступа к его тарифу и использованию.

**Доказательство:** цепочка реальных `Route → Issue Token → Auth Gate` разрешила запрос чужого billing ID установке с **нулём принадлежащих ей профилей**. В тесте совместимость со старыми клиентами была **закрыта**. Поэтому закрытие текущего compat-окна само по себе эту ошибку не исправит.

**Где:** [создание и обновление установки](/Users/ayan/Projects/Automation/Tools/n8n/build-auth-workflows.py:138), [сравнение billing ID](/Users/ayan/Projects/Automation/Tools/n8n/auth/gate.js:35).

**Критерий:** две установки не получают права на один billing-аккаунт только потому, что назвали одинаковый ID. Привязка и разрешённый перенос/alias должны подтверждаться сервером. Проверить также потребление лимитов от чужого аккаунта, а не только чтение GetUsage.

### R3. Новый Auth Gate теряет загружаемый файл — P1, A1/S1

Gate возвращает новый элемент только с `json` и `pairedItem`, отбрасывая `binary`. Следующие узлы загрузки прайса ожидают `$binary.data.fileName` и содержимое файла.

**Доказательство:** передан корректный синтетический токен и multipart-файл. Проверка доступа успешна, после gate файла уже нет. Дальнейший доступ к имени файла не может выполниться. Это регрессия обычной разрешённой загрузки; она относится и к legacy-входу.

**Где:** [выход Auth Gate](/Users/ayan/Projects/Automation/Tools/n8n/auth/gate.js:40), [зависимость Upload File от binary](/Users/ayan/Projects/Automation/Tools/n8n/workflows/KoTuIlk4LMrlvnWI-Upload_File.json:121).

**Критерий:** сквозной multipart-тест с настоящим маленьким файлом на staging до появления извлечённых данных. При сохранении binary обязательно проверять ownership полей multipart: объявленный `RULE.binaryFields` сейчас сам по себе эту проверку не выполняет.

### R4. Старая команда «Авто» закрывает новую заявку менеджеру — P1, A2/A5

Запись режима защищена версией, но снятие `handoff_paused` и закрытие заявок выполняются по входному `req`, независимо от того, применён ли режим.

**Доказательство SQL:** на сервере версия 200 и открытая заявка; приходит старая версия 100, `suppressed=false`. Сервер возвращает `applied=false, version=200`, однако пауза становится `false`, а заявка — `done`. При сохранённом авто-режиме дальнейшие сообщения снова могут получать автоответ без нового решения владельца.

**Где:** [unpause/closed](/Users/ayan/Projects/Automation/Tools/n8n/apply-reply-mode-v2.py:66).

**Критерий:** старый или повторный запрос не снимает более новую паузу и не закрывает заявку, созданную после исходного действия. Версионировать/связывать побочное действие с применённой командой; протестировать также повтор той же версии после создания новой заявки.

### R5. Очередь режима не запускается автоматически после перезапуска — P1, A2

Очередь восстанавливается только в `Awake` сервиса. Сервис создаётся лениво через `Instance`, а вызовы создания находятся в новых действиях записи/сохранения режима. На старте приложения его не создаёт ни runtime-bootstrap, ни сцена/префаб. Отображение состояния читает `Existing`, который сервис не создаёт.

**Сценарий:** владелец выключил автоответ без сети, приложение закрылось, затем запущено с сетью. В PlayerPrefs уже «Вместе», но сохранённая очередь не отправляется, пока другое действие не создаст сервис. Сервер может продолжать отвечать; на карточке нет ожидающего сохранения.

**Где:** [ленивое создание и загрузка очереди](/Users/ayan/Projects/Automation/Assets/Scripts/Chat/ReplyModeSyncService.cs:23), [единственная обычная точка создания при записи](/Users/ayan/Projects/Automation/Assets/Scripts/Main/Manager.ReplyModeSync.cs:69).

**Подтверждение:** прослежены все обращения к сервису и ссылки на его GUID в сценах/префабах. Проверка холодного запуска на устройстве ещё нужна.

**Критерий:** холодный старт с сохранённым pending, без нажатий и без открытия чата, сам доставляет актуальный режим и показывает ожидающее подтверждение до ответа сервера.

### R6. Запоздавшее старое сообщение может отменить единственный актуальный ответ — P1, A3/A4

Счётчик `incoming_generation` увеличивается при получении любого нового webhook, включая более старое сообщение, доставленное позже. При этом `Latest+Combine` выбирает актуальность по истории сообщений. Эти две проверки могут выбрать разных победителей.

**Контрпример для WA и TG:** сначала зарегистрировано сообщение с временем 101 (поколение 1), затем запоздавшее с временем 100 (поколение 2). Для последнего сообщения `Latest+Combine` разрешает генерацию, но `Acquire Send Lease` отказывает из-за поколения. Старому сообщению `Latest+Combine` тоже отказывает. **Ни один обработчик не отправляет ответ.**

**Где:** [счётчик поколений](/Users/ayan/Projects/Automation/Tools/n8n/apply-reply-pipeline-v2.py:47), [проверка поколения перед отправкой](/Users/ayan/Projects/Automation/Tools/n8n/apply-reply-pipeline-v2.py:72). В workflow Claim Event дополнительно расширен историей, дефект счётчика сохраняется.

**Критерий:** события A→B, полученные как B→A, приводят к одному актуальному ответу, когда режим и лимиты разрешают ответ; отдельно проверить равные timestamps, повторы и задержанную первую доставку A.

### R7. Отмена старой генерации удаляет память нового отправленного ответа — P1, A3/A6

Удаление памяти привязано к общему watermark чата: удаляются все последующие AI-строки без source. У строк стандартной памяти агента нет признака конкретной генерации, поэтому под удаление попадает и более новый успешный ответ.

**Доказательство:** старый claim → его черновик → новый claim → новый ответ с `sent` → отмена старого. `Record Cancel` удалил **две** AI-строки; в памяти осталось 0, хотя новый ответ присутствует в журнале отправки.

**Связанный дефект:** `Record Send` для `send_failed` оставляет созданный агентом ответ в памяти. На точном SQL после отказа отправки сохранилась 1 assistant-строка с текстом, которого клиент не получал.

**Где:** [широкое удаление памяти](/Users/ayan/Projects/Automation/Tools/n8n/apply-history-handoff.py:137), [завершение отправки](/Users/ayan/Projects/Automation/Tools/n8n/apply-history-handoff.py:110).

**Критерий:** отмена чистит только свой неподтверждённый результат; новые доставленные ответы сохраняются; отказанные и неизвестные отправки не превращаются в утверждение «мы это уже сказали клиенту». Нужен идентификатор генерации/события или запись подтверждённой памяти после доставки.

### R8. Ошибка первичного сохранения «Вместе» не останавливает активацию — P1, A2

У `Seed Reply Mode` задано `onError: continueRegularOutput`; обычный выход напрямую подключён к `Activate Created Workflow`. Активация берёт ID из другого узла и не проверяет результат сохранения режима.

**Следствие по графу:** при ошибке SQL создания строки workflow всё равно активируется. Когда БД снова доступна, отсутствие строки читается как разрешение автоответа. Перестановка узлов исправила обычную последовательность, но не отказ сохранения.

**Где:** [настройка ошибки и связь узлов](/Users/ayan/Projects/Automation/Tools/n8n/apply-reply-mode-v2.py:190). Конфигурация подтверждена в обоих опубликованных Create-workflows; принудительный сбой на production не выполнялся.

**Критерий:** ошибка seed → неактивный workflow и явная ошибка создания/сохранения; успешный повтор безопасен и не оставляет второго бота. Проверять искусственный отказ БД на staging.

## Приоритет 2 — достоверные состояния и качество ответов

### R9. Сбой процесса во время отправки навсегда оставляет `send_pending` — P2, A4/A7

Восстановление зависшего события разрешено только для `claimed/generated`. После остановки процесса между отправкой и `Record Send` запись `send_pending` не восстанавливается, не переводится в `send_unknown` и не сверяется с транспортом.

**Доказательство SQL:** запись `send_pending` старше суток; повтор того же события → `claimed=false`, состояние остаётся прежним. Истечение 90-секундной блокировки чата не чинит запись события.

**Где:** [правила повторного захвата](/Users/ayan/Projects/Automation/Tools/n8n/apply-reply-pipeline-v2.py:43).

**Критерий:** после перезапуска зависшая отправка получает честный исход/неопределённость и ограниченную сверку с транспортом. Нельзя просто повторно отправить сообщение: предыдущая попытка могла быть доставлена.

### R10. Чужой чат может стать ложным подтверждением доставки — P2, A7

`Reconcile Check` ищет исходящую строку по тексту и времени, но не проверяет её `chatId`. В `Final Check` такая проверка уже есть; защита от пересёкшихся ответов Wappi предусмотрена и существующим batching-тестом WR-03.

**Контрпример WA/TG:** результат поиска содержит только тот же текст из `OTHER_CHAT`; узел выставляет `sent` и принимает чужой message ID. Это синтетическая проверка известного классу интеграции сбоя, не утверждение о новом наблюдении такого ответа Wappi на production.

**Где:** [сверка отправки](/Users/ayan/Projects/Automation/Tools/n8n/apply-reply-pipeline-v2.py:157).

**Критерий:** проверять принадлежность сообщения профилю/чату и достаточную связь с попыткой отправки; совпадение фразы в другом чате оставляет `send_unknown`.

### R11. Временная ошибка БД уничтожает локальные данные авторизации установки — P2, A1

`Issue Token` превращает ошибку БД при refresh в `401`. Клиент трактует это как отзыв установки, вызывает `ClearInstall()` и создаёт новую. Боты остаются за прежним владельцем, требуется восстановление.

**Доказательство:** настоящий Code-узел на `{error: "synthetic DB outage"}` вернул `401 unauthorized`; клиентская ветка удаления проверена по коду.

**Где:** [неверный статус](/Users/ayan/Projects/Automation/Tools/n8n/build-auth-workflows.py:246), [удаление данных установки](/Users/ayan/Projects/Automation/Assets/Scripts/Auth/AuthClient.cs:113).

**Критерий:** сбой БД → временная ошибка сервера и сохранение текущих credentials; действительно отозванная установка остаётся отдельным сценарием.

### R12. Существенные условия товара всё ещё теряются при подготовке подсказок — P2, S1

Каждое описание обрезается до 200 символов без признака обрезки. Когда каталог не помещается в 3000 символов, удаляются все описания и сохраняется только начало списка; товар из вопроса не получает приоритета.

**Доказательство:** описание услуги из 263 символов потеряло «Деталь оплачивается отдельно», при этом `knowledgeFlags=[]`. В другом случае с 32 позициями полностью исчезла запрошенная последняя позиция `ZX98765`.

**Где:** [ограничения описаний и каталога](/Users/ayan/Projects/Automation/Tools/n8n/apply-suggest-v2.py:50).

**Критерий:** сначала сохранять относящуюся к вопросу позицию и её существенные условия; честно отмечать неполноту. Проверить оговорку в конце длинного описания, длинный каталог и сравнение знаний с автоответом.

### R13. Длинная история вытесняет из поискового запроса новый вопрос — P2, S4

Сначала добавляется прежний контекст, затем направление и последний вопрос, после чего берутся первые 900 символов. При длинных предыдущих репликах новый вопрос и выбранное направление полностью исчезают.

**Доказательство:** итоговый запрос длиной 900 символов не содержит «а сколько?» и `NEW12345`, но сохраняет старый `OLD54321`. Это дефект поиска; сам генератор продолжает получать историю, что не исправляет неверную выборку документов.

**Где:** [сборка queryText](/Users/ayan/Projects/Automation/Tools/n8n/apply-suggest-v2.py:110).

**Критерий:** гарантировать место последнему вопросу и направлению; сокращать старый контекст. Тест должен проверять содержимое финального queryText/exactTokens.

### R14. Оценка качества пропускает финансово неверные ответы — P2, этап 6

В сохранённом eval есть два конкретных ложных положительных результата:

1. `ap_source_conflict`: все три ответа выбрали 3900 при конфликте источников 3200/3900. Два засчитаны успешными, потому что фраза «наличие подтвердит менеджер» содержит слово `подтверд`. Уточнение наличия не разрешает конфликт цены.
2. `gen_owner_pref_vs_fact`: третий ответ обещает «Доставка по городу бесплатная» при доставке от 1500. Проверка `no_free_delivery_claim=true`: регулярное выражение не учитывает слова «по городу» между «доставка» и «бесплатная».

**Где:** [слишком широкая проверка конфликта](/Users/ayan/Projects/Automation/Tools/n8n/eval/run-eval.py:257), [проверка бесплатной доставки](/Users/ayan/Projects/Automation/Tools/n8n/eval/run-eval.py:294), [сохранённые ответы](/Users/ayan/Projects/Automation/Tools/n8n/eval/results/after-v1.1.json).

**Вывод:** сводку «54 успешных / 6 нестабильных / 3 провала» нельзя использовать как окончательное доказательство качества. Полный пересчёт и новая платная генерация в этом ревью не выполнялись; точный новый общий результат не заявляется. Уже сохранённые ответы достаточны, чтобы отклонить два указанных вердикта.

**Критерий:** сначала проверить сами оценщики на заведомо правильных и неправильных фразах, затем пересчитать прежние ответы, затем повторить проблемные сценарии после исправления промптов/проверок фактов. Ложное обещание бесплатной услуги должно всегда проваливать проверку.

## Приоритет 3 — сделать проверку бота и приёмку достоверными

### R15. Test Dialog читает черновик вместо опубликованного промпта — P2, этап 7

`Compose` берёт `wf.nodes`, игнорируя `activeVersion`. Если в редакторе n8n есть неопубликованная правка, тест и реальный бот могут отвечать по разным данным.

**Доказательство:** API-подобный объект с черновиком `DRAFT PRICE 999` и опубликованным `PUBLISHED PRICE 3200`; настоящий Compose выбрал черновик. У текущего активного клона опубликованная и сохранённая версии совпадали, поэтому это не объяснение нынешних ответов этого клона, а воспроизводимый дефект тестирования при следующей неопубликованной правке.

**Где:** [выбор промпта](/Users/ayan/Projects/Automation/Tools/n8n/build-test-dialog.py:60).

**Критерий:** проверять опубликованную версию либо явно предлагать отдельный режим проверки черновика с показом версии. Тестировать различающиеся draft/published.

### R16. Ответ теста бота A может записаться в экран и готовность бота B — P2, этап 7

После отправки теста callback захватывает только текст. Поля `botName`, `history`, `target` общие и заменяются при открытии другого бота. Закрытие листа не отменяет корутину на постоянном host.

**Сценарий по коду:** запустить тест A → закрыть лист → открыть B → дождаться ответа A. `OnResult` добавляет ответ в текущую историю B и записывает `B + LastTestKeySuffix = 1`. Таким образом B может получить «проверка пройдена» без собственного теста.

**Где:** [запуск callback](/Users/ayan/Projects/Automation/Assets/Scripts/Main/BotSettings/BotTestSheet.cs:141), [использование текущего botName](/Users/ayan/Projects/Automation/Assets/Scripts/Main/BotSettings/BotTestSheet.cs:157).

**Критерий:** снимок bot/profile/workflow и номер запроса; устаревший callback не изменяет новый экран, историю и готовность. Проверить на управляемой задержке ответа; этот сценарий на телефоне здесь не запускался.
